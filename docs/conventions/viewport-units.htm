CONVENTION
Viewport Units
Cuándo usar svh y cuándo dvh para alturas relativas al viewport, evitando el jank de las barras del navegador en mobile.
Scope: UI / StylingStatus: Active
01
Overview

En mobile, las barras del navegador (URL, herramientas) aparecen y desaparecen al scrollear, por lo que la altura del viewport no es un valor único. CSS expone tres unidades para esto: svh (small viewport, con las barras visibles), lvh (large, con las barras ocultas) y dvh (dynamic, que cambia en vivo entre ambas). Elegir la unidad equivocada produce contenido tapado o reflow visible mientras el usuario scrollea.

02
Goal

Mantener un comportamiento estable y consistente en Chromium y WebKit (Safari/iOS), que es donde estas unidades más divergen. dvh llena más pantalla pero provoca jank al togglear las barras; svh es estable pero deja un margen cuando las barras se ocultan. La regla acota cada unidad al caso donde su ventaja es real y su desventaja no aplica.

03
Rules
CasoUnidadPor qué
min-height de páginas y secciones que deben llenar al menos la pantalla y cuyo contenido puede crecersvhGarantiza el alto mínimo de forma estable; no hay reflow cuando las barras aparecen u ocultan.
Scroll containers acotados al viewport (max-height: calc(100svh - …)), típicamente sidebars sticky o fixed en desktopsvhEl borde no se mueve; la barra del navegador no togglea en esos contextos, así que dvh solo agregaría inestabilidad.
Overlays fullscreen de mobile (position: fixed, ocupan toda la pantalla, sin scroll de la página de fondo)dvhLlenan todo el espacio disponible. El scroll interno del overlay no togglea las barras del navegador, así que no introduce jank.
  • No usar 100vh en código de producto: en mobile resuelve al viewport grande y deja contenido tapado detrás de la barra de URL.
  • No hacer un reemplazo masivo svh → dvh "para mobile": en diálogos centrados y scroll containers de desktop, dvh agrega jank sin beneficio.
  • Mantener las clases min-h-svh / h-svh generadas por shadcn/ui (por ejemplo en components/ui/sidebar.tsx) tal como vienen: ya cumplen la convención.
Al combinar dvh con env(safe-area-inset-bottom) en un overlay fullscreen, validar en iOS real que la zona de acciones inferior no quede clippeada ni salte cuando la barra del navegador togglea.
04
Usage
// Página/sección: alto mínimo estable.
.SignInPage {
  min-height: 100svh;
}

// Scroll container de desktop acotado al viewport.
.Sidebar {
  max-height: calc(100svh - 3.5rem);
  overflow-y: auto;
}

// Overlay fullscreen de mobile: llena toda la pantalla.
@media (max-width: 1023px) {
  .Dialog {
    height: 100dvh;
    max-height: 100dvh;
  }
}
05
Notes
  • Esta convención es la aplicación concreta de la regla "Cross-engine compatibility (Chromium and WebKit)" de AGENTS.md, que marca svh/dvh/vh como unidades de comportamiento divergente entre motores.
  • Si un overlay fullscreen depende de un track fr para su scroll interno, darle un alto definido (con svh o dvh según esta tabla) en vez de depender del intrinsic sizing, que diverge entre motores.
