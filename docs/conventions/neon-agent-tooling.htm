Neon: herramientas para agentes

Configuración de Codex y autenticación para validar migraciones en ramas aisladas.

Instalación y alcance

La CLI global neon permite administrar el proyecto existente. Las skills del repositorio están en .agents/skills/neon/, .agents/skills/neon-postgres/ y .agents/skills/neon-postgres-branches/; skills-lock.json registra su origen. Instalar solamente las skills necesarias para la tarea.

El MCP remoto de Neon está configurado para Codex en .codex/config.toml, con OAuth y limitado al proyecto cold-firefly-92947172 (TuTribu). La configuración del repositorio contiene la URL, sin credenciales. Las sesiones se mantienen fuera del repositorio mediante las herramientas correspondientes.

Esta configuración complementa los servidores globales de Codex. Las nuevas skills y herramientas requieren que Codex vuelva a cargar su configuración antes de estar disponibles en una conversación existente.

Renovar y comprobar las sesiones

La CLI y el MCP tienen sesiones independientes. Si la CLI devuelve 401 y la renovación falla con invalid_grant, ejecutar neon auth y completar la autorización en el navegador. Comprobar después con neon projects list. Para el MCP, usar codex mcp login Neon y comprobar su estado con codex mcp list.

Para instalar las piezas en otro checkout, usar npm install --global neon, neon skills -s neon -s neon-postgres -s neon-postgres-branches --agent codex -y y neon mcp --oauth --project --agent codex --project-id cold-firefly-92947172 -y, después de revisar lo que ya está instalado.

La actualización oficial es neon skills update -y. Si falla por rutas ambiguas o por una instalación anterior sin skillPath, respaldar la skill afectada y reinstalarla por nombre con neon skills -s <skill-name> --agent codex -y. Conservar las personalizaciones antes de cualquier actualización.

Validación de migraciones

Usar la CLI autenticada y una rama efímera con fecha de expiración. Consultar neon branches create --help y pasar explícitamente el proyecto y la rama padre. Ejecutar las migraciones y sus comprobaciones solamente contra la conexión de esa rama; eliminarla al finalizar.

Preservar las variables de entorno existentes. No usar neon init, link ni checkout indiscriminadamente: pueden escribir configuración o descargar variables. Si hace falta vincular o cambiar de rama conservando las variables, usar --no-env-pull. No registrar tokens ni cadenas de conexión en logs o documentación.

El acceso administrativo confirmado y la instalación de herramientas no sustituyen la ejecución de las migraciones ni validan su resultado.
