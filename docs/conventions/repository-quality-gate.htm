CONVENTION
Repository Quality Gate
Validación automática en GitHub Actions y comprobaciones locales durante el desarrollo.
Scope: GitHub Actions / Vercel / agentsStatus: Active
01
Commits y pushes locales

El repositorio no ejecuta el gate desde hooks pre-commit ni pre-push. Los commits y pushes se envían sin esperar validaciones locales. El script prepare puede instalar los wrappers de Husky, pero no existe un hook de producto que invoque el gate.

Durante el trabajo, correr las comprobaciones relevantes al cambio: lint, type checks y las suites relacionadas. Los hooks Stop de agentes no deben duplicar el gate completo.

02
GitHub Actions: gate completo

.github/workflows/quality-gate.yml ejecuta pnpm run ci en cada push a main, en las actualizaciones de pull requests y por ejecución manual. Los pushes a otras ramas no lo activan: una rama se valida a través de su pull request, sin correr el gate dos veces. Los tags no activan este workflow. En pushes valida el commit enviado; en pull requests valida el commit de merge preparado por GitHub.

El runner instala Node.js según .nvmrc, pnpm según packageManager de package.json y Bun según .bun-version: typecheck y typecheck:tests corren bun check, el type checker de Bun, que reporta los mismos errores que tsc de TypeScript 7. Primero ejecuta pnpm install --frozen-lockfile, para rechazar diferencias entre el manifiesto y el lockfile. Después corre el contrato de pnpm run ci repartido en jobs. El job Static checks and build ejecuta lint, typecheck y typecheck:tests en un grupo parallel de GitHub Actions y después next build. La suite de Vitest es la mayor parte del tiempo del gate, así que el job Tests la reparte en tres shards (pnpm run test --shard=N/3), cada uno en su propio runner y con Chromium instalado; cada runner conserva el maxWorkers de vitest.config.mts. El composite action .github/actions/setup-quality-gate comparte la preparación de todos los jobs: pnpm, Node.js, la instalación y el entorno aislado. El job final Quality gate espera a los demás y falla si alguno no terminó bien: es el único check que hay que exigir en la protección de la rama. Si cambia el script ci de package.json, el workflow debe actualizarse en el mismo trabajo para seguir ejecutando el mismo contrato.

La caché de pnpm se identifica por pnpm-lock.yaml. Una ejecución nueva cancela la anterior del mismo evento y ref, también en main. Los jobs Static checks and build y Tests tienen un límite de 20 minutos y Quality gate uno de 5, para que un paso colgado (por ejemplo pnpm exec playwright install --with-deps) falle en lugar de ocupar el runner durante horas. HUSKY=0 desactiva la instalación de hooks en CI y NEXT_TELEMETRY_DISABLED=1 desactiva la telemetría de Next.js.

El workflow usa contents: read, no conserva la credencial del checkout y no recibe secretos de la aplicación. Para recopilar las rutas durante el build, genera valores aleatorios efímeros para la configuración de Better Auth y Google, los enmascara en los logs y usa una URL de aplicación local y una URL PostgreSQL de loopback sin credenciales. Estos valores no habilitan login real ni conexiones a Neon. No ejecuta migraciones ni necesita las credenciales del proyecto Neon.

Un fallo de Actions no revierte el push. Para bloquear merges, configurar Quality gate como check obligatorio en la protección de la rama de destino. Agregar el workflow no modifica esa protección.

Los type checks del producto y del build usan tsconfig.typecheck.json. Los tests se chequean separadamente con tsconfig.test.json. Los outputs .next/, .open-next/ y los worktrees de .claude/ quedan fuera de los controles correspondientes.

pnpm run commitlint sigue siendo una comprobación independiente de los últimos 30 mensajes; no forma parte de pnpm run ci.

03
Vercel

Vercel sigue verificando el build real de deployment con el contrato nativo de Next.js y las variables sensibles del entorno. No reemplaza al gate completo: mientras vercel.json use ignoreCommand, un deploy salteado también saltea esa validación.

El workflow de release instala las dependencias desde npm, sin permisos de paquetes ni tokens. Instala la CLI de Vercel y Chromium como pasos background, en paralelo con la instalación de dependencias y el preflight del esquema, y los espera con wait antes del primer paso que los usa: los checks esperan a Chromium y vercel pull espera a la CLI. Si una instalación en segundo plano falla, la publicación se detiene en ese wait. El job tiene un límite de 30 minutos (un release normal tarda menos de 10), así que un paso colgado lo corta en lugar de bloquear el grupo de concurrencia golfo-rp-release, que no cancela releases en curso. Genera credenciales ficticias de autenticación sólo durante los checks aislados. Antes de ejecutarlos consulta los journals del tag y origin/main sin modificar la base: si el esquema tiene migraciones pendientes o no se puede confirmar, la publicación se detiene. TUTRIBU_RELEASE_READ_ONLY=1 también bloquea el adapter de aplicación de migraciones, incluso si el motor vuelve a detectar una migración después del preflight. La construcción de producción usa después la configuración del proyecto Vercel; el permiso de lectura del paquete también está disponible en ese paso, sin escribir el token en el repositorio.

04
Validación esperada

Cuando cambie el workflow o el contrato ci, validar la sintaxis de Actions y ejecutar los comandos reales afectados. La ejecución remota se comprueba con una corrida de GitHub Actions después de publicar los cambios; no reemplazarla por tests que inspeccionen strings internos de archivos de configuración.

Cuando cambie commitlint.config.mjs o el script commitlint, validar mensajes observables del historial reciente y ejecutar pnpm run commitlint.

05

Compilación adicional de Workers

.github/workflows/admission-workers-build.yml ejecuta pnpm run build:cloudflare en Ubuntu al modificar ese workflow y por despacho manual sobre el ref elegido. Reutiliza el setup frozen, las versiones del proyecto y las credenciales sintéticas enmascaradas del gate principal. Cada ejecución tiene un límite de veinte minutos y no cancela otra corrida activa del mismo ref.

El job no recibe credenciales de Cloudflare ni de la aplicación. Conserva recovery bloqueado y mantenimiento deshabilitado, produce el target real con sus comprobaciones de versión y registra SHA, versiones y presencia/tamaño de .open-next/worker.js. Sólo se conserva el recibo saneado durante siete días; no se publica el bundle. Un build aprobado exige que termine el comando y exista el entrypoint producido.

Este check complementa Quality gate y no modifica la protección de ramas. Tampoco despliega, instala secretos, habilita crons ni acredita el control de claves, el restore o el comportamiento operativo de Workers. El historial de validación y el fallo local de preparación se conservan en la evidencia del target.

06

Preflight del lector en Linux

.github/workflows/admission-reader-probe.yml prepara Ubuntu 24.04, navegadores con ventana, Orca, Speech Dispatcher y un monitor de audio. La publicación oficial de Orca se fija por commit y su ejecutable debe informar la versión esperada. La instalación y la prueba comparten una ruta explícita de binarios de Playwright; no dependen de una caché implícita que cambie con el entorno de captura.

El preflight y los recorridos reales fijan la misma publicación oficial: Orca 51.1 sobre AT-SPI 2.58.6, ambos compilados desde su commit verificado. La suite conserva el pin de fuente y la versión informada por el binario. La actualización del lector exige repetir los recorridos; el historial de versiones anteriores conserva sus fallos. Orca 48.9 no sirve para el preflight: escribe su log de depuración con buffer por bloques, y la prueba, que lee ese log, no veía a tiempo un anuncio ya pronunciado.

El preflight corre sólo Chromium (defaultEngines en tests/support/constants/admission-reader-probe.mjs). WebKit en Linux, tanto el de Playwright como WebKitGTK de la distribución, expone el texto de la región viva pero no emite el evento AT-SPI de cambio, así que ningún lector puede anunciarlo. admission-reader-current-probe.yml sigue midiendo WebKit: elige los dos motores con ADMISSION_READER_ENGINES, conserva su observador de eventos nativos y corre sólo por despacho manual, para no dejar un check en rojo esperado en cada PR.

Antes de navegar con Tab, la prueba exige que el documento tenga el foco del sistema operativo (document.hasFocus(), con la emulación de foco de Chromium desactivada). Un navegador recién abierto puede arrancar con el foco en su barra de herramientas, donde Tab recorre sólo esos controles y nunca entra a la página. En ese caso envía F6 nativo, que mueve el foco al panel de contenido, hasta maximumContentPaneSwitches veces, y registra contentPaneSwitches en el reporte.

El wrapper distingue la versión de Orca de los datos de AT-SPI/sesión que la CLI nueva incluye en --version. Rechaza una salida ausente o contradictoria y mantiene la comparación exacta con la versión esperada. La proyección señala un recorrido no iniciado cuando falla la preparación antes de producir un reporte de tests.

El fixture sólo contiene canarios sintéticos de plataforma, sin credenciales ni conexión a Neon. El teclado se envía a la ventana propia comprobada. Cada criterio exige un mensaje del backend real de voz y PCM no silencioso; un evento de DOM, un árbol accesible o una línea de fallback no los sustituyen. Los diagnósticos de AT-SPI son sólo de lectura y no generan anuncios.

Los artefactos identifican expresamente que todavía no certifican recorridos de producto. Un resultado parcial o fallido no cierra accesibilidad; después deben ejecutarse las solicitudes y decisiones reales con sus efectos SQL. La configuración y los fallos conservados están en la evidencia del lector. El workflow se activa por despacho manual y por pushes a ramas que cambian sus fuentes de CI; los pushes de tags de versión no lo disparan, porque GitHub no evalúa paths en ellos. No despliega ni habilita mensajería.

admission-reader-journeys.yml prepara por separado la aplicación real y las ocho superficies de cancelación/aprobación. Sólo ejecuta el ensayo por despacho manual con una capacidad temporal del proyecto Neon, un nonce de rama previsto y el SHA exacto autorizado. Un push o la ausencia de capacidad dejan el paso Native omitido, sin acreditar éxito. La VM comparte los mismos servicios de lector/audio mediante run-admission-reader-session.sh; propaga el display al entorno de activación de D-Bus y limita el cierre a sus procesos de fondo todavía activos. Conserva etapas seguras de diagnóstico, observaciones y capturas sintéticas, elimina el resultado crudo después de su proyección y exige efectos SQL además de voz real. El protocolo y el cleanup pertenecen a la validación de recorridos reales.

Una lectura fallida conserva sólo contadores y banderas sobre el backend, la coincidencia esperada y el PCM; nunca transcripciones. La suite intenta las siguientes combinaciones de navegador/tamaño después de guardar el fallo y cerrar su navegador. Cualquier combinación fallida conserva el resultado agregado como fallido. La coincidencia normalizada del diagnóstico no cambia el criterio de anuncio exacto.

El perfil de Orca del runner usa su propio XDG_DATA_HOME y declara sayAllOnLoad: false y enableKeyEcho: false también por aplicación. La CLI recibe explícitamente el directorio privado de preferencias. La proyección informa si se observó la rama del lector que suprime SayAll y conserva los códigos de cada combinación; la ausencia de esa marca deja esa aplicación sin confirmar. El diagnóstico cuenta sólo ecos independientes de Tab/Espacio. Su eficacia se valida ejecutando la aplicación con el lector real.

Las comprobaciones visibles apuntan al estado de la solicitud y al aviso administrativo, con alcance propio, para evitar la ambigüedad del texto repetido en los toasts. Ante un fallo se conservan únicamente conteos de esos elementos y de regiones ocupadas. Esos datos complementan las observaciones de voz/audio y los efectos SQL.

El foco real exige también que el documento conserve el foco; su último elemento activo puede persistir mientras se opera la interfaz del navegador. La inspección nativa de un fallo conserva únicamente roles, banderas de estado y coincidencias booleanas con el nombre esperado, con plazo acotado y una marca explícita de indisponibilidad. Esa inspección no genera voz ni sustituye los anuncios exigidos.

El preflight y la suite contrastan el foco forzado de Playwright desactivándolo en Chromium con la API real CDP y conservando la configuración de WebKit por separado. El resultado identifica focusEmulationDisabled; ese dato no acredita un recorrido. Los criterios de voz, PCM, teclado, estado propio y efectos SQL permanecen completos.

El diagnóstico de voz añade contadores de entradas del pipeline web de Orca: inserción de texto, tratamiento o descarte de la región, documento inactivo, foco dentro de alertas, entrada a la cola de presentación, monitoreo desactivado y cambio de página. Una entrada de cola precede a la presentación y no acredita voz o audio. Los contadores no retienen texto, identidad de objetos o transcripciones. El preflight declara la fase setup, focus o live y usa su propio offset y mensaje esperado; el fallo de un aviso ya no se diagnostica usando el nombre del control. Los datos de caso y fase se derivan de una misma captura del log.

El canario contrasta además el foco DOM con AT-SPI antes de dar por encontrado el control y antes de activarlo. El control esperado debe estar enfocado, visible, mostrado y habilitado en la proyección nativa; otro elemento editable enfocado o la ausencia del contrato de foco del control cierran la activación. Se admite un ancestro no editable enfocado. La interfaz de Chromium y sus idiomas aceptados se alinean con el contexto español para evitar que un diálogo de traducción intercepte el recorrido. Esta preparación del navegador no genera anuncios ni sustituye los requisitos del lector.

En Linux se genera el locale español y se pasa a los navegadores por LANG/LC_ALL; el flag --lang de Chromium no configura allí su interfaz. El lector puede empezar una introducción después del primer Control: sólo durante esa preparación se interrumpe una nueva salida observada del backend mediante otro Control real. El foco y los avisos mantienen su observación completa sin esa cancelación. El inspector de estado expone atributos de regiones vivas y banderas de soporte/coincidencia de texto, sin texto leído; la proyección indica también si se observó la rama que desactiva Say All.

El preflight compara además la región vacía original con dos formas de conservar un nodo de texto previo, a través del mismo manejador del botón. Cada variante se ejecuta en los dos motores y tamaños y se identifica en reporte y captura. El agregado exige las doce combinaciones y conserva el fracaso del caso original; las variantes son diagnóstico de plataforma y no cambian los componentes del producto. El renderer del fixture tiene pruebas de DOM y ejecución de su propio manejador, independientes de la prueba de voz real.

El driver de recorridos reales exige también la proyección nativa al encontrar un control y antes de escribir o activarlo. Conserva sólo la referencia del objetivo elegido; cada entrada vuelve a comprobar su página y foco actuales. Un fallo de lectura distingue el mensaje esperado del estado nativo del control que inició la acción. Esta barrera no dispensa la voz, el PCM ni los efectos SQL del recorrido.

Esperas de PostgreSQL en la carga Native

ADMISSION_NODE_OBSERVE_BACKENDS=1 activa un controlador independiente que consulta sólo cantidades, estados y tipos de espera en la rama propia. Las muestras se filtran por el marcador de la invocación y cuentan por separado otros clientes de esa rama. No conservan SQL, usuarios, direcciones, PID ni credenciales. El sampler está acotado y espera su consulta actual al cerrarse.

El resultado del host declara qué binding seleccionó y la presencia del marcador de pooler en su hostname, sin publicar la conexión. Adjunta también una ventana de pared del tramo medido; las muestras usan el reloj PostgreSQL y el p95 sigue usando el reloj monotónico de cada solicitud. El scope completo incluye preparación y warm-up. La observación agrega carga y no sustituye la aceptación del benchmark sin ella.

ADMISSION_NODE_OBSERVE_LOCKS=1 habilita además cantidades de locks de relación por fast path o tabla principal, máximo de relaciones distintas por backend, tipos, modos y solicitudes sin conceder. Filtra el mismo workload y excluye el controlador y los clientes ajenos; no devuelve PID, OID, nombres de relaciones ni claves advisory. Consulta cada 500 ms más el tiempo de SQL y drena la operación al detenerse. Leer pg_locks toma locks internos y puede afectar la medición; los conteos son un diagnóstico puntual, no una aceptación de latencia ni una prueba de causalidad. El modo anterior conserva su consulta sin inventario.

El protocolo y su prueba con locks reales se mantienen en la validación de backends. Se conserva el criterio p95, el dataset completo, stock, replay y pool balanceado.
