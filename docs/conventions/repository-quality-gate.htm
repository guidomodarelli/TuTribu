CONVENTION
Repository Quality Gate
Dónde vive la validación completa del repositorio y qué rol cumplen los agentes.
Scope: GitHub Actions / Vercel / agentsStatus: Active
01
Regla de ejecución

El gate completo del repositorio vive en .github/workflows/quality-gate.yml y corre en cada push y pull_request. El workflow instala dependencias con pnpm install --frozen-lockfile y ejecuta el contrato compartido pnpm run ci.

El script ci encadena pnpm run lint, pnpm run typecheck, pnpm run test y pnpm run build. Ese orden mantiene los checks estáticos, la suite Jest y el análisis de producción de Next.js en un único punto de entrada reutilizable.

El workflow configura el registry público de npm para el scope @siteping y pasa NODE_AUTH_TOKEN desde el secret NPM_TOKEN durante pnpm install. Si una dependencia de ese scope vuelve a ser privada, el secret debe estar configurado en GitHub antes de esperar que el gate llegue a lint, typecheck, tests o build.

El workflow puede declarar placeholders no sensibles para variables server-only que Next.js necesita al evaluar rutas durante next build. Esos valores permiten validar bundling y App Router sin exponer credenciales reales ni reemplazar las variables de deployment.

El script commitlint valida los ultimos 30 mensajes contra commitlint.config.mjs. La configuracion acepta el estilo real del repositorio: commits convencionales con prefijo, releases semver como 0.52.3 y titulos imperativos heredados sin prefijo.

Los hooks Stop de agentes no deben duplicar este gate pesado. Durante el trabajo local, Codex y Claude deben ejecutar validaciones enfocadas al cambio realizado y dejar el gate completo para GitHub Actions.

Los outputs generados por builds, como .next/ y .open-next/, no forman parte del codigo fuente validable. Deben quedar fuera de ESLint para que los artefactos de adaptadores externos no rompan el gate del repositorio.

Los worktrees generados por agentes bajo .claude/ tampoco forman parte del checkout validable de Jest ni ESLint. Jest debe ignorarlos tanto para descubrir tests como para construir el mapa de modulos, y ESLint debe excluirlos de sus ignores globales, evitando que copias temporales de package.json o de suites antiguas interfieran con la rama actual.

La validación completa queda asociada al push y al pull request, no al cierre de cada turno del agente.
02
Cambios relevantes

Los cambios que afectan comportamiento de producto, runtime, estilos, base de datos o configuración de validación deben llegar a GitHub Actions con el gate determinístico pasando. En local se debe elegir la validación mínima suficiente para iterar sin duplicar el costo del workflow completo.

  • Code: .ts, .tsx, .js, .jsx, .mjs, .cjs, .mts, .cts.
  • Styles and data changes with runtime impact: .scss, .css, .sql.
  • Validation and package config: package.json, lockfiles, tsconfig, commitlint, eslint, jest, next, playwright, postcss, and components.json.
  • CI config: .github/workflows/quality-gate.yml.
No mover el gate completo exclusivamente a Vercel mientras vercel.json use ignoreCommand, porque un deploy salteado también saltearía esa validación.
03
Vercel

Vercel sigue siendo responsable de verificar el build real de deployment con el contrato nativo de Next.js y las variables sensibles configuradas en el entorno de despliegue. El flujo de deploy no reemplaza al gate de GitHub Actions: lo complementa con la validación del entorno de despliegue.

Si en el futuro se decide ejecutar pnpm run ci dentro de Vercel, primero se debe revisar scripts/ignore-build.sh para evitar que una omisión intencional del deploy deje el gate sin correr.

04
Validación esperada

Cuando se modifica el workflow o el script ci, validar como mínimo el parseo de package.json, el formato del YAML y que el workflow invoque el contrato compartido. No agregar tests que inspeccionen strings internos de los archivos fuente como sustituto del comportamiento real.

Cuando se modifica commitlint.config.mjs o el script commitlint, validar con tests de tooling sobre mensajes observables del historial reciente y ejecutar pnpm run commitlint para comprobar el rango configurado.

Para cambios de producto, mantener los tests relevantes en local durante la iteración y dejar que GitHub Actions ejecute el gate completo antes de mergear o desplegar.
