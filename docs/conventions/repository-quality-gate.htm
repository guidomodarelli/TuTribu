Repository Quality Gate
Qué se valida en cada push, y qué rol cumplen los agentes.
Scope: Husky / Vercel / agentsStatus: Active
01
Hooks de Git

El repositorio no usa un workflow de GitHub Actions como gate ni un hook pre-commit: los commits no corren chequeos. La validación automática vive solo en el hook pre-push de Husky, que corre el gate completo al pushear una rama distinta de main.

El hook se instala solo: el script prepare (husky) corre en cada pnpm install. En entornos sin .git, como los builds de Vercel o Cloudflare, Husky no instala nada y el install sigue normalmente. Para saltear el hook en una situación puntual se puede exportar HUSKY=0; no se usa --no-verify como práctica habitual.

Mientras se trabaja conviene correr las validaciones enfocadas al cambio (pnpm run lint, los type checks o vitest related --run) antes de pushear, para no esperar al gate completo para enterarse de un error.

02
Hook pre-push: gate completo

El contrato completo sigue siendo pnpm run ci: encadena lint, typecheck, typecheck:tests, la suite completa de Vitest (incluidas las suites de guardrails de SQL y migraciones) y next build. Lo ejecuta el hook pre-push de Husky (.husky/pre-push) antes de cada push de una rama distinta de main; si falla, el push no se envía. Reemplaza al gate que antes corría en GitHub Actions, así que para mergear no se esperan checks de Actions.

Los pushes a main (por ejemplo, el de pnpm release) y a tags no corren el gate: main recibe código por pull requests cuyas ramas ya pasaron el gate al pushearse. Es un trade-off deliberado: el commit resultante del merge en GitHub no se valida localmente; Vercel sigue validando el build de deployment.

El hook valida solo el HEAD actual con el working tree limpio: nunca hace checkout ni ejecuta código de un commit distinto del checkout. .husky/pre-push delega en scripts/pre-push-gate.mjs, que lee de stdin las líneas <local ref> <local oid> <remote ref> <remote oid> que git le entrega:

  • Solo valida las refs remotas refs/heads/* distintas de refs/heads/main. Si el push no incluye ninguna, termina sin validar nada, sin verificar el runtime ni el working tree.
  • Cuando hay alguna rama para validar, primero verifica el runtime: .nvmrc y engines.node no cambian el node que ya está ejecutando el hook. Si la versión en curso no cumple engines.node (Node 24), el push se rechaza con un mensaje que indica la versión de .nvmrc a usar. Si cumple el major pero difiere de la versión exacta de .nvmrc, muestra una advertencia y continúa. Es un trade-off deliberado: bloquear cualquier diferencia de minor o patch dentro de Node 24 cortaría todos los pushes de quien todavía no actualizó, mientras que un major distinto sí puede cambiar el resultado del gate. El evaluador acepta comparadores separados por espacios (>=24 <25) y falla explícitamente ante otra sintaxis de rango. Una versión prerelease (por ejemplo 24.21.0-rc.1) nunca cumple engines.node ni se considera igual a .nvmrc, igual que en los rangos semver estándar, que excluyen prereleases salvo que un comparador las admita: el push se rechaza. La metadata de build (+build) se ignora.
  • Los borrados de ramas (oid local en ceros) se permiten y no se validan.
  • Cada commit validado tiene que ser HEAD y git status --porcelain tiene que estar vacío (sin cambios staged, sin cambios sin stagear ni archivos untracked; los ignorados como .env* no cuentan) y ningún archivo trackeado puede estar marcado con skip-worktree o assume-unchanged (git ls-files -v: tag S o en minúscula). git status no compara esos archivos con HEAD, así que un fix local sobre uno de ellos haría pasar el install y pnpm run ci mientras git sube la versión commiteada; el push se rechaza con un mensaje en español que lista los archivos y pide quitar las marcas con git update-index --no-skip-worktree --no-assume-unchanged <archivo>. En ese caso corre una sola vez en el checkout, aunque varias refs apunten al mismo commit, pnpm install --frozen-lockfile --prefer-offline (con HUSKY=0, para que el prepare no toque la configuración de hooks) y, si pasa, pnpm run ci. El install congelado falla cuando package.json y pnpm-lock.yaml no coinciden; pnpm run ci solo no lo detecta si node_modules ya está instalado.
  • Después del install y otra vez después de pnpm run ci vuelve a comprobar que HEAD siga siendo el commit pusheado y que el working tree siga limpio, incluida la ausencia de archivos marcados con skip-worktree o assume-unchanged. Git sube el oid que capturó en stdin, así que un commit, una edición o un checkout hecho en otra terminal durante los ~10 minutos del gate haría que pnpm run ci validara código distinto del que se publica. Si algo cambió, el push falla con un mensaje en español que pide volver a pushear sin modificar el checkout mientras corre el pre-push.
  • Si se pushea a una rama validada cualquier otro oid (git push origin otra-rama, una ref traída de otro lado, o HEAD con cambios sin commitear o archivos untracked), el push falla con un mensaje en español que indica el oid y la ref, el motivo, y que hay que hacer checkout de esa rama o commit con el working tree limpio y volver a pushear. Así el gate no ejecuta bajo la cuenta del desarrollador código de un commit que no eligió checkoutear, y los pins de runtime (.nvmrc, engines.node) que lee del checkout son siempre los del commit pusheado.
  • La corrida en el checkout mantiene el entorno del desarrollador y sus .env*: es el código que ya tiene checkouteado y ejecuta localmente, y next build lee esos archivos del directorio de todas formas. Si se hace checkout de una rama no confiable, sus scripts ya pueden leer esos archivos con cualquier pnpm que se corra ahí; el gate no agrega exposición en ese camino.
Para pushear otra rama, primero hacer checkout de esa rama, dejar el working tree limpio (commitear, stashear o descartar los cambios, incluidos los archivos untracked) y recién ahí pushear. Un fix sin commitear nunca hace pasar el gate: el push falla hasta que el working tree quede limpio.

El hook corre mientras git ya abrió la conexión con el remoto. Por SSH, GitHub corta la conexión inactiva durante los ~10 minutos de pnpm run ci y el push falla aunque el gate haya pasado (código 141). Pushear por HTTPS (por ejemplo con gh auth git-credential como credential helper) o configurar ServerAliveInterval para github.com en ~/.ssh/config.

El script commitlint valida los últimos 30 mensajes contra commitlint.config.mjs. La configuración acepta el estilo real del repositorio: commits convencionales con prefijo, releases semver como 0.52.3 y títulos imperativos heredados sin prefijo.

Los hooks Stop de agentes no deben duplicar el gate completo. Durante el trabajo, Codex y Claude ejecutan validaciones enfocadas al cambio; el pre-push corre el gate completo al pushear la rama.

Los outputs generados por builds, como .next/ y .open-next/, no forman parte del código fuente validable y quedan fuera de ESLint. Los worktrees generados por agentes bajo .claude/ tampoco: Vitest y ESLint los ignoran para que copias temporales no interfieran con la rama actual.

03
Vercel

Vercel sigue verificando el build real de deployment con el contrato nativo de Next.js y las variables sensibles del entorno. No reemplaza al gate completo: mientras vercel.json use ignoreCommand, un deploy salteado también saltea esa validación.

04
Validación esperada

Cuando se modifica el hook pre-push, scripts/pre-push-gate.mjs o el script ci, validar con un push real de una rama que el hook se ejecute y bloquee ante un error de lint, de tipos o de tests. No agregar tests que inspeccionen strings internos de los archivos de configuración como sustituto del comportamiento real.

Cuando se modifica commitlint.config.mjs o el script commitlint, validar con tests de tooling sobre mensajes observables del historial reciente y ejecutar pnpm run commitlint.
