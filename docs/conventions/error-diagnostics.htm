CONVENTION
Error Diagnostics
Cómo hacer que un 500, un rechazo de negocio, una variable de entorno faltante o un warning de React digan su causa en el primer log, sin exponer datos privados.
Scope: Server, tests y desarrollo localStatus: Active
01
Overview

Las boundaries HTTP propias nunca serializan mensajes, stacks ni valores de un error. Eso protege los datos, pero deja el log en un unexpected_failure anónimo cuando la falla no conserva su causa tipada. Esta convención fija cuatro defensas que se complementan:

  • Cadena de causas en el log. La boundary registra las clases y los códigos cerrados de toda la cadena cause.
  • Rechazos con motivo. Un 4xx de negocio lleva el requisito incumplido como causa tipada.
  • Entorno verificado al arrancar. Una variable faltante se informa al iniciar el servidor, no en medio de un flujo.
  • Warnings de React como fallas. Un warning de desarrollo hace fallar el test que lo produce.
02
Cause chain

createOwnJsonRouteBoundary agrega causes al diagnóstico de cada falla que conserva cause. summarizeErrorCauses recorre cause y AggregateError.errors, visita cada error una sola vez y guarda como máximo ERROR_CAUSE_SUMMARY_MAX_ENTRIES eslabones, cada uno con solo dos campos:

CampoRegla
nameNombre de la clase si es un identificador; si no, UnnamedError. Un valor que no es Error se registra solo por su tipo.
codeSolo si es un string cerrado (ERROR_CAUSE_CODE_PATTERN): códigos propios, SQLSTATE o códigos de Node. Un texto libre se descarta.
{"code":"unexpected_failure","status":500,"causes":[
  {"name":"AdmissionOperationError","code":"unexpected_failure"},
  {"name":"MessagingCryptographyError","code":"messaging_crypto_configuration_invalid"}]}

Para que funcione, cada falla llega a la boundary con su error real como cause, y cada clase de error propia expone un code cerrado. Una lectura de configuración, una llamada a un proveedor o un SQL que puede fallar dentro de una operación se envuelve en el error tipado de la feature, con cause, en el lugar donde falla. Por ejemplo, readFingerprint envuelve la lectura de las claves de mensajería.

Al reproducir un 500 reportado, leé primero causes. Si una falla sigue saliendo sin causas, agregar la cause faltante es parte del arreglo.
03
Business rejections

Un rechazo esperado que tiene un motivo de dominio lleva ese motivo como causa tipada. En admisiones, PostgresAdmissionPolicyRepository lanza admission_ineligible con un AdmissionPolicyRequirementError cuyo code es el requisito incumplido (verification_unavailable, admission_evaluator_unavailable, etc.), y el log de la boundary lo muestra en causes. El navegador no recibe esa causa: sigue leyendo sus propios requisitos seguros (preflight y requisitos de activación) para explicar qué falta.

04
Environment at startup

instrumentation-node.ts corre checkServerEnvironment con SERVER_ENVIRONMENT_REQUIREMENTS (src/modules/server-environment-requirements.ts) cada vez que arranca un servidor, salvo durante next build.

SeveridadDesarrollo localProducción
blockingRegistra el problema y el servidor no arranca.Registra el problema; la feature sigue fallando cerrada.
degradedRegistra una advertencia.Registra una advertencia.

El log nombra la feature, las variables faltantes y, si un valor existe pero no sirve, la cadena de causas de su validación (por ejemplo, MESSAGING_KEYRINGS_JSON con JSON inválido). Nunca incluye valores. Toda variable nueva que lea una feature se agrega en el mismo cambio a .env.example y a SERVER_ENVIRONMENT_REQUIREMENTS.

Además, pnpm run dev avisa si la base configurada tiene migraciones sin aplicar, con el mismo chequeo que el release (scripts/release/pending-migrations.mjs). pnpm db:sandbox genera claves de mensajería de desarrollo cuando faltan y registra sus pruebas en el sandbox (ver Local Database Sandbox).

05
React warnings in tests

vitest.setup.ts instala installReactWarningGuard (tests/support/react-warning-guard.ts). El guard envuelve console.error y console.warn, sigue reenviando cada llamada y hace fallar el test que registró un warning de desarrollo de React:

  • cambios entre controlado y no controlado;
  • keys faltantes o duplicadas en listas;
  • actualizaciones fuera de act o durante el render de otro componente;
  • props desconocidas o atributos no booleanos en el DOM.

La corrección va en el componente. Un input controlado sigue controlado toda su vida: el estado sin selección se representa con el valor vacío del componente ("", false o el null que acepte), nunca con undefined. ACCEPTED_REACT_WARNING_PATTERNS solo admite warnings de dependencias que no se pueden corregir acá, con la suite afectada y el motivo.
