CONVENTION
Proceso de release
Un solo comando, pnpm create-version, diagnostica el repositorio, muestra qué falta y publica la versión desde main. El comando es beez-rp create-version, compartido con los demás proyectos Beez; lo propio de TuTribu vive en beez-rp.config.js.
Scope: beez-rp.config.js / scripts/release/pending-migrations.mjs / VercelStatus: Active
01
Uso
ComandoQué hace
pnpm create-version o pnpm cvDiagnóstico, plan y ejecución interactiva (cv es un alias). La versión se elige con las flechas; se sugiere patch, minor o major según los commits.
pnpm create-version --bump patch|minor|majorElige el tipo de versión sin preguntar.
pnpm create-version --set-version X.Y.ZFija la versión exacta. Solo se acepta el siguiente patch, minor o major de la versión actual: nunca una menor, igual ni una que saltee versiones (por ejemplo, de 0.93.0 solo valen 0.93.1, 0.94.0 o 1.0.0).
pnpm create-version --dry-runDiagnostica y muestra el plan sin cambiar nada.
Sin terminal interactiva (por ejemplo con stdin redirigido) cada pregunta toma su opción por defecto y lo informa en pantalla. No hay confirmación del plan: correr el comando es el pedido de publicar, y para ver el plan sin ejecutarlo está --dry-run. Las únicas preguntas son la versión (si no se pasa --bump ni --set-version) y las migraciones pendientes. Las opciones están numeradas: se eligen apretando su número, o con las flechas y Enter; cada versión muestra debajo qué significa patch, minor o major. El tiempo total que se muestra al final no cuenta la espera de las respuestas.
02
Diagnóstico

Antes de tocar nada, el comando hace git fetch origin --prune --tags y arma un panel con:

  • Rama: los releases salen solo desde main.
  • Working tree: tiene que estar limpio.
  • main ↔ origin: commits atrás o adelante de origin/main.
  • Último release: el último commit de origin/main que cambió el version de package.json (hoy, los commits X.Y.Z). Los tags vX.Y.Z históricos solo existen en clones locales, por eso no se usan como referencia.
  • Sin publicar: commits de origin/main posteriores al último release.
  • Migraciones (adaptador migrations.check de beez-rp.config.js): entradas de database/migrations/meta/_journal.json (de HEAD y origin/main) más nuevas que el último created_at de drizzle.__drizzle_migrations, la misma regla que usa drizzle-kit migrate. La conexión se resuelve igual que drizzle.config.ts (DATABASE_MIGRATION_URL y luego DATABASE_URL) y solo se muestra el host. Si la base no responde, el release sigue con una advertencia.
  • CHANGELOG: cantidad de entradas en ## [Unreleased] de CHANGELOG.md, o si está vacío o usa secciones no válidas.
  • Node.js: advierte si difiere de .nvmrc.
03
Bloqueos

Estas situaciones no se automatizan; el comando se detiene y explica el próximo paso concreto:

  • Rama feature: indica si faltan commits por subir, si hay que abrir el PR, si el PR está abierto o en borrador (con su link) o si ya se mergeó y solo falta volver a main.
  • Cambios sin commitear: lista los archivos y pide commitearlos en una rama o stashearlos. La única excepción es CHANGELOG.md, que viaja en el commit de versión.
  • Secciones no válidas en [Unreleased]: solo se aceptan las de Keep a Changelog.
  • Commits locales en main que no son un release: pide moverlos a una rama y llevarlos por un PR.
  • HEAD desacoplado.
04
Pasos que ejecuta
PasoCuándoDetalle
Actualizar mainmain está atrás de origingit merge --ff-only origin/main.
Aplicar migracionesHay migraciones pendientesMuestra la lista y el host destino, y pregunta: aplicar ahora (migrations.apply corre node scripts/push-migrations.js, lo mismo que pnpm run db:migrate), saltear o cancelar. Después de migrar vuelve a llamar a migrations.check para verificar que no quede ninguna pendiente. Corre antes de subir la versión para que el deploy encuentre el esquema listo.
Completar el CHANGELOGHay commits sin publicar y [Unreleased] está vacíoInvoca a Codex (codex exec --sandbox workspace-write --ephemeral -, con el prompt por stdin) para que complete [Unreleased] desde los commits sin publicar y muestra el resultado. Si Codex no está instalado, falla o deja el bloque vacío o con secciones no válidas, el release se corta y pide completarlo.
VersionarHay commits sin publicarMuestra qué se publica, elige la versión (flag o pregunta), actualiza package.json, renombra ## [Unreleased] a ## [X.Y.Z] - AAAA-MM-DD dejando un [Unreleased] vacío arriba, crea el commit X.Y.Z con los dos archivos y el tag anotado vX.Y.Z.
PublicarSiempre que se versionó, o hay un release a medio subirEjecuta, sin preguntar, git push --atomic origin main refs/tags/vX.Y.Z. El hook pre-push no corre el gate en main ni en tags: ya corrió al pushear la rama que llegó a main por pull request. Al terminar verifica que el tag exista en origin.

Vercel buildea solo cuando la versión de package.json es una versión estable válida respecto del commit anterior (vercel.json → scripts/ignore-build.sh), así que el push del commit de versión dispara el deploy de producción. Como el ignoreCommand corre antes de instalar dependencias, el wrapper ejecuta npx --yes beez-rp@<rango> ignore-build con el rango de la devDependency beez-rp declarada en package.json. beez-rp no tiene dependencias, así que la descarga tarda segundos. La regla es la misma que aplica pnpm create-version, porque las dos usan beez-rp/versions:

  • Solo se buildea la siguiente patch, minor o major: de 1.2.3 valen 1.2.4, 1.3.0 o 2.0.0.
  • Se saltea el build si la versión no cambió, bajó, saltea versiones (1.0.0 → 3.0.0, 1.2.3 → 1.4.0) o no reinicia las partes menores (1.2.3 → 1.3.3).
  • Nunca se buildean prereleases ni metadata de build (1.3.0-alpha.1, 2.0.0-beta.2, 2.0.0-rc.1, 1.2.4+build.5) ni nada que no sea X.Y.Z plano.
  • Si no se puede leer la versión del commit anterior, se buildea solo si la actual es estable. Si el gate no puede verificar la versión (sin Node.js, sin beez-rp declarado, falla de npx o de red, o un error del gate), se saltea el build.
Cada paso se deriva del estado actual. Si algo falla, se corrige la causa y se vuelve a correr pnpm create-version: retoma desde el primer paso que falte. Un commit de versión creado en local pero no subido se detecta como release a medio subir y solo se reintenta el push.
05
CHANGELOG

CHANGELOG.md sigue Keep a Changelog. Cada cambio que afecta a quien usa TuTribu agrega sus entradas en ## [Unreleased], agrupadas en ### Added, ### Changed, ### Deprecated, ### Removed, ### Fixed y ### Security (solo las que apliquen), en español. Nunca se escriben la versión ni la fecha a mano: las agrega pnpm create-version. La regla completa está en AGENTS.md (Changelog governance). Las versiones hasta la 0.93.0 no tienen entradas.

Estructura
ArchivoResponsabilidad
beez-rp create-versionMotor compartido (devDependency beez-rp): flags, diagnóstico, PR de la rama con gh, plan o bloqueos, preguntas y ejecución de cada paso. pnpm create-version y pnpm cv lo invocan desde la raíz.
beez-rp.config.jsConfiguración de TuTribu: nombre del banner, audiencia del CHANGELOG para Codex, qué significa patch, minor y major para los usuarios, etiqueta en producción, adaptador de migraciones (check, apply y targetHint) y la línea del deploy de Vercel en el resumen final. No importa beez-rp en runtime: los hooks reciben Git, run y fail por contexto.
scripts/release/pending-migrations.mjsAdaptador Postgres/Drizzle: lee y mergea el journal de HEAD y origin/main y detecta las migraciones pendientes en la base configurada, con el contrato { status, pending, target, reason } de beez-rp.
scripts/ignore-build.shignoreCommand de Vercel: corre npx beez-rp@<rango> ignore-build y sale con 1 (buildear) solo cuando la última línea es BUILD; en cualquier otro caso sale con 0 (saltear).
devDependency beez-rpPaquete compartido con agenda-mensual y beez-ui: comando de release (beez-rp create-version), reglas de versión (beez-rp/versions), gate de Vercel (beez-rp ignore-build), CHANGELOG (beez-rp/changelog), Codex (beez-rp/changelog-ai), UI de terminal (beez-rp/terminal-ui) y fixtures de versiones (beez-rp/testing). Se excluye de minimumReleaseAge en pnpm-workspace.yaml porque es un paquete propio.

Los tests viven en tests/unit/tooling/pending-migrations-script.test.ts (journal, host sin credenciales y el adaptador real de beez-rp.config.js sobre repositorios Git reales con un remoto bare) y tests/unit/tooling/build-gate-script.test.ts (corre el ignore-build.sh real con un npx falso que ejecuta el beez-rp instalado o simula fallos; en Windows usa el Git Bash porque el bash de WSL deja los archivos bloqueados). El motor de create-version (flags, estado, plan y ejecución), las reglas y la UI compartidas se testean en el repositorio de beez-rp.
