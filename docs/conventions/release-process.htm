CONVENTION
Proceso de release
Un solo comando, pnpm create-version, diagnostica el repositorio, muestra qué falta y publica la versión desde main.
Scope: scripts/release.mjs / scripts/release/ / VercelStatus: Active
01
Uso
ComandoQué hace
pnpm create-version o pnpm cvDiagnóstico, plan y ejecución interactiva (cv es un alias). La versión se elige con las flechas; se sugiere patch, minor o major según los commits.
pnpm create-version --bump patch|minor|majorElige el tipo de versión sin preguntar.
pnpm create-version --set-version X.Y.ZFija la versión exacta. Solo se acepta el siguiente patch, minor o major de la versión actual: nunca una menor, igual ni una que saltee versiones (por ejemplo, de 0.93.0 solo valen 0.93.1, 0.94.0 o 1.0.0).
pnpm create-version --dry-runDiagnostica y muestra el plan sin cambiar nada.
Sin terminal interactiva (por ejemplo con stdin redirigido) cada pregunta toma su opción por defecto y lo informa en pantalla.
02
Diagnóstico

Antes de tocar nada, el comando hace git fetch origin --prune --tags y arma un panel con:

  • Rama: los releases salen solo desde main.
  • Working tree: tiene que estar limpio.
  • main ↔ origin: commits atrás o adelante de origin/main.
  • Último release: el último commit de versión (X.Y.Z) que llegó a origin/main. Los tags vX.Y.Z históricos solo existen en clones locales, por eso no se usan como referencia.
  • Sin publicar: commits de origin/main posteriores al último release.
  • Migraciones: entradas de database/migrations/meta/_journal.json (de HEAD y origin/main) más nuevas que el último created_at de drizzle.__drizzle_migrations, la misma regla que usa drizzle-kit migrate. La conexión se resuelve igual que drizzle.config.ts (DATABASE_MIGRATION_URL y luego DATABASE_URL) y solo se muestra el host. Si la base no responde, el release sigue con una advertencia.
  • Node.js: advierte si difiere de .nvmrc.
03
Bloqueos

Estas situaciones no se automatizan; el comando se detiene y explica el próximo paso concreto:

  • Rama feature: indica si faltan commits por subir, si hay que abrir el PR, si el PR está abierto o en borrador (con su link) o si ya se mergeó y solo falta volver a main.
  • Cambios sin commitear: lista los archivos y pide commitearlos en una rama o stashearlos.
  • Commits locales en main que no son un release: pide moverlos a una rama y llevarlos por un PR.
  • HEAD desacoplado.
04
Pasos que ejecuta
PasoCuándoDetalle
Actualizar mainmain está atrás de origingit merge --ff-only origin/main.
Aplicar migracionesHay migraciones pendientesMuestra la lista y el host destino, y pregunta: aplicar ahora (scripts/push-migrations.js, lo mismo que pnpm run db:migrate), saltear o cancelar. Después de migrar vuelve a verificar que no quede ninguna pendiente. Corre antes de subir la versión para que el deploy encuentre el esquema listo.
VersionarHay commits sin publicarMuestra qué se publica, elige la versión (flag o pregunta), actualiza package.json, crea el commit X.Y.Z y el tag anotado vX.Y.Z.
PublicarSiempre que se versionó, o hay un release a medio subirPide confirmación y ejecuta git push --atomic origin main refs/tags/vX.Y.Z. El hook pre-push no corre el gate en main ni en tags: ya corrió al pushear la rama que llegó a main por pull request. Al terminar verifica que el tag exista en origin.

Vercel buildea solo cuando cambia la versión de package.json (scripts/ignore-build.sh), así que el push del commit de versión dispara el deploy de producción.

Cada paso se deriva del estado actual. Si algo falla, se corrige la causa y se vuelve a correr pnpm create-version: retoma desde el primer paso que falte. Un commit de versión creado en local pero no subido se detecta como release a medio subir y solo se reintenta el push.
