CONVENTION
Payload Validation Boundaries
Qué se valida con schema en el middleend (input y DTO público), dónde viven los schemas y qué nunca se valida (filas de Postgres y respuestas de proveedores).
Scope: Route handlers / Pages / Browser adaptersStatus: ActiveValidador: zod ^4.3.6
01
Overview

Hay tres tipos de payload y cada uno tiene su regla. No se mezclan:

PayloadReglaMecanismo
Input middleend: params, query y body de un route.ts; params y searchParams de una page.tsxSiempre se valida, una sola vez, en el boundary de entradaSchemas Zod en src/modules/<feature>/infrastructure/api/schemas/
DTO público middleend: body JSON que la ruta entrega al navegador y props que una página server pasa a componentes clienteSiempre se valida antes de entregarlo (server) y antes de usarlo (cliente)Schemas Zod en src/modules/<feature>/application/results/*-public-dto-schemas.ts
Upstream: filas de Postgres, respuestas de proveedores (Mercado Pago, Wistia, Cloudflare…)Nunca se valida con schema ni allowlist completaNarrowing estructural mínimo en el adapter (status, null/array/objeto, discriminadores que cambian el flujo)

La fuente canónica de la regla es ~/.agents/rules/payload-validation-boundaries.md. La primera implementación es el módulo de eventos (docs/architecture/tribe-events.htm, sección 08); el módulo de notificaciones aplica la misma regla (docs/architecture/notifications.htm, sección 06).

02
Dónde vive cada schema y por qué
  • Input en infrastructure/api/schemas/: describe el contrato HTTP de entrada (texto del formulario, query strings, segmentos de ruta). Es transporte, así que pertenece a infraestructura. Su salida tipada coincide con los commands de application/commands (satisfies z.ZodType<Command>), de modo que el caso de uso recibe valores ya validados.
  • DTO público en application/results/: es el contrato de la UI, el mismo lugar que los tipos *Result. Zod es una librería pura (sin I/O, framework ni proveedor), así que la ruta (app), la página y el adapter del navegador (lib) lo importan sin romper la regla de dependencias. Cada schema se ata a su tipo con satisfies z.ZodType<Result>.
  • Helpers genéricos compartidos: src/modules/shared/infrastructure/validation/validation-issue-summary.ts reduce issues a { path, code } para logs.
application y domain siguen sin importar lib ni infrastructure. El adapter del navegador solo importa tipos (import type) desde los schemas de input, para compartir la forma del body sin empaquetar código de servidor. Los componentes presentacionales no importan esos tipos ni los de los adapters: emiten su propio contrato de UI (en eventos, lib/events/tribe-event-form-submissions.ts) y el adapter o el hook lo traduce al body del request.
03
Reglas
  • Una validación por ruta. El handler llama un único parser de boundary (en eventos, parseTribeEventRouteInput) con los schemas de params, query y body. Después solo usa la salida tipada.
  • Formato en el schema, negocio en el caso de uso. Tipos, presencia, rangos, enums, uuid, instantes ISO y formas canónicas van en el schema. Reglas que relacionan campos o necesitan datos persistidos (fin posterior al inicio, instante que pertenece a la serie, permisos) quedan en el caso de uso o el dominio. Los value objects de dominio siguen siendo invariantes; no se repite en el caso de uso lo que el schema ya garantizó.
  • Categorías, no mensajes de Zod. Cada regla declara una categoría estable ({ error: CATEGORY }) y el boundary la traduce a copy en español. El body de un 400 es siempre { message }, sin issues, códigos ni el valor recibido.
  • Log seguro. Input rechazado → warn con part (params/query/body) e issues: [{ path, code }]. DTO rechazado → error con reason: "public_dto_rejected", issues e identificadores seguros. Nunca el valor rechazado.
  • DTO en el server. Toda respuesta de éxito pasa por el schema y se envía la salida parseada (z.object descarta campos fuera del contrato). Un DTO inutilizable es un 500 con el mensaje seguro de la ruta. Los cuerpos de error son constantes tipadas { message }.
  • DTO en el cliente. El adapter del navegador no usa as T: valida el body; si no cumple, devuelve { isSuccess: false, message: null } y el hook muestra su toast de fallback. Solo se muestra message de una respuesta de error que cumple { message: string }.
  • Páginas. Un searchParam inválido se descarta (.catch(undefined)) y la página muestra su valor por defecto. Un segmento de ruta inválido es notFound(). Las props que cruzan server → client se validan como DTO; si no cumplen, la página muestra su estado de error seguro.
  • Tests con el validador real. No se mockea Zod. Cada ruta necesita tests de params, query y body inválidos (400 sin llamar al caso de uso), DTO válido consumido y DTO inutilizable rechazado (server y cliente), y ausencia de diagnóstico o valores crudos en respuestas y logs.
No agregar schemas a filas de repositorio ni a respuestas de proveedores, aunque "parezca más seguro". Si una respuesta upstream no se puede consumir, el adapter la convierte en un fallo controlado.
04
Cómo aplicarlo en una ruta nueva
  1. Escribí primero los tests de boundary (input inválido → 400, DTO inutilizable → 500) y el test del schema.
  2. Declará los schemas de input en infrastructure/api/schemas/, reutilizando los campos compartidos (slug, uuid, instante, mes) y una categoría por regla.
  3. Declará el DTO público en application/results/*-public-dto-schemas.ts con satisfies z.ZodType<Result>.
  4. En el handler: sesión → parser de boundary → caso de uso → respuesta validada.
  5. En el adapter del navegador: safeParse del body con el mismo schema.
  6. Quitá del caso de uso cualquier chequeo de formato que el schema ya cubre.
const input = await parseTribeEventRouteInput({
  logger,
  params: context.params,
  request,
  schemas: { body: bodySchema, params: paramsSchema, query: querySchema },
});

if (!input.isValid) {
  return input.response; // 400 { message } + warn log con { path, code }
}

const result = await modules.feature.useCases.doSomething({ ...input.body, ...input.params });

return createTribeEventPublicResponse({
  body: result,
  failureMessage: COPY.unexpected,
  logger,
  metadata: { slug, viewerId },
  schema: publicDtoSchema,
  status: HTTP_STATUS.ok,
});
