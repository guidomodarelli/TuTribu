CONVENTION
Dev Sign-In
Login de desarrollo con email y contraseña de Better Auth para entrar a https://dev.tutribu.app sin Google OAuth. Solo existe en next dev y detrás de una flag explícita.
Scope: Auth / Local toolingStatus: Active
01
Overview

Google OAuth es una redirección del navegador hacia Google y de vuelta al callback de Better Auth: no se puede simular con MSW como los proveedores server-side (los mocks de MOCK_EXTERNAL_APIS). Para trabajar en local sin cuenta de Google, sin red hacia Google o con la base de una branch sandbox de Neon, el servidor de desarrollo puede registrar el método email y contraseña de Better Auth para un único usuario de prueba.

La sesión que crea es una sesión real de Better Auth: usa la misma tabla session, cookie y renovación. La aplicación la consulta con el mismo contrato de sesión. Las acciones sensibles de admisión siguen comprobando por separado la cuenta y la autenticación reciente de Google; una credencial de desarrollo no acredita esas pruebas.

02
Activación

El método se registra solo si se cumplen las dos condiciones:

  • NODE_ENV === "development", que solo ocurre con next dev (pnpm run dev).
  • DEV_SIGN_IN vale 1 o true (sin distinguir mayúsculas ni espacios).
EntornoFlagResultado
next devactivaSe registra /api/auth/sign-in/email y la página de inicio de sesión muestra el formulario.
next devausente o 0Comportamiento normal: redirección automática a Google.
build, next start, Vercel, Cloudflare, testsactivaNo se registra. Se loguea un warning (feature: dev-sign-in) y el endpoint responde EMAIL_PASSWORD_DISABLED.

La regla vive en resolveDevSignInActivation (src/modules/auth/infrastructure/dev-sign-in/dev-sign-in-activation.ts) y sigue el mismo patrón que MOCK_EXTERNAL_APIS. Es una flag separada a propósito: se puede simular Mercado Pago sin tocar el login, y al revés.

Con la flag activa y DEV_SIGN_IN_EMAIL o DEV_SIGN_IN_PASSWORD vacíos (o un email con formato inválido, o una contraseña de menos de 8 o más de 128 caracteres, lo que Better Auth rechazaría), el módulo de auth falla al cargar con un mensaje que nombra la variable. Es intencional: la flag se pidió de forma explícita y una configuración a medias no debe pasar desapercibida.
03
Configuración

En .env.local (nunca en código, fixtures ni capturas):

DEV_SIGN_IN=1
DEV_SIGN_IN_EMAIL=dev@tutribu.example
DEV_SIGN_IN_PASSWORD=una-contraseña-local
# Opcional: nombre del usuario creado (por defecto "Integrante de desarrollo").
DEV_SIGN_IN_NAME=

Las variables están documentadas en .env.example. La contraseña solo protege el acceso al servidor local; igual Better Auth la guarda hasheada en la tabla account.

04
Cómo funciona
  • Wiring. withDevSignIn (dev-sign-in-auth-options.ts) envuelve las opciones de betterAuth en src/modules/auth/infrastructure/better-auth/auth.ts. Si la activación no es enabled, devuelve las opciones sin cambios. Si lo es, agrega emailAndPassword: { enabled: true, disableSignUp: true } y un plugin propio antes de nextCookies.
  • Un solo usuario. El plugin intercepta /sign-in/email con un hook before: cualquier email distinto de DEV_SIGN_IN_EMAIL recibe 403 sin tocar la base. El sign-up público queda deshabilitado.
  • Seed perezoso. Antes de que Better Auth valide la contraseña, el plugin asegura el usuario con el adapter interno de Better Auth: lo crea si no existe (con emailVerified), vincula una cuenta credential si falta y reescribe el hash solo cuando DEV_SIGN_IN_PASSWORD cambió. No hace falta un script de seed ni una migración. Si el email ya pertenece a un miembro creado con Google, la credencial se vincula a ese mismo miembro y se conservan sus tribus. Un miembro creado solo con email y contraseña no tiene cuenta de Google: al renovar su sesión, el refresh de la foto de perfil se omite en lugar de registrar un error.
  • UI. SignInContent llama a resolveDevSignInFormEmail(process.env). Con el método activo, SignInView no arranca la redirección automática a Google: muestra el botón manual de Google y DevSignInForm (components/auth/dev-sign-in-form) con el email precargado. El formulario usa startDevSignIn del cliente de Better Auth y, al entrar, carga la ruta de callbackUrl como documento completo porque cambió la identidad.
05
Verificación
  • tests/unit/modules/auth/infrastructure/dev-sign-in-activation.test.ts: la regla de activación y la validación de credenciales.
  • tests/integration/modules/auth/dev-sign-in.test.ts: Better Auth real con el adapter en memoria. Cubre el alta en el primer login, la reutilización y el cambio de contraseña, el vínculo con un miembro existente, el rechazo de otros emails, el sign-up cerrado y que con NODE_ENV=production el endpoint responde EMAIL_PASSWORD_DISABLED aunque la flag esté activa.
  • tests/unit/pages/signin-page.test.tsx: el formulario solo aparece en next dev con la flag, no se redirige a Google y los errores se muestran junto al formulario.
06
Ensayo de admisión con diez cuentas

tests/e2e/admission-entry-sample.spec.ts ejecuta el criterio funcional SC-014 con diez cuentas ficticias independientes, repartidas entre Chromium y WebKit y anchos de 390 y 1280 píxeles. El escenario inicial usa revisión manual y comprobación adicional desactivada; la confirmación visible de una solicitud pendiente termina la medición.

El arnés de tests/support/admission-entry-sample-auth.ts compone el mismo withDevSignIn con el adapter real de Drizzle y el handler HTTP real de Better Auth en un servidor de pruebas limitado a loopback. Cada instancia admite su único correo configurado. Las direcciones .test y contraseñas se generan en memoria, Better Auth guarda los hashes y el navegador recibe sus cookies por HTTP. El endpoint de sesión del build de Next confirma después cada identidad y sesión. La aplicación conserva su configuración normal: el método de contraseña continúa deshabilitado en su build productivo.

La preparación ocurre únicamente en una rama Neon propia del ensayo, migrada por el arnés existente. Cuentas, claves y cookies no se incluyen en reportes ni capturas. La rama se elimina al salir, también ante fallos. El reporte conserva las diez observaciones, incluidas las fallidas; exige al menos nueve confirmaciones estrictamente antes de 120.000 ms desde la navegación inicial y comprueba el replay del identificador original sin solicitudes duplicadas. En este escenario no existe espera externa que restar.

pnpm build
pnpm exec playwright test --config playwright.admission-entry-sample.config.ts

La ejecución necesita el entorno privado local y acceso al proyecto Neon ya configurados. El reporte adjunto contiene alias, motor, ancho, tiempos y conteos de efectos; la medición técnica no acredita usabilidad humana, verificación de Google, entrega real de códigos ni validación con lector de pantalla. El protocolo y el resultado observado se conservan en specs/001-academy-admissions/validation/admission-entry-sample.md.
