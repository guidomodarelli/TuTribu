Pruebas de admisión a academias

Preparación para 001-academy-admissions. El arnés está implementado; los recorridos del producto y los gates operativos aún no están acreditados.

Transporte cerrado y dependencias reales

tests/support/admission-provider-transport.ts ofrece un fetch propio con registro exacto de origen, pathname y método. Rechaza cualquier ruta no registrada, sin recurrir a la red real. Sus observaciones contienen método, ruta registrada, estado HTTP y outcome; no guardan bodies, destinatarios, headers, tokens ni respuestas del proveedor.

Las pruebas usan el SDK oficial Zavu 0.57.0, el verificador Google de Better Auth y Web Crypto reales. Las claves y firmas de prueba se generan durante la ejecución. La pérdida de respuesta puede ocurrir después de un efecto aceptado; abortar la espera no acredita cancelar un envío ya iniciado. El scope de fetch global se restaura en finally y rechaza scopes superpuestos dentro del mismo worker.

pnpm test tests/support/admission-provider-transport.test.ts

Postgres en una rama propia

tests/support/academy-admission-database.ts crea una rama con nombre impredecible en el proyecto autorizado cold-firefly-92947172. Verifica que sea su propio hijo y que no sea default. DATABASE_URL aporta únicamente nombres de base y rol; el host y las credenciales de SQL se solicitan explícitamente para la rama recién creada. La conexión mantiene verificación TLS completa.

El ejecutor local delega autenticación, locking y renovación de tokens al manager oficial de Neon CLI; NEON_CLI_PATH permite ubicar su entrypoint. Con una autorización privada explícita para la invocación, el arnés usa directamente la API oficial con timeout acotado. No ejecuta refresh grants propios ni imprime credenciales, bodies del proveedor o stdout del CLI. Ante una respuesta de creación incierta, consulta el nombre único sin repetir el POST.

Un propietario externo puede planificar un UUID impredecible mediante ownershipNonce. El arnés valida ese UUID y rechaza un nombre ya existente antes del POST: no toma prestada ni elimina una rama anterior. La creación, las transacciones y la limpieza conservan los checks de proyecto, hijo exacto y condición no default. Las credenciales de administración no reemplazan esos checks.

Las transacciones usan createPostgresPool y runWithGuardedTransaction, con timeout de abandono y contexto local por cuenta. Se consulta la metadata real del rol runtime y se crea un rol temporal NOLOGIN NOSUPERUSER NOBYPASSRLS; los tests conceden únicamente las tablas que necesitan. applyMigration ejecuta el archivo versionado real en esa rama, sin comprobar strings de SQL como sustituto del comportamiento.

Al salir, se cierra el pool y se elimina la rama cuya propiedad fue confirmada, también cuando falla el callback. Una falla de cleanup conserva el error de trabajo e identifica el recurso pendiente. Si se pierden la respuesta de creación y la de reconciliación, el error neon_branch_creation_unknown conserva ambas causas y el nombre único para una reconciliación posterior; no repite el POST ni borra una rama no acreditada. El helper devuelve un resultado exitoso solo después de comprobar que su rama ya no está presente.

$env:RUN_ADMISSION_SQL_TESTS = '1'
pnpm test tests/support/academy-admission-database.test.ts
La suite SQL exige opt-in explícito y credenciales locales vigentes. Sin RUN_ADMISSION_SQL_TESTS=1 queda salteada y no cuenta como evidencia de SQL. Las suites futuras que modifiquen persistencia deben ejecutarse en la rama propia antes de dar su tarea por terminada.

Carga Native en CI

El workflow admission-performance.yml prepara una ejecución independiente de las cien presentaciones simultáneas y diez mil entradas. Conserva pool, guard, lease y presupuesto de tres segundos; registra veinte consultas mínimas antes de la ventana medida para distinguir latencia de red, preparación y carga. El host de GitHub no se presenta como una región garantizada ni como el entorno HTTP operativo.

La ejecución exige una API key temporal limitada al proyecto autorizado, dos UUID propios para las ramas y el commit exacto revisado. La key vive sólo en el secreto cifrado de GitHub; las otras tres entradas no son credenciales. Sin esa capacidad completa y el SHA coincidente, el job informa que el ensayo Native está pendiente y no acredita SQL ni rendimiento. Las pull requests externas no disparan este workflow.

run-admission-performance.mjs entrega al proceso hijo únicamente la autorización seleccionada, los nonces y un entorno sintético. Publica un DTO validado con estados de los dos casos, duraciones y contadores; un caso ausente o duplicado queda sin verificar. Conserva un fallo real del proceso y omite mensajes privados, SQL, parámetros, contactos y credenciales. El reporte original de Vitest no se publica y se retira al finalizar.

El propietario externo del ensayo debe comprobar el estado terminal de GitHub, reconciliar los dos nombres planificados con sus IDs y padres, confirmar la ausencia de ramas propias y revocar la API key y su configuración temporal. Un timeout de observación no demuestra que el job terminó ni que su limpieza ocurrió. La preparación del workflow no acredita todavía un resultado de CI Native, Node/Workers operativos ni los gates; la evidencia está en rendimiento de admisiones.

Carga distribuida reproducible en Node

tests/performance/academy-admissions-distributed-node-host.test.ts ejecuta una única cohorte de cien cuentas sintéticas sobre diez mil entradas. El coordinador prepara una rama propia y cuatro funciones Node, con veinticinco actores disjuntos por host y una sola configuración sintética externa. Los hosts reutilizan el boundary autenticado existente: sin bearer, con capacidad vencida o en otra rama no ejecutan SQL. La entrada privada nunca incluye tokens de sesión ni puede seleccionarla el caller HTTP.

La barrera SQL espera el calentamiento de los cuatro hosts. El percentil global conserva las cien duraciones originales, también las fallidas. Los límites del reloj de PostgreSQL deben demostrar solapamiento de las cien operaciones; cuatro picos locales no lo sustituyen. El coordinador comprueba además cincuenta ingresos, cincuenta pendientes, cien solicitudes, cincuenta miembros y cero entregas, con pool sin errores, esperas o conexiones retenidas. El replay compara también las mediciones persistidas originales, no sólo el estado del comando.

La preparación de rama, fixture/migraciones, despliegue/metadata, preflight HTTP, importación de configuración, calentamiento, barrera y consultas de salud se registran aparte del p95 de confirmación. El preflight incluye red e inicialización observada; no representa un arranque puro del proceso. Se conservan commit, hash del bundle, hashes de inputs, versión del compilador y capacidad efectiva. La configuración de prueba usa 4 CU; no altera defaults productivos ni el umbral estricto inferior a tres segundos.

$env:RUN_ADMISSION_SQL_TESTS = '1'
$env:RUN_ADMISSION_DISTRIBUTED_NODE_HOST_TESTS = '1'
$env:NEON_CLI_PATH = '<entrypoint del CLI oficial instalado>'
$env:ADMISSION_DISTRIBUTED_NODE_REPORT_FILE = '<archivo privado del ensayo>'
pnpm exec vitest run tests/performance/academy-admissions-distributed-node-host.test.ts

El CLI debe tener acceso al proyecto autorizado. Los nombres de base y rol se seleccionan explícitamente; las conexiones se obtienen sólo para el hijo recién creado. Sin ambos opt-in la prueba queda omitida. No se repite automáticamente un POST de resultado incierto. Las claves y el bearer se pasan por entorno privado, se comprueban contra archivos/argumentos propios y no integran el recibo. La limpieza elimina únicamente los cuatro slugs originales y la rama acreditada, también al fallar el umbral; el reporte conserva la medición fallida y confirma la retirada sólo después de observarla.

Las ejecuciones y sus límites se registran en evidencia de carga distribuida. Preparar el comando no acredita una ejecución Native, SC-015, Workers ni un gate operativo.

Fixtures y evidencia

El canario Linux de lector incorpora una captura pasiva de eventos AT-SPI en el display efímero de CI. Conserva sólo metadatos y conteos de un conjunto cerrado de eventos, con plazos y cierre confirmados; se detiene antes de consultar el texto nativo. El protocolo vigente diferencia la aplicación principal, el lector, otras aplicaciones y una identidad ausente, sin devolver sus nombres ni atribuir al navegador los mensajes de otra fuente. No genera anuncios ni cambia el foco. Rechaza contenido privado, totales inconsistentes, grupos duplicados y scopes desconocidos. La actividad del suscriptor y la voz/PCM mantienen comprobaciones independientes; una captura del árbol o del bus no sustituye la lectura del producto. El informe del lector conserva las ejecuciones y el scope de cada versión.

El disparo manual del canario actual acepta webkit_backend=webkitgtk para contrastar adicionalmente el MiniBrowser y WebKitWebDriver oficiales de Ubuntu. Conserva Chromium, las cuatro variantes y ambos tamaños; usa un transporte HTTP W3C hacia un proceso propio en loopback, sin sintetizar entrada, foco o voz. Comprueba el viewport observado después de descontar la barra del navegador y falla si no coincide. Registra el backend y su versión, conserva el paquete instalado y retira cada sesión y proceso propios. El valor predeterminado sigue usando Playwright. Este contraste adicional no sustituye los E2E ni acredita Safari, móviles físicos o recorridos de producto por sí solo.

La composición de owners del ensayo de restore reside en tests/support/messaging-restore-composition.ts, separada de seeders, Vitest y administración Neon. Recibe sólo transacciones guardadas, identidad de la sesión original y lectura de configuración externa; los fixtures conservan wrappers compatibles. La preparación puede compartir la configuración original del host sin exportar claves no extraíbles ni reconstruirlas desde SQL. La prueba completa de restore y reapertura sigue siendo obligatoria; un build o una importación de esta composición no acredita el escenario.

tests/support/academy-admission-fixtures.ts genera cuentas A/B, tribus distintas, roles y estados alternativos, snapshots comerciales conocidos o desconocidos y un reloj por escenario. La lista, invitación y política de uso parten de versión uno; países vacíos y época de verificación se mantienen separados. Las membresías son casos alternativos, no un lote que siembre dos líderes en la misma tribu. No se inventan credenciales ni URLs de invitación.

Los fixtures ayudan a ejercer las matrices; no autorizan autoingreso ni acreditan un canal productivo. Los gates OG-01 a OG-06 y sus pruebas pendientes se registran en operational-gates.md. Para los boundaries de payload y los guards compartidos, consultar validación de payloads y concurrencia y observabilidad.

Reconciliación paga y acceso a productos

Las pruebas de pago deben ejercer el webhook y las dos reconciliaciones administrativas con PostgreSQL y repositorios reales. Controlar sólo el puerto del proveedor mantiene la prueba sin cobros ni dependencia externa. La fixture compartida subscription-membership-reconciliation-fixture.ts conserva la configuración y las migraciones del escenario original; sus constantes pertenecen a tests/support/constants/.

Conservar una membresía no basta para acreditar que sus beneficios siguen intactos. Los casos de admission-membership-sources.test.ts siembran bonificaciones, matrícula y cursos existentes, leen el snapshot de producto y el árbol de cursos mediante los repositorios públicos del proyecto y comparan el resultado antes y después de cada reconciliación. Los dos productos y las tres entradas deben ejecutarse realmente; una variante filtrada no acredita la matriz. Las consultas de estado verifican identidades y efectos persistidos, nunca el texto SQL o los imports de una fuente.

El recorrido positivo de una invitación histórica por la política común mantiene su cobertura aparte: cerrar el writer antiguo después del marcador no prueba esa integración. No se anuncia el servicio externo ni OG-06 desde estos fixtures.
