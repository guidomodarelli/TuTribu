Pruebas de admisión a academias

Preparación para 001-academy-admissions. El arnés está implementado; los recorridos del producto y los gates operativos aún no están acreditados.

Transporte cerrado y dependencias reales

tests/support/admission-provider-transport.ts ofrece un fetch propio con registro exacto de origen, pathname y método. Rechaza cualquier ruta no registrada, sin recurrir a la red real. Sus observaciones contienen método, ruta registrada, estado HTTP y outcome; no guardan bodies, destinatarios, headers, tokens ni respuestas del proveedor.

Las pruebas usan el SDK oficial Zavu 0.57.0, el verificador Google de Better Auth y Web Crypto reales. Las claves y firmas de prueba se generan durante la ejecución. La pérdida de respuesta puede ocurrir después de un efecto aceptado; abortar la espera no acredita cancelar un envío ya iniciado. El scope de fetch global se restaura en finally y rechaza scopes superpuestos dentro del mismo worker.

pnpm test tests/support/admission-provider-transport.test.ts

Postgres en una rama propia

tests/support/academy-admission-database.ts crea una rama con nombre impredecible en el proyecto autorizado cold-firefly-92947172. Verifica que sea su propio hijo y que no sea default. DATABASE_URL aporta únicamente nombres de base y rol; el host y las credenciales de SQL se solicitan explícitamente para la rama recién creada. La conexión mantiene verificación TLS completa.

El arnés usa NEON_API_KEY local o el perfil existente de Neon CLI. Si el token está por vencer, delega renovación, locking y persistencia de tokens rotados al manager oficial del CLI mediante una consulta de proyecto. No ejecuta refresh grants propios ni imprime credenciales o stdout del comando. NEON_CLI_PATH permite ubicar el entrypoint instalado cuando no aparece en PATH. Ante una respuesta de creación incierta, consulta el nombre único; no repite el POST. No modifica la rama default ni la configuración del producto.

Cada solicitud administrativa, incluido cleanup, resuelve autorización nuevamente. Si falta menos de un minuto, espera ese plazo natural sin mantener una transacción SQL y deja que el manager oficial renueve el token vencido. Verifica también la vigencia devuelta: una consulta CLI exitosa no demuestra que haya renovado un token todavía válido. Una vigencia desconocida o insuficiente cierra la creación de recursos.

Las transacciones usan createPostgresPool y runWithGuardedTransaction, con timeout de abandono y contexto local por cuenta. Se consulta la metadata real del rol runtime y se crea un rol temporal NOLOGIN NOSUPERUSER NOBYPASSRLS; los tests conceden únicamente las tablas que necesitan. applyMigration ejecuta el archivo versionado real en esa rama, sin comprobar strings de SQL como sustituto del comportamiento.

Al salir, se cierra el pool y se elimina la rama cuya propiedad fue confirmada, también cuando falla el callback. Una falla de cleanup conserva el error de trabajo e identifica el recurso pendiente. Si se pierden la respuesta de creación y la de reconciliación, el error neon_branch_creation_unknown conserva ambas causas y el nombre único para una reconciliación posterior; no repite el POST ni borra una rama no acreditada. El helper devuelve un resultado exitoso solo después de comprobar que su rama ya no está presente.

$env:RUN_ADMISSION_SQL_TESTS = '1'
pnpm test tests/support/academy-admission-database.test.ts
La suite SQL exige opt-in explícito y credenciales locales vigentes. Sin RUN_ADMISSION_SQL_TESTS=1 queda salteada y no cuenta como evidencia de SQL. Las suites futuras que modifiquen persistencia deben ejecutarse en la rama propia antes de dar su tarea por terminada.

Fixtures y evidencia

tests/support/academy-admission-fixtures.ts genera cuentas A/B, tribus distintas, roles y estados alternativos, snapshots comerciales conocidos o desconocidos y un reloj por escenario. La lista, invitación y política de uso parten de versión uno; países vacíos y época de verificación se mantienen separados. Las membresías son casos alternativos, no un lote que siembre dos líderes en la misma tribu. No se inventan credenciales ni URLs de invitación.

Los fixtures ayudan a ejercer las matrices; no autorizan autoingreso ni acreditan un canal productivo. Los gates OG-01 a OG-06 y sus pruebas pendientes se registran en operational-gates.md. Para los boundaries de payload y los guards compartidos, consultar validación de payloads y concurrencia y observabilidad.
