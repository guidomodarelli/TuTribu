CONVENTION
Concurrency, Observability, and Performance
Reglas de concurrencia, observabilidad y performance para flujos de producto.
Scope: ReliabilityStatus: Active
01
Overview

Design client and server flows assuming concurrent execution, partial failures, retries, and out-of-order completion from the start.

02
Goal

Reduce hard-to-reproduce bugs and improve operational debugging by making concurrency, observability, and performance explicit engineering concerns.

03
Observability Rules

Structured logs

Use structured logs by default so events can be filtered, correlated, and aggregated across environments.

Prefer including:

  • event or message name
  • requestId and traceId when available
  • feature or use-case context
  • duration and outcome
  • safe resource identifiers

Do not log secrets, tokens, raw provider payloads, session data, or internal stack traces in user-facing surfaces.

logger.info({
  message: "Tribe created",
  tribeId,
  requestId,
  durationMs,
});

Request correlation

Treat request correlation as mandatory for server-side flows that cross boundaries such as route handlers, use cases, repositories, or external providers.

Every important request flow should be traceable through stable correlation identifiers: x-request-id identifies the local request and x-trace-id links related work across boundaries. When a trace header is missing, use the request id as the trace id fallback.

Route handlers that return JSON or redirects should attach both correlation headers to the response and log outcomes through the shared route observability helper so logs include status, outcome, durationMs, requestId, and traceId.

Actionable metrics

Measure the operational signals that help detect regressions early.

Track at least:

  • latency for critical flows
  • error rate
  • retry rate when retries exist
  • throughput for high-traffic paths
04
Client Concurrency Rules

Effects may re-run

Assume useEffect can run more than once, especially in Strict Mode and during rapid state changes.

Do not rely on an effect running exactly once unless the framework explicitly guarantees it.

Cancel async work

Cancel or invalidate asynchronous work when the component unmounts or when the effect dependencies change.

Prefer AbortController for fetch-based work and an equivalent cleanup strategy for other async APIs.

useEffect(() => {
  const controller = new AbortController();

  fetch("/api/data", { signal: controller.signal })
    .then((response) => response.json())
    .then((data) => setData(data))
    .catch((error) => {
      if (error.name !== "AbortError") {
        console.error(error);
      }
    });

  return () => controller.abort();
}, []);

Guard against stale or out-of-order responses

When multiple requests can overlap, ensure only the latest relevant response updates UI state.

Use request sequencing, refs, or equivalent invalidation patterns to prevent older responses from overwriting newer state.

const requestIdRef = useRef(0);

useEffect(() => {
  const requestId = ++requestIdRef.current;

  fetchData().then((result) => {
    if (requestId === requestIdRef.current) {
      setData(result);
    }
  });
}, [dependency]);

Avoid stale state updates

Use functional updates when the next value depends on the previous state.

setCount((previousCount) => previousCount + 1);

Client logging

Keep production client logging sparse, contextual, and safe.

Prefer reporting actionable failures to the approved observability platform instead of leaving noisy console output in production code.

05
Server Concurrency Rules

Assume concurrent mutations

Design every write path assuming multiple requests may target the same resource at nearly the same time.

Do not rely on the browser or UI ordering to guarantee consistency.

Idempotency and retries

Critical mutations should be safe under retries, duplicated submissions, and transient transport failures.

Prefer:

  • idempotency keys for retryable create operations
  • deterministic conflict handling for repeated writes
  • explicit retry policies only where side effects are safe

Shared-resource protection

Protect shared state with the correct consistency mechanism for the use case.

Common options include:

  • database transactions
  • optimistic concurrency with version checks
  • unique constraints for write deduplication
  • queueing or serialization where required by the domain

Error boundaries

Classify errors by responsibility and exposure level.

Expose safe, stable messages externally and keep detailed diagnostics in internal logs.

06
Performance and Resilience Rules

Avoid event-loop blocking

Keep CPU-heavy or blocking work out of latency-sensitive request paths unless it is explicitly bounded and justified.

Prefer asynchronous I/O, batching, background processing, or precomputation when appropriate.

Reduce unnecessary work

Avoid duplicate requests, overfetching, and repeated expensive computations in both client and server flows.

Prefer:

  • batching related operations
  • caching when data staleness is acceptable
  • debouncing or throttling for high-frequency user input
  • one primary server-side data entrypoint per route when possible

Design for partial failure

Assume provider calls, network requests, and downstream services can fail independently.

Handle timeouts, retries, and fallback behavior intentionally instead of letting failures leak as generic runtime errors.

Database connection pool resilience

Server renders can be aborted mid-flight (dev render restarts on cache miss, or a client disconnect in production). An aborted render suspends the finally that returns a pooled client, so a request-scoped transaction can leak its connection and eventually exhaust the pool, surfacing as timeout exceeded when trying to connect.

  • Every pooled checkout we control goes through the shared guarded transaction (runWithGuardedTransaction, used by withRequestContext and the profile-refresh pool) instead of a bare pool.connect()/finally pair. The only exception is runWithGuardedStatement (withStandaloneStatement): it runs exactly one self-contained statement without a transaction, such as the standalone account projection read_authenticated_account, which sets and restores its own request-local settings. It keeps the same release and connection-death handling. It sets a local idle_in_transaction_session_timeout right after BEGIN and releases the client on a connection error event. Postgres terminates an abandoned transaction, which closes the socket and lets the pool reclaim the slot. The window is far larger than any legitimate request, so healthy work is never affected.
  • For transactions opened by library adapters that own their own checkout (the Better Auth Drizzle adapter), createPostgresPool applies the same guard at the connection level via a session set_config in the pool onConnect hook. If that guard cannot be applied, acquisition must fail closed instead of handing out an unguarded connection. The Neon pooler rejects the options startup parameter, so the onConnect set_config is the supported way to set a connection-level GUC through the pooler; it persists across the pooled connection and is inherited by later transactions.
  • Keep enough pool headroom for concurrent renders. The Neon pooler tolerates hundreds of connections, so a small per-pool ceiling only starves legitimate concurrency.
  • Do not retry a session or query failure caused by a connection-acquisition timeout: retrying while the pool is saturated only doubles the pressure. Reserve retries for genuinely transient terminations (for example a backend-closed idle client).
  • To measure pool capacity in a deployed runtime, set POSTGRES_POOL_METRICS_LOG_INTERVAL_MS (an integer of at least 1000). createPostgresPool then attaches attachPostgresPoolMetrics, which logs one info entry per interval while the pool is in use (operation: "postgres_pool_metrics", message Postgres pool usage window.). Each window carries checkouts, queued checkouts (requested while the pool was full with no idle connection), checkout failures, acquisitions, releases, error releases, opened and removed connections, total and maximum checkout time, maximum queued checkout time, peaks of queued checkouts, checked-out and open connections, and the gauges at the end of the window. It is grouped by poolOperation and a random poolInstanceId per runtime instance. It never logs connection strings, hosts, SQL or row data. Leave the variable unset in production unless a measurement needs it; any other value keeps the metrics off.

Throttle provider reconciliation on hot read paths

When access resolution reconciles a subscription against the provider on every page load, concurrent renders multiply the provider HTTP calls and writes. Gate the reconciliation by freshness: reuse the locally stored status when it was reconciled within a short window (RECONCILIATION_FRESHNESS_SECONDS) and only call the provider once the stored status ages out. Real-time provider webhooks keep the stored status current between windows, so authorization staleness stays bounded by the window.

ProblemDescriptionConsequence
Race conditionsMultiple operations update the same state without coordinationInconsistent or corrupted data

08
Notes
  • Treat concurrency as a default condition, not an edge case.
  • Keep consistency guarantees on the server, not in the client.
  • Put external DTO mapping and provider-specific resilience logic in infrastructure, not in domain or presentational UI.
  • Follow repository security rules when logging or handling failures.
  • Use this document for decision guidance; keep AGENTS.md focused on compact mandatory rules.

Se revalidan después de las esperas y en el commit del efecto; un control oculto en UI, una cookie o un snapshot de cola no sustituyen esa autoridad. Los agregados derivan de efectos, ledgers, reservas e intentos persistidos. Un rethrow o un log no crean una serie adicional. El reporter de dispatch selecciona campos seguros y deduplica la misma causa en su contexto; esa deduplicación diagnóstica no reemplaza el ledger de la mutación. Una consulta no incrementa la versión, reinicia consumo ni fabrica un run.

Una reserva se vuelve a contrastar con países/cupo/versiones vigentes antes del marker. Los intentos inciertos conservan su identidad, conexión y reserva; no se cambian a otra cuenta, tribu, canal o pagador para superar una restricción. La recuperación consulta el resultado original y luego los hechos actuales, manteniendo separadas la versión histórica y la vigente.

Los tiempos publicados provienen de fases realmente observadas: operaciones, materialización interna, dispatch y retención con efectos positivos. Un lote vacío o revertido no produce otro éxito de retención y un hecho histórico sin tiempo mantiene su ausencia. El p95 de una fase no acredita por sí solo SC-013/SC-015: los ensayos de carga, entrega externa, cierre de ventana y arranque de infraestructura conservan sus mediciones y gates propios.

La señal de fallo y la recuperación deben seguir disponibles dentro de TuTribu aunque falle la mensajería. La consulta no depende de que llegue una alarma por ese mismo canal. Ver actividad y métricas, custodia y recuperación y el registro de gates.
