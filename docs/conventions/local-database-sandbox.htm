CONVENTION
Local Database Sandbox
Cómo correr el servidor local contra una branch propia de Neon, migrada y aislada de la base compartida, para usarla junto con los mocks de proveedores externos.
Scope: Local developmentStatus: Active
01
Overview

La base local es Postgres real: la app usa pg.Pool, SQL crudo, RLS con set_config y Better Auth, así que no se reemplaza por un driver en memoria. En su lugar, cada desarrollador trabaja sobre una branch de Neon con nombre estable, creada desde la branch default del proyecto (copy-on-write), con su propio compute.

pnpm db:sandbox crea o reutiliza esa branch, le aplica las migraciones pendientes de database/migrations/, enrola las claves de mensajería locales y escribe sus connection strings en .env.local. Desde ahí, pnpm run dev usa el sandbox sin otro cambio, porque Next.js prioriza .env.local sobre .env.

Es el complemento de External API Mocks: con MOCK_EXTERNAL_APIS=1, los planes, preapprovals y cuentas de vendedor que crea el mock de Mercado Pago quedan en el sandbox y nunca se mezclan con la base compartida, cuyos IDs pertenecen al proveedor real.

VariableDóndeUso
NEON_API_KEYEntorno o .env.localAPI key personal de Neon. Solo local; nunca en CI ni en el repositorio.
NEON_PROJECT_IDEntorno o .env.localProyecto de Neon de TuTribu (cold-firefly-92947172).
NEON_DEV_BRANCH_NAMEOpcionalNombre de la branch. Por defecto dev-sandbox-<usuario del sistema>, así cada desarrollador tiene la suya.
MESSAGING_SECURITY_ENVIRONMENT, MESSAGING_SECURITY_EPOCH, MESSAGING_RECOVERY_LOCK, MESSAGING_KEYRINGS_JSON.env.localClaves de mensajería solo para desarrollo, con el formato de .env.example y MESSAGING_RECOVERY_LOCK=false. El ledger de admisiones firma cada operación con ellas: sin estas variables o sin sus pruebas enroladas en la base, las decisiones de admisiones fallan. Si faltan, pnpm db:sandbox las genera con material propio de 32 bytes por clave en un bloque # >>> dev-messaging-keys; nunca las reutilices en otro entorno.
# .env.local
NEON_API_KEY=...
NEON_PROJECT_ID=cold-firefly-92947172
MOCK_EXTERNAL_APIS=1

pnpm db:sandbox
pnpm run dev
03
Commands
ComandoEfecto
pnpm db:sandboxCrea la branch si no existe (o la reutiliza y le asegura un compute read-write), aplica las migraciones pendientes, enrola las claves de mensajería y escribe .env.local. Es idempotente: correrlo de nuevo solo aplica migraciones nuevas y enrola claves nuevas.
pnpm db:sandbox -- --resetResetea la branch desde su padre (descarta los datos locales y toma una copia fresca de la default), migra, enrola las claves de mensajería y reescribe .env.local. Si la branch no existe, la crea.
pnpm db:sandbox -- --deleteElimina la branch y quita su bloque de .env.local; la app vuelve a la conexión configurada antes del sandbox (una asignación previa en .env.local o, si no hay, la de .env).
--dry-runSe combina con cualquiera de los anteriores. Solo consulta Neon e imprime el plan; no crea, migra ni escribe nada. Sin credenciales, asume que la branch no existe.

El script escribe al final de .env.local un bloque delimitado por comentarios # >>> dev-database-sandbox con DATABASE_URL, DATABASE_MIGRATION_URL y DATABASE_MAINTENANCE_URL. Las tres usan la connection string directa del sandbox: el runtime también la necesita, porque createPostgresPool aplica idle_in_transaction_session_timeout como estado de sesión, que un pooler en modo transacción no preserva (ver docs/architecture/migrating-to-neon.htm).

Neon entrega esa connection string con sslmode=require. createPostgresPool reescribe los alias prefer, require y verify-ca a sslmode=verify-full antes de crear el pool: pg 8 ya los trata como verify-full, así que la verificación TLS no cambia, desaparece la advertencia de seguridad de pg-connection-string en la consola y el comportamiento estricto se conserva cuando pg 9 adopte la semántica de libpq. Una connection string con uselibpqcompat=true se respeta tal cual.

El script solo reemplaza o quita ese bloque; no toca las asignaciones de esas variables que ya existían fuera de él. Next.js aplica la última asignación de cada variable, así que el bloque gana mientras exista y, al quitarlo con --delete, vuelven a regir los valores previos.

Después de migrar, si MESSAGING_KEYRINGS_JSON no está definida, el script genera claves de desarrollo, las agrega a .env.local en un bloque propio (que --delete conserva, porque las pruebas enroladas dependen de esas claves) y las usa en la misma corrida. Luego corre scripts/enroll-messaging-key-materials.mjs contra el sandbox para registrar en messaging_key_material_proofs las pruebas de las claves contact_fingerprint y operation_payload. El enrolamiento es idempotente y nunca reemplaza una prueba: si una clave cambió de material bajo el mismo id, falla y .env.local no se modifica.

pnpm run dev avisa al arrancar si la base configurada tiene migraciones sin aplicar; correr pnpm db:sandbox las aplica en el sandbox. Ver Error Diagnostics.

Si next dev ya estaba corriendo, reinicialo después de crear, resetear o eliminar el sandbox para que tome la nueva conexión.

04
Safety rules
  • Las migraciones corren con DATABASE_URL, DATABASE_MIGRATION_URL y DATABASE_MAINTENANCE_URL apuntando al sandbox, igual que el runner de pnpm test:ui. Nunca se migra la branch default: aplicar migraciones allí sigue siendo pnpm run db:migrate por pedido explícito.
  • El script se niega a crear, resetear, migrar o eliminar una branch default, primary o protegida, aunque NEON_DEV_BRANCH_NAME la nombre.
  • .env.local solo se escribe después de una migración y un enrolamiento exitosos: una corrida fallida no deja la app apuntando a un sandbox a medio preparar.
  • El enrolamiento corre con las tres variables de base apuntando al sandbox, así que nunca registra claves de desarrollo en la branch default.
  • Nunca se imprimen la API key ni las connection strings. El log muestra solo rol, host y database (postgresql://rol:***@host/db), y los errores de la API de Neon incluyen operación, método, path y status, sin el body.
  • El sandbox nace como copia de la branch default, con sus datos. Tratalo como datos sensibles: no lo compartas ni copies sus filas fuera de la máquina.
El sandbox es de larga vida y consume compute mientras se usa. Cuando no lo necesites, pnpm db:sandbox -- --delete lo elimina. Las branches efímeras de validación de migraciones (ver AGENTS.md) siguen siendo descartables y separadas de este sandbox.
05
Implementation
  • scripts/dev-database-sandbox.mjs: flags, plan de pasos, bloque de .env.local y redacción. Su lógica propia está cubierta en tests/unit/tooling/dev-database-sandbox-script.test.ts.
  • scripts/neon/neon-api-client.mjs: cliente mínimo de la API REST de Neon, compartido con scripts/e2e/neon-test-branch.mjs.
  • Las migraciones se aplican con el mismo runner que pnpm run db:migrate (scripts/push-migrations.js).
  • Las claves se enrolan con el mismo comando que pnpm messaging:enroll-keys (scripts/enroll-messaging-key-materials.mjs).
