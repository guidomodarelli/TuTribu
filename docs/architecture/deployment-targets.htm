Targets de despliegue
Decision operativa para mantener Vercel y habilitar Cloudflare Workers en la misma aplicacion Next.js App Router.
Scope: DeploymentStatus: Active
01
Decision

TuTribu mantiene compatibilidad con Vercel y agrega Cloudflare Workers como target de despliegue alternativo para la misma aplicacion Next.js App Router.

El script build conserva next build para no cambiar el contrato actual de Vercel. Los comandos de Cloudflare viven en scripts dedicados con el sufijo :cloudflare.

Criterio principal: cada target conserva su contrato de build y deploy sin mezclar herramientas ni outputs.
02
Matriz de targets
Target Estado Build Deploy
Vercel ACTIVE pnpm run build Build nativo de Next.js en Vercel.
Cloudflare Workers ALTERNATIVE pnpm run build:cloudflare opennextjs-cloudflare deploy o opennextjs-cloudflare upload.
PART 03
Cloudflare Workers
04
Runtime y output

Cloudflare usa @opennextjs/cloudflare para convertir el build de Next.js al runtime de Workers. El deploy no debe invocar wrangler directamente para publicar la aplicacion Next.js; debe usar opennextjs-cloudflare deploy o opennextjs-cloudflare upload.

La configuracion de wrangler.jsonc apunta al worker generado en .open-next/worker.js y a los assets generados en .open-next/assets. El directorio .open-next es output de build y no se versiona.

Los redirects legacy que pueden expresarse de forma estatica deben vivir en next.config.ts a traves de redirects, no en proxy.ts. En Next.js 16, proxy.ts corre con runtime nodejs; OpenNext Cloudflare no soporta middleware Node.js y el build debe evitar ese entrypoint cuando el comportamiento sea un redirect estatico.

Como el runtime usa pg para Postgres, pg-cloudflare debe declararse como dependencia directa y sus archivos runtime deben incluirse en outputFileTracingIncludes solo fuera de Vercel. OpenNext bundla con la condicion workerd, y pg resuelve ese adapter durante el empaquetado del server function.

Contrato esperado: wrangler.jsonc describe el artefacto generado; OpenNext sigue siendo el entrypoint de build y publicacion para Cloudflare.
05
Validacion operativa

Para validar el target de Cloudflare se debe ejecutar pnpm run build:cloudflare. Para preview local del runtime de Workers se debe usar pnpm run preview:cloudflare.

Advertencia de entorno: OpenNext advierte que los builds locales en Windows pueden fallar por comportamiento especifico del sistema operativo. La validacion final de Cloudflare debe correr en Linux, WSL con Node.js instalado o el entorno de build de Cloudflare.
06
Mantenimiento programado (cron)

El barrido de imagenes huerfanas de Cloudflare corre como tarea programada en ambos targets contra el mismo endpoint /api/maintenance/image-cleanup. Sin esta tarea, los drafts abandonados y la cola de huerfanos en cascada se acumulan.

En Vercel los crons diarios se declaran en vercel.json con crons. En Cloudflare Workers no existe equivalente automatico, por lo que se declaran los mismos schedules en wrangler.jsonc bajo triggers.crons. Los schedules diarios deben mantenerse sincronizados entre ambos archivos.

RutaScheduleDisparador en VercelDisparador en CloudflareTrabajo
/api/maintenance/image-cleanup0 4 * * *vercel.jsonwrangler.jsoncImagenes huerfanas de Cloudflare (diario, 04:00 UTC)
/api/maintenance/file-cleanup30 4 * * *vercel.jsonwrangler.jsoncAdjuntos huerfanos de R2 (diario, 04:30 UTC)
/api/maintenance/event-reminders*/5 * * * *GitHub Actions (.github/workflows/event-reminders-cron.yml)wrangler.jsoncRecordatorios de eventos y purga de notificaciones leidas (Notificaciones in-app)

Con varias expresiones en triggers.crons, el handler scheduled recibe la expresion que disparo y resolveMaintenancePathForCron (MAINTENANCE_CRON_SCHEDULE) la mapea a su ruta. Todas las rutas comparten la verificacion del bearer en src/modules/shared/infrastructure/http/cron-authorization.ts.

Vercel Hobby: el plan Hobby solo admite crons diarios y rechaza el deploy si vercel.json declara una expresion mas frecuente. Decision: el proyecto sigue en Hobby y el cron de recordatorios (*/5 * * * *) no se declara en vercel.json; lo dispara el workflow de GitHub Actions .github/workflows/event-reminders-cron.yml con curl GET a produccion y Authorization: Bearer <CRON_SECRET>. Requiere el secret de Actions CRON_SECRET (mismo valor que en Vercel) y la variable de Actions EVENT_REMINDERS_BASE_URL; sin ellos el job termina OK con un aviso y no llama a la ruta. Como GitHub puede demorar los schedules, la seleccion de recordatorios es catch-up ("vencido y aun no enviado", ver Notificaciones in-app). Cloudflare mantiene su propio trigger */5 en wrangler.jsonc.

Como OpenNext genera el worker en .open-next/worker.js y ese artefacto solo expone fetch, Cloudflare necesita un entrypoint propio. El campo main de wrangler.jsonc apunta a cloudflare/worker.ts, que reutiliza el fetch generado por OpenNext y agrega un handler scheduled. Ese handler vuelve a entrar a la misma ruta con el token Authorization: Bearer <CRON_SECRET>, de modo que la autorizacion del barrido es identica a la del cron de Vercel.

La logica testeable de ese disparo vive en config/cloudflare-scheduled-maintenance.ts (inyecta el fetch handler para poder probarse sin el worker generado). El entrypoint cloudflare/worker.ts importa output de build, por lo que se excluye del typecheck de la app y de oxlint y se valida en el build de Cloudflare.

Requisito: el cron de Cloudflare necesita CRON_SECRET configurado como secret del Worker. Si falta, el barrido se omite y la invocacion del cron falla de forma visible en Cloudflare, en lugar de correr sin autorizacion.
PART 06
Vercel
07
Contrato existente

Vercel sigue usando el build nativo de Next.js. No requiere wrangler.jsonc ni los scripts de Cloudflare para desplegar.

El mantenimiento de ambos targets no debe cambiar el comportamiento de pnpm run build, porque ese comando sigue siendo el contrato compartido por el flujo actual.

La inicializacion de desarrollo de @opennextjs/cloudflare y el tracing extra de archivos para Workers deben omitirse cuando el entorno define VERCEL=1, para que el build nativo de Vercel no ejecute tooling especifico de Workers ni empaquete archivos de dependencias pensados para Cloudflare.

Region de funciones: vercel.json fija regions: ["iad1"], la misma region que el proyecto Neon (aws-us-east-1). Es la region que ya tenia configurada el proyecto en Vercel; declararla en el repositorio evita que un cambio en el panel o un proyecto nuevo (como el piloto) aleje las funciones de la base. Cada request abre varias consultas a Postgres, asi que una funcion lejos de la base suma la latencia de red a cada una; el piloto midio checkouts de conexion de 40 a 250 ms con funciones en iad1. Si la base cambia de region, hay que mover regions en el mismo cambio. framework: "nextjs" deja explicito el preset que Vercel ya detecta.

Archivos excluidos del despliegue: .vercelignore deja fuera de lo que sube la CLI los .env* locales (salvo .env.example), los artefactos de build y de pruebas (.next, node_modules, test-results, playwright-report), los manuales internos de user-guides/ y la evidencia de validacion de la spec. Ninguno lo usa el build. El release no copia el entorno de producción a .env: vercel build carga .vercel/.env.production.local por su cuenta, y un .env en la raíz queda referenciado desde el artefacto prearmado pero fuera de la subida, lo que hace fallar vercel deploy --prebuilt con ENOENT (pasó en el release 1.10.0). No lista .git: la CLI ya lo excluye y el ignoreCommand (.golfo-rp/vercel-ignore-build.mjs) necesita el historial de Git para reconocer el commit de release.

Inscripción de claves HMAC de mensajería

Las operaciones de admisión y mensajería exigen que cada keyId activo y retenido de contact_fingerprint y operation_payload en MESSAGING_KEYRINGS_JSON tenga su prueba en public.messaging_key_material_proofs. Sin ella, el ledger rechaza cada operación nueva con platform_security_unavailable (409) y las pantallas muestran «Depende del equipo de TuTribu» con el código de diagnóstico admission_security_unconfigured; antes respondía resource_unavailable («El recurso solicitado no está disponible»), como ocurrió en el piloto al recrearlo con keyrings nuevos. Lo mismo pasa si faltan las MESSAGING_* o si MESSAGING_RECOVERY_LOCK está activo (código admission_recovery_locked); ver Seguridad de plataforma en el ledger.

Paso obligatorio: después de aplicar las migraciones y antes de exponer un deployment que use keyrings nuevos o rotados, un operador ejecuta con los secretos del entorno destino:

pnpm messaging:enroll-keys

Requiere MESSAGING_SECURITY_ENVIRONMENT, MESSAGING_SECURITY_EPOCH, MESSAGING_RECOVERY_LOCK=false, MESSAGING_KEYRINGS_JSON y DATABASE_MAINTENANCE_URL (o DATABASE_MIGRATION_URL). Exit 0 con state: "completed" y los newlyEnrolledKeyIds por propósito; exit 1 con un code estable: messaging_key_enrollment_connection_missing, messaging_crypto_configuration_invalid, messaging_crypto_recovery_locked, messaging_crypto_context_mismatch (la conexión no es el owner), messaging_crypto_key_continuity_unproven (un keyId inscripto cambió de material: no rotar reutilizando ids) o messaging_key_enrollment_failed con su SQLSTATE. Repetirlo es seguro.

Por qué no es automático: el build de Vercel corre también para previews y no debe escribir en la base de producción ni recibir el owner; el flujo de golfo-rp aplica migraciones desde la máquina del operador, que no tiene por qué tener los keyrings de producción, y su motor es compartido. Por eso queda como paso explícito del runbook, igual que pnpm run db:migrate. Si se automatiza, el lugar es un job de GitHub Actions manual o post-release con un environment protegido que tenga sólo esos secretos.

Detección: si se omite, cada request afectado registra messaging_key_material_unverified (feature messaging) con los propósitos y keyIds; ver la arquitectura de mensajería. Conviene configurar una alerta de logs de Vercel sobre ese mensaje.

Disparadores de admisión con activación explícita

GET /api/maintenance/admission-messaging compone el mantenimiento privado de admisión con el bearer nativo actual. Conserva un presupuesto total de cuarenta y cinco segundos y resultados parciales explícitos. El host retiene sólo la observación del trabajo original tardío; no lanza otro intento ni confunde aceptación con recepción.

La configuración base de wrangler.jsonc mantiene ADMISSION_MESSAGING_MAINTENANCE_ENABLED=false y los tres schedules anteriores. El entorno optativo admission-maintenance agrega * * * * * y habilita exclusivamente este disparador. Apunta al mismo Worker tutribu, conserva sus assets y repite el binding de autorreferencia, porque los bindings y las variables no se heredan entre entornos. Compilar con opennextjs-cloudflare build --env admission-maintenance prepara ese artefacto; no lo publica ni activa crons remotos.

El handler scheduled selecciona la ruta por la expresión del evento, exige la activación exacta true y un CRON_SECRET, y vuelve a entrar una sola vez mediante el fetch real de OpenNext. Sólo 200 confirma el recorrido; 202 conserva un original ocupado y no confirma trabajo completo; los demás estados y fallos de transporte hacen fallar la invocación. El wrapper no reintenta y conserva la causa privada de una respuesta incierta.

El workflow .github/workflows/admission-messaging-cron.yml prepara un catch-up HTTP cada cinco minutos y una ejecución manual. El schedule queda omitido mientras la variable de Actions ADMISSION_MESSAGING_MAINTENANCE_ENABLED no sea exactamente true. Una ejecución manual incompletamente configurada termina con error antes de enviar. Requiere además el origen ADMISSION_MESSAGING_MAINTENANCE_BASE_URL y el secret CRON_SECRET; la concurrencia evita solapamientos del mismo workflow.

node scripts/run-admission-maintenance.mjs realiza una única petición GET autorizada, sin seguir redirects ni repetirla. Admite HTTPS y HTTP sólo para loopback, rechaza credenciales, paths adicionales, query y fragmentos en el origen y aplica un plazo exterior de sesenta segundos. Descarta el cuerpo y registra únicamente operación, código propio y estado HTTP; nunca serializa el bearer, contenido ni causas internas. Los fallos y el estado 202 dejan exit code 1.

Límite operativo: no se modifica vercel.json, no se despliega este entorno ni se configura el hosting o Actions. Vercel Hobby conserva pendiente un driver frecuente aprobado y medido. La cadencia declarada de Actions no garantiza puntualidad; ni el build ni la ejecución local acreditan el p95 de SC-015 o el gate OG-05. T187 y su dependencia T186 conservan sus criterios completos hasta la auditoría de cierre. La evidencia del disparador distingue configuración, ejecución local y validación operativa.
