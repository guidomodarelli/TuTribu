Targets de despliegue
Decision operativa para mantener Vercel y habilitar Cloudflare Workers en la misma aplicacion Next.js App Router.
Scope: DeploymentStatus: Active
01
Decision

TuTribu mantiene compatibilidad con Vercel y agrega Cloudflare Workers como target de despliegue alternativo para la misma aplicacion Next.js App Router.

El script build conserva next build para no cambiar el contrato actual de Vercel. Los comandos de Cloudflare viven en scripts dedicados con el sufijo :cloudflare.

Criterio principal: cada target conserva su contrato de build y deploy sin mezclar herramientas ni outputs.
02
Matriz de targets
Target Estado Build Deploy
Vercel ACTIVE pnpm run build Build nativo de Next.js en Vercel.
Cloudflare Workers ALTERNATIVE pnpm run build:cloudflare opennextjs-cloudflare deploy o opennextjs-cloudflare upload.
PART 03
Cloudflare Workers
04
Runtime y output

Cloudflare usa @opennextjs/cloudflare para convertir el build de Next.js al runtime de Workers. El deploy no debe invocar wrangler directamente para publicar la aplicacion Next.js; debe usar opennextjs-cloudflare deploy o opennextjs-cloudflare upload.

La configuracion de wrangler.jsonc apunta al worker generado en .open-next/worker.js y a los assets generados en .open-next/assets. El directorio .open-next es output de build y no se versiona.

Los redirects legacy que pueden expresarse de forma estatica deben vivir en next.config.ts a traves de redirects, no en proxy.ts. En Next.js 16, proxy.ts corre con runtime nodejs; OpenNext Cloudflare no soporta middleware Node.js y el build debe evitar ese entrypoint cuando el comportamiento sea un redirect estatico.

Como el runtime usa pg para Postgres, pg-cloudflare debe declararse como dependencia directa y sus archivos runtime deben incluirse en outputFileTracingIncludes solo fuera de Vercel. OpenNext bundla con la condicion workerd, y pg resuelve ese adapter durante el empaquetado del server function.

Contrato esperado: wrangler.jsonc describe el artefacto generado; OpenNext sigue siendo el entrypoint de build y publicacion para Cloudflare.
05
Validacion operativa

Para validar el target de Cloudflare se debe ejecutar pnpm run build:cloudflare. Para preview local del runtime de Workers se debe usar pnpm run preview:cloudflare.

Advertencia de entorno: OpenNext advierte que los builds locales en Windows pueden fallar por comportamiento especifico del sistema operativo. La validacion final de Cloudflare debe correr en Linux, WSL con Node.js instalado o el entorno de build de Cloudflare.
06
Mantenimiento programado (cron)

El barrido de imagenes huerfanas de Cloudflare corre como tarea programada en ambos targets contra el mismo endpoint /api/maintenance/image-cleanup. Sin esta tarea, los drafts abandonados y la cola de huerfanos en cascada se acumulan.

En Vercel los crons diarios se declaran en vercel.json con crons. En Cloudflare Workers no existe equivalente automatico, por lo que se declaran los mismos schedules en wrangler.jsonc bajo triggers.crons. Los schedules diarios deben mantenerse sincronizados entre ambos archivos.

RutaScheduleDisparador en VercelDisparador en CloudflareTrabajo
/api/maintenance/image-cleanup0 4 * * *vercel.jsonwrangler.jsoncImagenes huerfanas de Cloudflare (diario, 04:00 UTC)
/api/maintenance/file-cleanup30 4 * * *vercel.jsonwrangler.jsoncAdjuntos huerfanos de R2 (diario, 04:30 UTC)
/api/maintenance/event-reminders*/5 * * * *GitHub Actions (.github/workflows/event-reminders-cron.yml)wrangler.jsoncRecordatorios de eventos y purga de notificaciones leidas (Notificaciones in-app)

Con varias expresiones en triggers.crons, el handler scheduled recibe la expresion que disparo y resolveMaintenancePathForCron (MAINTENANCE_CRON_SCHEDULE) la mapea a su ruta. Todas las rutas comparten la verificacion del bearer en src/modules/shared/infrastructure/http/cron-authorization.ts.

Vercel Hobby: el plan Hobby solo admite crons diarios y rechaza el deploy si vercel.json declara una expresion mas frecuente. Decision: el proyecto sigue en Hobby y el cron de recordatorios (*/5 * * * *) no se declara en vercel.json; lo dispara el workflow de GitHub Actions .github/workflows/event-reminders-cron.yml con curl GET a produccion y Authorization: Bearer <CRON_SECRET>. Requiere el secret de Actions CRON_SECRET (mismo valor que en Vercel) y la variable de Actions EVENT_REMINDERS_BASE_URL; sin ellos el job termina OK con un aviso y no llama a la ruta. Como GitHub puede demorar los schedules, la seleccion de recordatorios es catch-up ("vencido y aun no enviado", ver Notificaciones in-app). Cloudflare mantiene su propio trigger */5 en wrangler.jsonc.

Como OpenNext genera el worker en .open-next/worker.js y ese artefacto solo expone fetch, Cloudflare necesita un entrypoint propio. El campo main de wrangler.jsonc apunta a cloudflare/worker.ts, que reutiliza el fetch generado por OpenNext y agrega un handler scheduled. Ese handler vuelve a entrar a la misma ruta con el token Authorization: Bearer <CRON_SECRET>, de modo que la autorizacion del barrido es identica a la del cron de Vercel.

La logica testeable de ese disparo vive en config/cloudflare-scheduled-maintenance.ts (inyecta el fetch handler para poder probarse sin el worker generado). El entrypoint cloudflare/worker.ts importa output de build, por lo que se excluye del typecheck de la app y de ESLint y se valida en el build de Cloudflare.

Requisito: el cron de Cloudflare necesita CRON_SECRET configurado como secret del Worker. Si falta, el barrido se omite y la invocacion del cron falla de forma visible en Cloudflare, en lugar de correr sin autorizacion.
PART 06
Vercel
07
Contrato existente

Vercel sigue usando el build nativo de Next.js. No requiere wrangler.jsonc ni los scripts de Cloudflare para desplegar.

El mantenimiento de ambos targets no debe cambiar el comportamiento de pnpm run build, porque ese comando sigue siendo el contrato compartido por el flujo actual.

La inicializacion de desarrollo de @opennextjs/cloudflare y el tracing extra de archivos para Workers deben omitirse cuando el entorno define VERCEL=1, para que el build nativo de Vercel no ejecute tooling especifico de Workers ni empaquete archivos de dependencias pensados para Cloudflare.
