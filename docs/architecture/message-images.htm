Architecture
Imágenes en mensajes
Decisión de almacenamiento, tenancy y borrado remoto para adjuntos del feed.
Scope: MessagesStatus: Active
01
Decisión

Los mensajes de la ronda usan Cloudflare Images mediante Direct Creator Uploads. La app crea la URL de subida en servidor, el browser sube el archivo directo a Cloudflare y luego el mensaje adjunta assets ya verificados.

El token de Cloudflare queda siempre server-side. El browser recibe solamente uploadUrl, assetId e imageId.

02
Modelo de datos

La tabla message_images pertenece al módulo messages y usa tribe_id como clave de aislamiento multi-tenant. message_id es nullable para soportar drafts antes de publicar.

  • draft: asset creado y todavía no adjuntado.
  • attached: asset visible en un mensaje.
  • pending_delete: asset oculto y pendiente de borrado remoto.
  • deleted: asset remoto borrado o tratado como eliminado.
El máximo de cuatro imágenes se refuerza con sort_order entre 0 y 3 para assets adjuntos, además de la validación en application.
03
Límites de arquitectura

Los use cases de messages dependen del puerto MessageImageRepository. La aplicación prepara y valida comandos, pero no conoce Cloudflare ni detalles HTTP externos.

El adapter CloudflareImagesMessageImageRepository concentra Direct Creator Uploads, verificación de draft, construcción de delivery URLs y borrado remoto.

Después de una subida directa, Cloudflare puede mantener el asset como draft durante una ventana corta aunque el upload HTTP ya haya terminado. Por eso el adapter espera y reintenta de forma acotada la verificación remota antes de rechazar el adjunto.

Las policies de message_images permiten que quien subió la imagen administre sus drafts y que los roles autorizados por public.can_pin_tribe_messages muevan assets desde attached a pending_delete durante borrados moderados y luego a deleted durante la limpieza remota.

Si el borrado remoto falla durante una eliminación directa, el adapter restaura el estado local previo para que una imagen adjunta siga visible y el usuario pueda reintentar. Durante la limpieza de assets ya pendientes, el sistema conserva pending_delete para permitir reintentos posteriores.
