Architecture
Medios en mensajes
Almacenamiento, tenancy y borrado de los adjuntos del feed: imágenes (Cloudflare) y videos externos, unificados en una sola galería.
Scope: MessagesStatus: Active
01
Decisión

Los mensajes de la ronda usan Cloudflare Images mediante Direct Creator Uploads. La app crea la URL de subida en servidor, el browser sube el archivo directo a Cloudflare y luego el mensaje adjunta assets ya verificados.

El token de Cloudflare queda siempre server-side. El browser recibe solamente uploadUrl, assetId e imageId.

02
Modelo de datos

La tabla message_images pertenece al módulo messages y usa tribe_id como clave de aislamiento multi-tenant. message_id es nullable para soportar drafts antes de publicar.

  • draft: asset creado y todavía no adjuntado.
  • attached: asset visible en un mensaje.
  • pending_delete: asset oculto y pendiente de borrado remoto.
  • deleted: asset remoto borrado o tratado como eliminado.
Una publicación admite hasta 10 medios combinados (imágenes + videos externos). Cada medio ocupa un sort_order global entre 0 y 9 compartido por imágenes y videos; el constraint sort_order BETWEEN 0 AND 9 de message_images es defensa, y el tope combinado lo refuerza la validación en application (MESSAGE_MEDIA.maxCount).
04
Videos externos y galería unificada

Los videos son links externos (YouTube, Vimeo, Wistia, Loom) y viven en la tabla message_videos del módulo messages, con tribe_id de aislamiento, message_id con ON DELETE CASCADE, external_video_provider, external_video_id y sort_order. No tienen lifecycle de subida: se validan con el value object parseExternalVideoUrl y se insertan directo. La columna histórica de un único video en messages fue migrada a esta tabla y eliminada.

Imágenes y videos comparten un único espacio de sort_order (0..9) por mensaje. La galería unificada se arma al leer: el repositorio de ronda mergea ambas tablas por sort_order y expone un solo arreglo media (unión discriminada por kind: image | video), en el orden que eligió el autor. El modal del mensaje renderiza el arreglo completo como una galería de miniaturas cuadradas 1:1 debajo del texto; cada miniatura abre el carrusel fullscreen al hacer click. El feed muestra solo el primer medio (media[0]) como una única miniatura cuadrada 1:1 a la derecha del contenido, sin galería ni carrusel inline. Ambas miniaturas (feed y modal) comparten el mismo tamaño, definido una sola vez con la variable SCSS $media-thumbnail-size.

El composer envía un único arreglo ordenado media al crear o editar; el índice de cada ítem es su slot global. En edición, media: [] limpia todos los medios. El use case normalizeMessageMediaDrafts valida el tope combinado, deduplica imágenes, parsea las URLs de video y asigna el sort_order global.

El carrusel fullscreen monta el iframe del proveedor solo para el slide activo; los slides de video inactivos muestran un poster liviano (miniatura del proveedor o placeholder). Esto evita arrancar varios reproductores de terceros a la vez —que contendían el main thread y producían lag al navegar— y evita que un iframe cross-origin retenga el foco del teclado.

El montaje/desmontaje del iframe se dispara con el evento settle de Embla (scroll terminado), no con select (scroll iniciado). Desmontar un reproductor cross-origin a mitad de la animación estanca el rAF de Embla y deja las flechas como "presiono pero no avanza"; al diferirlo hasta settle, la animación completa y solo los indicadores de progreso se actualizan durante el desplazamiento. Además se desactiva watchFocus: un slide con iframe enfocado haría que Embla volviera a él y cancelara la navegación.

La navegación con flechas de teclado (ArrowLeft/ArrowRight) se intercepta a nivel del diálogo en fase de captura, de modo que funciona sin importar qué elemento del diálogo tenga el foco (botón de cerrar, cuerpo o controles del carrusel); la única excepción inevitable es cuando el foco ya está dentro de un reproductor cross-origin en reproducción.

Las policies de message_videos: lectura para quien puede leer el contenido de la tribu (public.can_read_tribe_content); inserción, edición y borrado directos solo para el autor activo del mensaje. El borrado del mensaje elimina sus videos por cascada de la FK (sin pasar por RLS).
03
Límites de arquitectura

Los use cases de messages dependen del puerto MessageImageRepository. La aplicación prepara y valida comandos, pero no conoce Cloudflare ni detalles HTTP externos.

El adapter CloudflareImagesMessageImageRepository concentra Direct Creator Uploads, verificación de draft, construcción de delivery URLs y borrado remoto.

Después de una subida directa, Cloudflare puede mantener el asset como draft durante una ventana corta aunque el upload HTTP ya haya terminado. Por eso el adapter espera y reintenta de forma acotada la verificación remota antes de rechazar el adjunto.

Cuando application ya preparó imágenes para una creación pero el mensaje no termina en estado created, intenta borrar esos assets con deleteImage antes de devolver el fallo. En el cliente, si una creación o edición falla, los drafts nuevos se quitan del compositor y se envía el borrado remoto correspondiente.

Las policies de message_images permiten que quien subió la imagen administre sus drafts y que los roles autorizados por public.can_pin_tribe_messages muevan assets desde attached a pending_delete durante borrados moderados y luego a deleted durante la limpieza remota.

Si el borrado remoto falla durante una eliminación directa, el adapter restaura el estado local previo para que una imagen adjunta siga visible y el usuario pueda reintentar. Durante la limpieza de assets ya pendientes, el sistema conserva pending_delete para permitir reintentos posteriores.
