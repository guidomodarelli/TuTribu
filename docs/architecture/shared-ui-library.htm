Arquitectura · UI

Una biblioteca compartida

beez-ui concentra los componentes y las modificaciones reutilizables entre repositorios.

Actualizado: 2026-10-16 · pnpm 12.6.0

Responsabilidades

El repositorio beez-ui es la fuente de verdad para los componentes originales de LaTribu y los componentes reutilizables de agenda-mensual. Incluye sus modificaciones, utilidades de clases, detección móvil, contrato de cookies del sidebar, props para integrar la navegación del consumidor y acceso a Sonner.

Desde 0.9.0 también pertenecen a beez-ui las piezas reutilizables que antes vivían en TuTribu: primitivas y tokens de movimiento, menú de cuenta, links en markdown y su editor, botón de reacción y helpers como formatFileSize o copyTextToClipboard. TuTribu les pasa datos ya resueltos y su copy en español. Las piezas atadas a un flujo del producto (campana de notificaciones, calendario de eventos, handoff de navegadores internos, selector de emojis, reloj por minuto) y los envoltorios simples (estados vacío y de error) siguen en la aplicación.

El tema (el foundation de Arc), los tokens y las fuentes locales de la biblioteca pertenecen a beez-ui. TuTribu conserva sus componentes de producto, SCSS Modules y preferencias de página. No contiene copias de los componentes compartidos. Las capas de dominio y aplicación no dependen de esta biblioteca de presentación.

Contrato de consumo

import { Button, Dialog, Input, toast } from "beez-ui";

Agrupar los imports nombrados desde la raíz. Los hooks de uso general (useIsMobile, useIsHydrated, useViewerTimeZone, useHorizontalSwipe) se importan desde el entrypoint beez-ui/hooks. El barrel no tiene use client: cada módulo mantiene su frontera original. Next.js configura transpilePackages y experimental.optimizePackageImports para compilar los paquetes compartidos e importar únicamente los módulos usados; desde 0.2.0 el paquete distribuye JavaScript y declaraciones en dist.

AppUIProvider monta BeezUIProvider desde beez-ui/next. El wrapper @/components/navigation/link reexporta Link desde la raíz de la biblioteca: Next conserva navegación cliente con prefetch desactivado. AvatarImage usa Next Image sin optimizador por defecto, con carga y fallback administrados por Base UI. Los componentes de imagen específicos del producto conservan sus propias opciones de Next.

El provider usa next-themes como único propietario del tema. Mantiene storageKey: tutribu-theme y default system. Selector, notificaciones y selector de emojis leen useTheme desde beez-ui. Se eliminan los scripts y el estado local duplicados; html conserva suppressHydrationWarning. Los valores guardados inválidos se normalizan al sistema. El error global monta su propio AppUIProvider porque reemplaza al root layout.

Importar únicamente beez-ui/styles.css en la hoja global. Desde 0.3.1, la biblioteca publica CSS listo para el navegador: reset, utilidades, tema y fuentes. El consumidor no necesita Tailwind, plugins PostCSS ni @source. Los tokens de producto se sobrescriben con CSS normal y los estilos de pantalla permanecen en SCSS Modules. La entrada de desarrollo styles.source.css se compila dentro de beez-ui; no forma parte del tarball.

Diseño Arc

Desde 1.0.0 la biblioteca adopta el foundation de Arc: colores por rol (--surface, --surface-muted, --text-secondary, --text-muted, --border-strong, --danger), radios concéntricos (--radius-control 18 px, --radius-panel 26 px, --radius-surface 34 px), alturas de control (--control-height-sm, -md y -lg), sombras, curvas y foco visible solo con teclado, en claro y oscuro. El acento es el azul de Arc. Los nombres de shadcn (--primary, --muted, --muted-foreground…) siguen como alias; --accent pasa a ser el acento de marca de Arc. El provider escribe el tema como clase dark y como data-theme.

TuTribu carga Inter (texto y controles) y Geist (títulos de página) con next/font/local desde app/fonts y los expone en --font-sans, --font-body, --font-heading y --font-display; Poppins se retiró. El fondo de la página es plano. Los estilos de producto usan solo los pesos 400 y 500, sin mayúsculas forzadas ni espaciado ancho.

Button sigue la API de Arc: variant primary, secondary, ghost o danger; size sm, md o lg; loading; type="button" por defecto. No admite asChild: una navegación con aspecto de botón queda como Link, <a> o <label> y toma el estilo con el mixin action-link de src/styles/_action-link.scss, que replica la receta de Arc sobre los mismos tokens. Los botones de solo ícono usan size="sm" con aria-label o texto oculto. Los disparadores de Radix siguen componiendo con asChild en el disparador.

Distribución reproducible

La biblioteca se publica en el registry público de npm como beez-ui, desde el workflow de release de beez-ui con trusted publishing. Entre 0.12.0 y 1.0.0 se publicó solo en GitHub Packages como @guidomodarelli/beez-ui; desde 2.0.0 vuelve a npm con el nombre sin scope. La aplicación consume beez-ui@^2.7.0 sin mapear registries ni configurar tokens, ni en desarrollo ni en GitHub Actions ni en Vercel. pnpm-lock.yaml fija la versión exacta y la integridad para desarrollo, el gate de GitHub Actions y el build de Vercel; no se guardan tarballs en el repositorio ni se requiere acceso al directorio hermano. pnpm-workspace.yaml excluye el paquete de minimumReleaseAge para adoptar una versión recién publicada.

  1. Modificar y validar la biblioteca en su repositorio.
  2. Preparar y publicar una versión mediante su flujo de releases.
  3. Actualizar el consumidor con pnpm add beez-ui@^VERSION y conservar el lockfile actualizado.
  4. Verificar instalación congelada, tests, tipos y build. Las pruebas de Chromium y WebKit cubren interacción, navegación y persistencia del tema; no fijan colores, tamaños ni otros valores CSS. Los tests de Vitest simulan movimiento reducido para evitar depender de animaciones del navegador.

Los nuevos componentes upstream se incorporan mediante el CLI oficial de shadcn/ui dentro de beez-ui. Revisar sus imports internos y exportarlos desde la raíz. No ejecutar ese CLI en el consumidor.

Compatibilidad y pruebas

Se preservan los estados deshabilitados, fallback y reintento de avatar, preferencias del sidebar e hidratación determinista. La librería usa Vitest 5.0.0 y cnfast 0.2.0, y cubre esos contratos con componentes reales; TuTribu verifica su consumo desde el artefacto instalado y sus flujos de producto.

pnpm test:ui construye la app y verifica interacción de controles, accesibilidad, restauración de tutribu-theme, persistencia, cambios del sistema, hidratación, navegación cliente y la animación de los diálogos en Chromium y WebKit, tanto desktop como móvil. En Windows, Playwright.exe de WebKit hereda sus pipes de stdio a WebKitNetworkProcess.exe, que a veces queda trabado al terminar y las mantiene abiertas: el worker esperaba el evento close para siempre y el runner lo mataba a los cinco minutos con código 1 aunque todos los tests pasaran. Por eso playwright.ui.config.ts y playwright.beezping.config.ts instalan tests/e2e/support/release-exited-browser-stdio.ts: cuando el proceso de WebKit ya salió y sus pipes siguen abiertas tras cinco segundos, las libera y deja una advertencia en stderr con el pid y el código de salida. Un navegador que no termina no se toca, así que el runner sigue fallando ante un cuelgue real. Los tests de Vitest montan el provider real para probar sincronización entre pestañas y recuperación ante almacenamiento bloqueado o valores inválidos.

Desde beez-ui 0.10 el sidebar sigue el animated sidebar de beui: el ancho cambia con un spring entre el panel y el riel de íconos, una píldora sigue al ítem activo y en el teléfono se abre como hoja con foco atrapado. Los ítems de AppSidebar reciben icon, isActive, onSelect y badge (para «Pronto» y el check de la tribu activa); el componente compartido marca aria-current y cierra la hoja móvil al elegir. Como SidebarMenuButton ya no admite asChild, el botón de marca es un botón propio que abre el selector de tribu, y el riel colapsado se detecta con [data-slot="sidebar"][data-state="collapsed"].

Desde la versión con App rail, la plataforma ya no usa el Sidebar de beez-ui: su shell es el bloque Pro «Sidebar rail» de Arc (modo App rail), adaptado en components/app-rail/app-rail-shell. La barra se pliega a un riel de íconos con resorte, flota sobre la página entre 480 y 640 px de ancho del shell, se abre como hoja arrastrable por debajo de 480 px, tiene tooltips de Radix en el riel, títulos de grupo que pasan a divisores, el botón del panel con la tecla [, anuncios en role="status", la marca de la tribu (que abre el selector de tribus), el perfil de la persona al pie y una ruta animada en la barra superior. Las adaptaciones son: la navegación real de components/app-rail/app-rail-navigation.ts en lugar de los datos de muestra, filas que navegan con el router, la preferencia en la cookie sidebar_state que el layout lee en el servidor, un shell de alto completo con scroll de la ventana (sidebar y barra superior fijas con sticky), la hoja montada en body, clases BEM en SCSS, textos en español y los tokens de motion de Arc en components/app-rail/app-rail-motion.ts, que coinciden con las variables --ease-* y --duration-* de beez-ui. Por usar Dialog y Tooltip de Radix como el bloque, radix-ui pasa a ser dependencia directa, en la misma versión que ya instala beez-ui. El ancho del sidebar se anima con resorte como en Arc: es la excepción documentada en docs/conventions/motion.htm.

Los archivos adaptados del bloque Pro llevan el aviso de la licencia Arc Pro (uiarc.dev/license) y no están cubiertos por la licencia del proyecto. TuTribu es un producto final, así que puede contenerlos; beez-ui es una librería publicada en npm y no puede recibir código Pro. Las reglas completas están en AGENTS.md, sección «Arc Pro license».

El loader de la aplicación es el componente Pro «Morph loader» de Arc (uiarc.dev/components/morph-loader), adaptado en components/loaders/morph-loader con el aviso de la licencia Arc Pro y fuera de beez-ui, porque la licencia no permite redistribuirlo en una librería publicada. Reemplaza al antiguo BouncingDotsLoader: dibuja cuatro trazos que pasan entre las formas dots, bars, ring y square con resortes de Motion, y al cambiar status a success o error los pliega en un check (--success) o una cruz (--danger). Las adaptaciones son: la geometría y el loop en reposo separados en morph-loader-geometry.ts y morph-loader-idle.ts, los tiempos de MOTION_TIMING y MOTION_EASE de beez-ui en lugar de los tokens de Arc, textos accesibles en español («Cargando...», «Listo», «No se pudo completar»), aria-label en el role="status", clases BEM en SCSS y la aparición con 120 ms de retraso del loader anterior, para que una carga breve no lo muestre. Con prefers-reduced-motion muestra una forma estática por estado. La ronda lo usa al cargar mensajes y respuestas.

Entre beez-ui 2.2.0 y 2.6.x, DialogContent y AlertDialogContent siguieron el Center Morph Modal de beUI (se desplegaban desde su centro y se plegaban hacia él); desde 2.7.0 usan la transición de Arc descripta abajo. Con movimiento reducido el diálogo aparece y desaparece sin animación. La API, el foco, el cierre con Escape y el botón de cerrar no cambian, así que TuTribu no adapta sus componentes. La suite de navegador de beez-ui valida esta animación y el camino de movimiento reducido en Chromium y WebKit, desktop y móvil, y pnpm test:ui la valida dentro de pantallas reales de TuTribu.

Desde beez-ui 2.6.0, 18 componentes adoptan el diseño y la motion de Arc Free sin cambiar su API: Switch, Checkbox, RadioGroup, Badge, Avatar, Skeleton, Card, Alert, Tooltip, Popover, HoverCard, DropdownMenu, Select, Tabs, Pagination, Dialog/AlertDialog, Calendar y Carousel. Lo que TuTribu tiene en cuenta al componerlos:

  • El velo, el radio, el borde, la sombra y el padding de 24 px de los diálogos son de beez-ui. DialogFooter sobresale ese padding hasta los bordes del panel con su propio borde superior, tinte y padding, así que los diálogos de TuTribu no le agregan border-top, fondo ni padding, ni redefinen el padding, el radio o el fondo de DialogContent cuando usan un footer. El composer de la ronda solo mantiene las acciones en una fila y, en el teléfono, suma el área segura inferior al padding del footer. DialogHeader ya deja espacio al botón de cerrar.
  • Ningún módulo pisa el velo global ([data-slot="dialog-overlay"]): todos los diálogos usan el de Arc. Solo se conserva overscroll-behavior y el ajuste del visor de medios que quita el desenfoque mientras reproduce video.
  • Badge mide 26 px (22 px con size="sm") y toma el color de tone (neutral, success, info, warning, danger) o del tono que implica variant; TuTribu elige el tamaño y el tono con props en lugar de redefinir alto, borde o color, y no vuelve a animar su entrada.
  • Switch mide 42×24 y Select usa la altura de Input (36 px con size="sm"); las filas de gestión centran sus controles sin alturas fijas.
  • Los tooltips esperan 250 ms (valor por defecto de TooltipProvider) y los hover cards abren a los 500 ms y cierran a los 140 ms. El popover saliente queda inert mientras termina su salida y el foco vuelve al trigger al terminar, por eso los tests esperan el foco con waitFor.

Desde beez-ui 2.6.1, TuTribu monta ThemedToaster (en components/providers/app-providers) en lugar del Toaster crudo de Sonner, conservando closeButton, position: "top-center", richColors y el tema resuelto por useTheme. Con un Dialog, AlertDialog o Sheet abierto, los botones de un toast reciben el puntero sin cerrar el modal, el atajo de Sonner (Alt+T) lleva el foco al toast a pesar de la trampa de foco del modal y, si el control enfocado cierra su toast, el foco vuelve al control del modal desde el que llegó. TuTribu no tiene estilos propios de toasts (cn-toast, [data-sonner-*]) que pisar. Los arreglos de 2.6.1 al Sidebar móvil no aplican porque la plataforma usa su propio App rail. PopoverContent más alto que el espacio disponible ahora se desplaza por dentro, lo que alcanza al selector de emoji de los canales en ventanas bajas. tests/e2e/toast-over-dialog.spec.ts abre el diálogo «Suscribirme al calendario» en los cuatro proyectos, responde la solicitud del link con un error y con un link válido, y comprueba que el botón de cerrar de cada toast responde al puntero y al teclado, que el diálogo sigue abierto y que el foco vuelve a «Generar link».

Desde beez-ui 2.7.0 la motion sigue los presets de Arc con los mismos nombres de tokens: los springs (SPRING_LAYOUT, SPRING_POP…) pasan a la forma { type, visualDuration, bounce }, MOTION_TIMING.enter sube a 0.24 s, MOTION_TIMING.exit a 0.18 s y MOTION_EASE_IN_OUT cambia de curva. TuTribu pasa los springs enteros como transition y nunca lee stiffness, damping ni mass, así que no adapta su código; $ease-in-out de src/styles/_motion.scss se alinea con la curva nueva. Dialog y AlertDialog entran como el diálogo de Arc: el panel sube 8 px y crece desde 0.96 con el spring smooth mientras aparece, y sale en 0.16 s bajando 4 px hasta 0.98 con un fundido; conserva la transformación y la opacidad que recibe por className y, si se reabre mientras sale, vuelve desde donde está. Input, Textarea, InputGroup y SelectTrigger ya no tiemblan con aria-invalid, y las opciones de Select, Alert, FormMessage y el ícono del cambio de tema aparecen sin desenfoque. TuTribu no tenía estilos que dependieran del plegado, del temblor ni del desenfoque, por eso no quita overrides. Los tokens deprecados (MOTION_TIMING.centerMorph, centerMorphFold, shake, MOTION_EASE_UNFOLD, MOTION_CENTER_MORPH_FOLDED_PERCENT, MOTION_INVALID_SHAKE_PX) no se usan en la aplicación.

tests/e2e/dialog-motion.spec.ts abre y cierra el detalle de un evento (DialogContent) y la confirmación para eliminarlo (AlertDialogContent) en los cuatro proyectos. Mide en cada frame la opacidad, el clip-path y la escala y el desplazamiento del transform del contenido: al abrirse debe pasar por frames más abajo y más chicos que el reposo, sin superar la distancia (MOTION_DIALOG_DISTANCE) ni la escala (MOTION_SURFACE_SCALE) de entrada y sin recorte, y terminar opaco y sin transformar; al cerrarse debe bajar y achicarse dentro de MOTION_DIALOG_EXIT_DISTANCE y MOTION_EXIT_SCALE, desvanecerse y desmontarse. Los límites salen de los tokens que exporta beez-ui. Con page.emulateMedia({ reducedMotion: "reduce" }), todos los frames deben estar ya en reposo, sin recorte y con opacidad completa. En computadora también abre el modal de detalle de un mensaje de la ronda con un viewport impar y comprueba que, al terminar la apertura, el panel queda en píxeles enteros y no se mueve en los frames siguientes. Ese caso se omite en móvil, donde el modal ocupa toda la pantalla. Cada grabación termina cuando el contenido queda asentado o se desmonta, no por tiempo, porque WebKit headless puede producir pocos frames por segundo.

Los escenarios con sesión no agregan rutas, plugins ni métodos de ingreso de prueba a producción. scripts/e2e/run-ui-tests.mjs, que ejecuta pnpm test:ui después del build, prepara la base antes de levantar next start:

  1. Con NEON_API_KEY y NEON_PROJECT_ID (en el entorno o en .env.local), crea por la API de Neon una rama efímera de la rama por defecto y la elimina al terminar, aunque los tests fallen o se interrumpan con Ctrl+C. Con E2E_DATABASE_URL usa en cambio una base descartable existente, sin eliminarla. Sin ninguna de las dos, los escenarios con sesión se omiten y los demás corren igual.
  2. Aplica las migraciones pendientes con scripts/push-migrations.js.
  3. Siembra un miembro líder, su tribu con el canal Ronda, un mensaje y un evento futuro, con identificadores únicos por corrida (scripts/e2e/dialog-fixtures.mjs).
  4. Crea la fila de session como la guarda Better Auth y firma la cookie better-auth.session_token con HMAC-SHA256 y un BETTER_AUTH_SECRET aleatorio generado para esa corrida, que no se escribe en disco.
  5. Ejecuta Playwright con DATABASE_URL, DATABASE_MIGRATION_URL y DATABASE_MAINTENANCE_URL apuntando a la base efímera, BETTER_AUTH_URL en http://127.0.0.1:3110 y la cookie y los datos sembrados en variables E2E_* que lee el spec.

Así la corrida nunca toca la base del desarrollador ni de producción, y el secreto de la sesión solo vale contra ese servidor de prueba. El gate de GitHub Actions no ejecuta pnpm test:ui y no recibe credenciales de Neon. El log de error Failed to refresh member profile image que aparece durante la corrida es esperado: el miembro sembrado no tiene una cuenta de Google vinculada.

Las pruebas del sidebar usan providers reales. Se conservan los dobles preexistentes de notificaciones para aislar los timers y el estado global de Sonner, con el resto de exports reales.

React Compiler

La versión 0.5.0 incluye memoización automática en los módulos de cliente, compilada con Oxc dentro de beez-ui. La aplicación no necesita habilitar React Compiler para recibir esas optimizaciones. Los módulos compatibles con Server Components conservan JavaScript sin cachés de cliente; La aplicación usa React y React DOM 19.3, con sus tipos 19.3; el runtime del compilador sigue siendo compatible con React 19.2 o posterior. El CSS sigue precompilado dentro del paquete.

Tooling de la biblioteca

El código y los tests de beez-ui se verifican con TypeScript 7 mediante configuraciones separadas. La API de TypeScript 6 se conserva mediante el alias oficial de compatibilidad porque el plugin de docgen de Storybook la declara como peer; el comando tsc sigue ejecutando TypeScript 7. Las dependencias de la biblioteca usan rangos ^ y el lockfile fija las versiones verificadas.

Revisión de constantes

El contrato de cookie se define una sola vez en beez-ui/src/constants/sidebar.ts y se exporta desde la raíz para el servidor y el cliente. Los anchos y el atajo del sidebar y el breakpoint móvil permanecen locales. El adaptador Next aporta dimensiones intrínsecas de 40 px y los estilos determinan el tamaño visual del avatar. Se preservan los nombres y valores públicos; las unidades quedan documentadas.

Lint con oxlint

LaTribu y beez-ui usan oxlint ^1.85.0, configurado en .oxlintrc.json. Las reglas de Next, React, React Compiler, jsx-a11y, import y TypeScript son nativas de oxlint, por lo que no hacen falta presets de ESLint ni excepciones de peers. En LaTribu, el plugin JS propio scripts/oxlint/no-lint-disable-plugin.mjs rechaza las directivas eslint-disable y oxlint-disable. Al agregar o cambiar una regla o un plugin JS, se corre pnpm lint sobre un cambio que la viole a propósito para confirmar que reporta: un plugin que no carga no produce ningún diagnóstico. No se mantienen tests que solo verifiquen que el tooling está configurado.

Integración de agenda-mensual

Se incorporan Alert, AnimatedThemeToggler, Calendar, DataTable, FilterQueryBar, Form, Highlighter, InputGroup, Label, RadioGroup, TypingAnimation y ThemedToaster, junto con sus tipos y gramática. La tabla preserva agrupación, filtros configurables y memoización. Los componentes mantienen el tema de LaTribu y sus primitivas existentes.

AnimatedThemeToggler y ThemedToaster consumen el provider compartido; sus props explícitas permiten usos controlados. Desde beez-ui 2.6.1, TuTribu monta ThemedToaster en lugar del Toaster original y le pasa resolvedTheme junto con sus opciones (closeButton, position: "top-center" y richColors). El sidebar ofrece storageKey opcional sin cambiar su cookie pública ni los defaults del servidor. Los paneles largos admiten scroll y los botones exponen variante y tamaño.

Las pruebas de tabla y filtros se trasladaron a Vitest conservando sus escenarios. Se agregaron pruebas de integración de las primitivas y una app React/Vite para validar interacción, tema y responsive en Chromium y WebKit. agenda-mensual se usó como fuente de lectura; su aplicación no se modificó.

Tests de la aplicación

Vitest 5 ejecuta las suites con Vite y React reales. El tsconfig de producto excluye los tests; tsconfig.test.json los valida con los tipos de Vitest y Testing Library mediante pnpm typecheck:tests. El gate pnpm ci incluye ambos chequeos. Los mocks de notificaciones conservan su aislamiento de timers, y las pruebas con relojes simulados permiten avanzar las esperas de Testing Library. pnpm 12.6.0 fija las dependencias en el lockfile.

Runtime y compilador de las aplicaciones

Node 24.21.0 se fija en .nvmrc, usado localmente y por el gate de GitHub Actions en .github/workflows/quality-gate.yml. Los pushes no ejecutan un gate local. El rango de engines admite únicamente Node 24, compatible con Vercel. pnpm 12.6.0 y Vitest 5 mantienen los comandos existentes. El paquete raíz typescript@^7.0.2 proporciona la CLI nativa para la aplicación, los tests y Next build mediante experimental.useTypeScriptCli.

El lint no usa la API JavaScript de TypeScript, así que la aplicación no necesita la capa de compatibilidad de TypeScript 6. Se conserva jsdom para los tests de las aplicaciones.

React Compiler en la aplicación

Next.js activa reactCompiler: true y experimental.turbopackRustReactCompiler: true para compilar los componentes propios durante desarrollo y build con Turbopack. Esta implementación nativa no requiere Babel y no admite builds con webpack. Vitest activa react({ compiler: true }) mediante @vitejs/plugin-react y oxc-transform-react@^0.145.0, compatible con el peer del plugin. Las suites ejecutan el código con memoización automática habilitada; se conserva jsdom. Los tests de páginas asíncronas que necesitan resolver componentes compilados usan el renderer de servidor de React y verifican el HTML resultante; no invocan esos componentes fuera del contexto de render. Las interacciones cliente continúan usando Testing Library. Son integraciones experimentales distintas: Next utiliza su implementación nativa y Vite utiliza Oxc. El gate existente ejecuta tipos, lint, tests y build con estas opciones, sin prometer mejoras de rendimiento no medidas.
