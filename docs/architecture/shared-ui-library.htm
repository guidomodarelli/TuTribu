Arquitectura · UI

Una biblioteca compartida

beez-ui concentra los componentes y las modificaciones reutilizables entre repositorios.

Actualizado: 2026-09-25 · pnpm 12.6.0

Responsabilidades

El repositorio beez-ui es la fuente de verdad para los componentes originales de LaTribu y los componentes reutilizables de agenda-mensual. Incluye sus modificaciones, utilidades de clases, detección móvil, contrato de cookies del sidebar, props para integrar la navegación del consumidor y acceso a Sonner.

Desde 0.9.0 también pertenecen a beez-ui las piezas reutilizables que antes vivían en TuTribu: primitivas y tokens de movimiento, menú de cuenta, links en markdown y su editor, botón de reacción y helpers como formatFileSize o copyTextToClipboard. TuTribu les pasa datos ya resueltos y su copy en español. Las piezas atadas a un flujo del producto (campana de notificaciones, calendario de eventos, handoff de navegadores internos, selector de emojis, reloj por minuto) y los envoltorios simples (estados vacío y de error, loader) siguen en la aplicación.

El tema default, los tokens y las fuentes locales de LaTribu pertenecen a beez-ui. TuTribu conserva sus componentes de producto, SCSS Modules y preferencias de página. No contiene copias de los componentes compartidos. Las capas de dominio y aplicación no dependen de esta biblioteca de presentación.

Contrato de consumo

import { Button, Dialog, Input, toast } from "beez-ui";

Agrupar los imports nombrados desde la raíz. Los hooks de uso general (useIsMobile, useIsHydrated, useViewerTimeZone, useHorizontalSwipe) se importan desde el entrypoint beez-ui/hooks. El barrel no tiene use client: cada módulo mantiene su frontera original. Next.js configura transpilePackages y experimental.optimizePackageImports para compilar los paquetes compartidos e importar únicamente los módulos usados; desde 0.2.0 el paquete distribuye JavaScript y declaraciones en dist.

AppUIProvider monta BeezUIProvider desde beez-ui/next. El wrapper @/components/navigation/link reexporta Link desde la raíz de la biblioteca: Next conserva navegación cliente con prefetch desactivado. AvatarImage usa Next Image sin optimizador por defecto, con carga y fallback administrados por Base UI. Los componentes de imagen específicos del producto conservan sus propias opciones de Next.

El provider usa next-themes como único propietario del tema. Mantiene storageKey: tutribu-theme y default system. Selector, notificaciones y selector de emojis leen useTheme desde beez-ui. Se eliminan los scripts y el estado local duplicados; html conserva suppressHydrationWarning. Los valores guardados inválidos se normalizan al sistema. El error global monta su propio AppUIProvider porque reemplaza al root layout.

Importar únicamente beez-ui/styles.css en la hoja global. Desde 0.3.1, la biblioteca publica CSS listo para el navegador: reset, utilidades, tema y fuentes. El consumidor no necesita Tailwind, plugins PostCSS ni @source. Los tokens de producto se sobrescriben con CSS normal y los estilos de pantalla permanecen en SCSS Modules. La entrada de desarrollo styles.source.css se compila dentro de beez-ui; no forma parte del tarball.

Distribución reproducible

La aplicación consume beez-ui@^0.6.0 desde el registro público de npm. pnpm-lock.yaml fija la versión exacta y la integridad para desarrollo, el gate del hook pre-push y el build de Vercel; no se guardan tarballs en el repositorio ni se requiere acceso al directorio hermano.

  1. Modificar y validar la biblioteca en su repositorio.
  2. Preparar y publicar una versión mediante su flujo de releases.
  3. Actualizar el consumidor con pnpm add beez-ui@^VERSION y conservar el lockfile actualizado.
  4. Verificar instalación congelada, tests, tipos y build. Las pruebas de Chromium y WebKit cubren interacción, navegación y persistencia del tema; no fijan colores, tamaños ni otros valores CSS. Los tests de Vitest simulan movimiento reducido para evitar depender de animaciones del navegador.

Los nuevos componentes upstream se incorporan mediante el CLI oficial de shadcn/ui dentro de beez-ui. Revisar sus imports internos y exportarlos desde la raíz. No ejecutar ese CLI en el consumidor.

Compatibilidad y pruebas

Se preservan Button.asChild, estados deshabilitados, fallback y reintento de avatar, preferencias del sidebar e hidratación determinista. La librería usa Vitest 5.0.0 y cnfast 0.2.0, y cubre esos contratos con componentes reales; TuTribu verifica su consumo desde el artefacto instalado y sus flujos de producto.

pnpm test:ui construye la app y verifica interacción de controles, accesibilidad, restauración de tutribu-theme, persistencia, cambios del sistema, hidratación y navegación cliente en Chromium y WebKit, tanto desktop como móvil. Los tests de Vitest montan el provider real para probar sincronización entre pestañas y recuperación ante almacenamiento bloqueado o valores inválidos.

Las pruebas del sidebar usan providers reales. Se conservan los dobles preexistentes de notificaciones para aislar los timers y el estado global de Sonner, con el resto de exports reales.

React Compiler

La versión 0.5.0 incluye memoización automática en los módulos de cliente, compilada con Oxc dentro de beez-ui. La aplicación no necesita habilitar React Compiler para recibir esas optimizaciones. Los módulos compatibles con Server Components conservan JavaScript sin cachés de cliente; La aplicación usa React y React DOM 19.3, con sus tipos 19.3; el runtime del compilador sigue siendo compatible con React 19.2 o posterior. El CSS sigue precompilado dentro del paquete.

Tooling de la biblioteca

El código y los tests de beez-ui se verifican con TypeScript 7 mediante configuraciones separadas. La API de TypeScript 6 se conserva mediante el alias oficial de compatibilidad porque el plugin de docgen de Storybook la declara como peer; el comando tsc sigue ejecutando TypeScript 7. Las dependencias de la biblioteca usan rangos ^ y el lockfile fija las versiones verificadas.

Revisión de constantes

El contrato de cookie se define una sola vez en beez-ui/src/constants/sidebar.ts y se exporta desde la raíz para el servidor y el cliente. Los anchos y el atajo del sidebar y el breakpoint móvil permanecen locales. El adaptador Next aporta dimensiones intrínsecas de 40 px y los estilos determinan el tamaño visual del avatar. Se preservan los nombres y valores públicos; las unidades quedan documentadas.

Lint con oxlint

LaTribu y beez-ui usan oxlint ^1.85.0, configurado en .oxlintrc.json. Las reglas de Next, React, React Compiler, jsx-a11y, import y TypeScript son nativas de oxlint, por lo que no hacen falta presets de ESLint ni excepciones de peers. En LaTribu, el plugin JS propio scripts/oxlint/no-lint-disable-plugin.mjs rechaza las directivas eslint-disable y oxlint-disable. Al agregar o cambiar una regla o un plugin JS, se corre pnpm lint sobre un cambio que la viole a propósito para confirmar que reporta: un plugin que no carga no produce ningún diagnóstico. No se mantienen tests que solo verifiquen que el tooling está configurado.

Integración de agenda-mensual

Se incorporan Alert, AnimatedThemeToggler, Calendar, DataTable, FilterQueryBar, Form, Highlighter, InputGroup, Label, RadioGroup, TypingAnimation y ThemedToaster, junto con sus tipos y gramática. La tabla preserva agrupación, filtros configurables y memoización. Los componentes mantienen el tema de LaTribu y sus primitivas existentes.

AnimatedThemeToggler y ThemedToaster consumen el provider compartido; sus props explícitas permiten usos controlados. LaTribu conserva el Toaster original y le pasa resolvedTheme para mantener sus opciones visuales. El sidebar ofrece storageKey opcional sin cambiar su cookie pública ni los defaults del servidor. Los paneles largos admiten scroll y los botones exponen variante y tamaño.

Las pruebas de tabla y filtros se trasladaron a Vitest conservando sus escenarios. Se agregaron pruebas de integración de las primitivas y una app React/Vite para validar interacción, tema y responsive en Chromium y WebKit. agenda-mensual se usó como fuente de lectura; su aplicación no se modificó.

Tests de la aplicación

Vitest 5 ejecuta las suites con Vite y React reales. El tsconfig de producto excluye los tests; tsconfig.test.json los valida con los tipos de Vitest y Testing Library mediante pnpm typecheck:tests. El gate pnpm ci incluye ambos chequeos. Los mocks de notificaciones conservan su aislamiento de timers, y las pruebas con relojes simulados permiten avanzar las esperas de Testing Library. pnpm 12.6.0 fija las dependencias en el lockfile.

Runtime y compilador de las aplicaciones

Node 24.21.0 se fija en .nvmrc, usado localmente y por el gate del hook pre-push (no hay gate en GitHub Actions). El rango de engines admite únicamente Node 24, compatible con Vercel. pnpm 12.6.0 y Vitest 5 mantienen los comandos existentes. El paquete raíz typescript@^7.0.2 proporciona la CLI nativa para la aplicación, los tests y Next build mediante experimental.useTypeScriptCli.

El lint no usa la API JavaScript de TypeScript, así que la aplicación no necesita la capa de compatibilidad de TypeScript 6. Se conserva jsdom para los tests de las aplicaciones.

React Compiler en la aplicación

Next.js activa reactCompiler: true y experimental.turbopackRustReactCompiler: true para compilar los componentes propios durante desarrollo y build con Turbopack. Esta implementación nativa no requiere Babel y no admite builds con webpack. Vitest activa react({ compiler: true }) mediante @vitejs/plugin-react y oxc-transform-react@^0.145.0, compatible con el peer del plugin. Las suites ejecutan el código con memoización automática habilitada; se conserva jsdom. Los tests de páginas asíncronas que necesitan resolver componentes compilados usan el renderer de servidor de React y verifican el HTML resultante; no invocan esos componentes fuera del contexto de render. Las interacciones cliente continúan usando Testing Library. Son integraciones experimentales distintas: Next utiliza su implementación nativa y Vite utiliza Oxc. El gate existente ejecuta tipos, lint, tests y build con estas opciones, sin prometer mejoras de rendimiento no medidas.
