1. Alcance y separación de responsabilidades

El proveedor administra planes, autorizaciones recurrentes, facturas y pagos. TuTribu administra membresía, vinculación verificada, habilitación de ventas y períodos de acceso. Un preapproval autorizado permite cobrar; por sí solo no acredita una cuota ni concede acceso pago a la academia.

La arquitectura específica está en Suscripciones por tribu y Acceso a la academia. El segundo documento conserva la evidencia detallada, las limitaciones y el historial de investigación. Los recorridos para usuarios están en Academia y Medios de pago.

El adapter externo pertenece a src/modules/subscriptions/infrastructure/mercado-pago/. Los casos de uso consumen puertos y resultados internos; la UI recibe DTO propios. Validar inputs y DTO públicos en sus fronteras; mapear solamente los campos upstream utilizados, sin volver a validar con esquemas completos las respuestas del proveedor o filas de PostgreSQL. Véase Validación de payloads.

2. OAuth, cuentas y configuración

Configuración del servidor
NombreUso
MERCADO_PAGO_CLIENT_IDAplicación que solicita la autorización del vendedor.
MERCADO_PAGO_CLIENT_SECRETIntercambio y renovación de tokens; secreto del servidor.
MERCADO_PAGO_WEBHOOK_SECRETSecreto de firma correspondiente a la aplicación que emite la notificación.
MERCADO_PAGO_BACK_URLBase HTTPS pública de retorno. Si está vacía, la aplicación utiliza BETTER_AUTH_URL; desarrollo necesita una URL pública válida.
ACADEMY_SALES_ACTIVATION_ENABLEDControl operativo propio de TuTribu: solamente "true" permite el recorrido de activación de ventas. No es una opción de Mercado Pago.
  1. Iniciar OAuth con el líder autenticado y autorizado para la tribu; construir state firmado que identifica miembro y tribu.
  2. Redirigir a https://auth.mercadopago.com.ar/authorization con client_id, response_type=code, platform_id=mp, redirect_uri y state.
  3. En el callback, comprobar firma de state, sesión y permisos antes de asociar la cuenta. Intercambiar code con el mismo redirect_uri registrado.
  4. Persistir tokens únicamente en almacenamiento del servidor de la integración correspondiente. Renovar mediante refresh_token; reemplazar los tokens devueltos y actualizar el vencimiento.
// POST https://api.mercadopago.com/oauth/token
// Authorization code: server-side JSON request
{
  "client_id": "<application-id>",
  "client_secret": "<server-secret>",
  "grant_type": "authorization_code",
  "code": "<one-time-code>",
  "redirect_uri": "https://example.com/api/mercado-pago/oauth/callback"
}
// Refresh: grant_type="refresh_token" and refresh_token,
// together with client_id and client_secret.
// Private internal result:
// {accessToken, expiresIn, providerAccountId, refreshToken}

El vendedor que posee el recurso determina el token para todas sus consultas y modificaciones. providerAccountId procede de user_id del intercambio OAuth; no aceptar una cuenta indicada por el navegador como autorización.

Mantener separados aplicación, vendedor, comprador y entorno. Una credencial de cuenta ficticia puede comenzar con APP_USR-: el prefijo solo no demuestra movimientos de dinero real. test_token: true y tokens TEST- corresponden a experimentos de sandbox; no son el flujo de producción del adapter. client_credentials no reemplaza la autorización delegada del vendedor. Confirmar identidades y compatibilidad de participantes; se observó error 2034 al mezclar participantes de prueba y producción.

En otro proyecto, completar la protección de OAuth con caducidad y uso único del estado, rotación de secretos y controles de acceso adecuados. El estado firmado actual de TuTribu no debe describirse como un registro persistido de nonce de un solo uso.

3. Endpoints externos utilizados

Base REST: https://api.mercadopago.com. Recursos del vendedor: Authorization: Bearer <seller-access-token>. Escrituras JSON: Content-Type: application/json. Creación de planes y suscripciones envía X-Idempotency-Key; la reserva local sigue siendo necesaria.

GET /preapproval_plan/{id}Obtener plan y estado. Mapear monto, moneda, referencia, motivo y prueba gratuita. 404 produce ausencia controlada.

Operaciones auxiliares de investigación, sin recorrido de producto implementado para ejecutarlas: POST /v1/payments/{id}/refunds (reembolso), POST /v1/card_tokens (tarjeta ficticia), POST /v1/payments, GET /v1/payments/search y GET /users/me (diagnóstico de identidad). No convertir los scripts temporales en API de producto ni trasladar datos de tarjeta a este repositorio.

4. Contratos mínimos y ejemplos

Plan y suscripción: recursos distintos

El template usa auto_recurring con moneda, monto, frecuencia mensual y free_trial opcional (frequency y frequency_type, en días o meses). Crear retorna el ID; leer o actualizar mapea {id,status,reason,externalReference,amountCents,currency,trial}, con términos anulables cuando no están disponibles. Los detalles de suscripción normalizan {id,status,externalReference,preapprovalPlanId}. Ambos IDs deben persistirse por separado.

Checkout de academia sin tarjeta previa

// POST /preapproval — synthetic data; illustrative amount
{
  "reason": "Academia de ejemplo",
  "external_reference": "example:academy:checkout-reservation-001",
  "payer_email": "buyer@example.com",
  "back_url": "https://example.com/subscriptions/return",
  "status": "pending",
  "auto_recurring": {
    "currency_id": "ARS",
    "frequency": 1,
    "frequency_type": "months",
    "transaction_amount": 1000
  }
}
// Minimum response: {"id":"<subscription-id>","init_point":"<https-checkout-url>"}

El monto local está en centavos: amountCents / 100 al enviar al proveedor. Las condiciones se congelan al reservar el checkout. Esta variante omite card_token_id y preapproval_plan_id; la tarjeta se elige en el checkout hospedado. El flujo clásico sigue enviando preapproval_plan_id, reason, payer_email, external_reference, back_url y status=pending. No generalizar la prueba real de academia como validación nueva de todos los planes clásicos.

Facturas y pagos normalizados

// AuthorizedPayment: required identity; remaining fields nullable
{
  id: "<invoice-id>",
  preapprovalId: "<subscription-id>",
  currencyId: "ARS",
  transactionAmount: 1000,
  debitDate: "<scheduled-cycle-date>",
  lastModified: "<provider-modification-date>",
  status: "processed",
  paymentId: "<payment-id>",
  paymentStatus: "approved",
  paymentStatusDetail: "accredited"
}
// Payment: required identity; remaining fields nullable
{
  id: "<payment-id>", collectorId: "<seller-id>",
  status: "refunded", statusDetail: "<provider-detail>",
  lastModified: "<date_last_updated>"
}

La factura mapea currency_id, debit_date, last_modified, preapproval_id, transaction_amount y payment.{id,status,status_detail}. El pago mapea collector_id, date_last_updated, id, status y status_detail. Los IDs numéricos utilizables se normalizan a strings. Una factura sin ID utilizable invalida la lectura completa; no inventar su identidad ni descartar silenciosamente esa cuota.

Los estados scheduled, processed y recycling de la factura describen procesamiento, no equivalen al estado del pago. Los DTO internos del gateway son privados; no devolver credenciales, payloads completos, correo ni IDs de pago al miembro.

5. Webhooks: autenticidad y procesamiento

TuTribu recibe POST https://www.tutribu.app/api/mercado-pago/webhooks. Configurar el destino canónico HTTPS directamente, evitando redirecciones de dominio o una portada. En un nuevo proyecto, registrar su propio destino y secreto en la aplicación emisora, separando prueba y producción.

Headers: x-signature: ts=<timestamp>,v1=<hex-hmac> y x-request-id. El verificador utiliza HMAC-SHA256, comparación de buffers con timingSafeEqual y el siguiente manifiesto; normaliza el ID con trim().toLowerCase().

id:<resource-id>;request-id:<x-request-id>;ts:<timestamp>;

La política local acepta timestamps en segundos o milisegundos y una tolerancia de cinco minutos. Es una política de TuTribu; comprobar compatibilidad con los reintentos del proveedor en cada implementación. Extraer tema e ID de la notificación de forma consistente con la firma; consultar la resolución exacta en app/api/mercado-pago/webhooks/route.ts.

Enrutamiento de notificaciones
TemaAcción confiable
payment / payment.*Resolver pago ya conocido por el ledger y consultar pago más factura con el token del vendedor. Un pago desconocido no se asocia por suposición.
subscription_authorized_payment*Consultar factura e historial para reconciliar cobertura; la notificación puede omitir user_id.
subscription_preapproval*Sincronizar recurrencia; reconciliación de academia adicional de mejor esfuerzo, con error registrado si falla.
subscription_preapproval_plan*Sincronizar template. Evaluar esta rama antes que el prefijo general de suscripciones.

user_id es contexto opcional, no autorización. La firma autentica la señal; la consulta al proveedor y el vínculo local determinan su pertenencia. Comparar integración, tribu, suscripción, factura, pago y vendedor antes de aplicar cambios.

Respuesta pública: 400 si faltan tema o recurso; 401 si la firma es inválida o antigua; 200 con {"status":"processed"} para resultados atendidos o ignorados y duplicate_webhook cuando corresponde a duplicación del flujo clásico; 503 ante resultados reintentables; 500 ante fallos inesperados, con mensaje seguro en español. Un 200 no demuestra que se haya otorgado acceso. El detalle del resultado permanece en logs seguros y almacenamiento local.

6. Consistencia, errores e idempotencia

Creación ambigua

Reservar la operación en PostgreSQL antes de pedir el checkout, con referencia e idempotency key estables. El adapter actual desactiva reintentos automáticos específicamente para la creación pendiente de academia; otras operaciones mantienen la configuración compartida de hasta un reintento, espera de 100 ms y timeout de 5000 ms. No asumir que toda escritura POST tiene la misma protección.

Ante timeout o respuesta ambigua, conservar la reserva y recuperar con /preapproval/search?q=…. Se observó que external_reference no filtraba correctamente esa búsqueda; q funcionó. Exigir un resultado único, referencia exacta y detalle consistente con checkout pendiente reutilizable. Una búsqueda fallida no demuestra ausencia del recurso. El resultado local checkout_unresolved devuelve 409 y evita crear una segunda suscripción. Rechazos definitivos 400/401/403/404/422 permiten liberar la reserva según el caso de uso.

Historial completo

Solicitar páginas de 12, avanzar el offset por la cantidad original de filas y contrastar paging.total. Fallar ante una página vacía antes de completar el total, más de 50 páginas o cualquier fila sin identidad utilizable. Se observaron HTTP 400 con límites 20 y 50, y 200 con 12; eso no demuestra un máximo universal del proveedor. No devolver historia parcial como completa ni suponer orden global o timestamps estrictamente crecientes.

Reembolsos y acceso

En las pruebas auxiliares, el reembolso se solicita al pago, no al ID de factura: POST /v1/payments/{paymentId}/refunds con token del vendedor e idempotency key. Un amount indica devolución parcial; omitirlo solicita devolución total. Leer el recurso resultante y volver a consultar el pago; el éxito de la solicitud no sustituye la reconciliación de acceso. El importe está expresado en unidades de moneda, no centavos. No hay botón ni endpoint propio de producto para emitir reembolsos en este trabajo.

Se observó /v1/payments.status=refunded mientras la factura seguía mostrando payment.status=approved. Combinar ambas lecturas: reembolso total y contracargo prevalecen sobre aprobación retrasada; un reembolso parcial queda en revisión. Conservar monto, moneda y fecha programada de la factura; usar la fecha de modificación válida más reciente. No resucitar un grant revocado con una aprobación vieja.

Las llamadas HTTP ocurren fuera de los locks de PostgreSQL. Ledger, grant y auditoría se actualizan transaccionalmente. Los rechazos no extienden cobertura ni eliminan períodos ya acreditados. Cancelar renovación conserva el período pago; reembolsar una cuota revoca el grant correspondiente, sin eliminar la membresía básica.

Cancelación y diagnóstico

Enviar cancelled al proveedor; el dominio local usa canceled. Se observó 400 al enviar la grafía local y 200 con la grafía del proveedor. Una repetición con 400 cuenta como cancelación exitosa solamente si una nueva consulta confirma el estado cancelado.

Separar errores definitivos, transitorios y resultados ambiguos. Registrar operación, correlación, HTTP status y metadatos mínimos sanitizados. Nunca registrar token, header de autorización, cookie, tarjeta, connection string o payload íntegro. Un 404 de lectura no implica éxito de reconciliación de una identidad ya conocida.

Las rutas propias requieren sesión y autorización local; no son endpoints de Mercado Pago. Los contratos ejecutables están en src/modules/product-access/infrastructure/api/academy-request-schemas.ts y src/modules/product-access/application/results/academy-public-dto-schemas.ts. Consultarlos antes de crear otro cliente.

Checkout puede devolver 409 (offer_changed, sales_closed, checkout_unresolved, already_subscribed, covered), 422 (not_eligible), 503 (provider_unavailable), y 400/403/404 según input, autorización o ausencia. El cliente debe mostrar el mensaje seguro y recuperar según el estado; no repetir un POST ciegamente.

El DTO de acceso permite accessModel, level, eligibility, renewalStatus, accessEndsAt, firstActivatedAt, hasBonusCoverage, hasPaidCoverage, isLeaderPreview, canStartCheckout y nextAction. Ver las uniones exactas en el esquema. Los endpoints administrativos de planes, activación, disponibilidad y bonificaciones, sus permisos y el almacenamiento se documentan en las dos decisiones arquitectónicas enlazadas; no son contratos reutilizables del proveedor.

9. Preparación para otro proyecto

  1. Crear su propia aplicación y destinos HTTPS; registrar callback, retorno y temas webhook. No copiar secretos, IDs de cuentas ni URLs de TuTribu.
  2. Definir quién cobra y quién puede autorizar una integración. Separar sesión, autorización OAuth y permisos de venta propios del producto.
  3. Modelar suscripción, factura y pago como identidades distintas; persistir cuenta propietaria, referencia estable, reserva de checkout, ledger, grants y auditoría.
  4. Implementar renovación de tokens, protección OAuth con caducidad y uso único, firma webhook y lectura autenticada de recursos con el vendedor correcto.
  5. Elegir reglas propias de acceso: cobertura, cancelación, rechazo, reembolso parcial, total y contracargo. No heredar permisos de academia o Fogón sin decisión de producto.
  6. Usar migraciones versionadas y políticas RLS simples; probar efectos reales en una base efímera, sin ejecutar diagnósticos destructivos en producción.
  7. Probar doble clic, concurrencia, timeout tras envío, recuperación exacta, páginas incompletas, recursos temporalmente ausentes, eventos duplicados y fuera de orden, firma inválida y cuenta incorrecta.
  8. Completar los tres pendientes externos: reintento real de la misma cuota, entrega automática original de webhook y un historial real que abarque varias páginas. Revalidar documentación oficial, límites y sandbox antes de lanzar.
  9. Limpiar recursos propios: cancelar recurrencias confirmadas, reembolsar cobros ficticios cuando corresponda, eliminar bases temporales y destruir credenciales temporales. Conservar referencias de operaciones ambiguas para seguimiento, sin secretos.

10. Fuentes oficiales y mantenimiento

  • Crear y refrescar tokens OAuth y Flujo OAuth.
  • Crear suscripción y Suscripciones pendientes sin plan asociado.
  • Consultar factura y Buscar facturas.
  • Consultar pago y Administrar suscripciones.
  • Configurar y verificar webhooks.
  • Tarjetas de prueba y Prueba de aprobación de suscripciones.

Las referencias oficiales definen contratos del proveedor; las observaciones de esta página describen lo comprobado en este proyecto y no garantizan comportamiento universal. Al cambiar endpoints, campos utilizados, estados, estrategias de recuperación o configuración, actualizar esta referencia junto con la decisión arquitectónica y los tests afectados.
