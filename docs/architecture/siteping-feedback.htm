SitePing feedback
Integracion del widget visual, persistencia propia y publicacion automatica en GitHub.
Scope: FeedbackStatus: Active
01
Decision vigente

LaTribu usa @siteping/widget para la experiencia visual, pero no usa Prisma ni el CLI de SitePing. El backend vive en src/modules/siteping para mantener Drizzle, Neon Postgres, Better Auth y la arquitectura hexagonal del repo.

El paquete del widget se instala desde el registry de npm. Si el paquete requiere autenticacion, GitHub Actions debe exponer un secret NPM_TOKEN con acceso de lectura para que pnpm install --frozen-lockfile pueda resolver la dependencia antes de ejecutar el gate.

El endpoint principal es /api/siteping. La identidad y el permiso del widget se resuelven en /api/siteping/identity.

Los contratos de dominio y aplicacion son propios de LaTribu. Los DTOs de @siteping/widget solo pueden aparecer en el borde visual o de entrada HTTP, y deben mapearse a tipos internos antes de cruzar hacia application o domain.

02
Acceso

El widget no es publico. Se habilita solo cuando:

  • SITEPING_ENABLED esta activo.
  • Better Auth resuelve una sesion valida.
  • El usuario tiene al menos una membresia activa como leader o guardian, o su email esta incluido en SITEPING_ALLOWED_EMAILS.

Cuando SITEPING_ENABLED esta apagado, el layout no monta el provider del widget y /api/siteping/identity devuelve enabled: false antes de resolver modulos, sesion o membresias.

La base tambien aplica RLS con un modelo de ownership estricto: cada usuario solo puede ver, actualizar y borrar el feedback que creo. Todas las operaciones del panel (listado, cambio de estado y borrado) corren bajo el contexto del usuario autenticado y quedan atadas a la policy base created_by = current_app_user_id(). No existe un contexto de administrador de proyecto: la maquinaria app.siteping_project_admin/app.siteping_project_name y las funciones is_siteping_project_admin/current_siteping_project_name fueron eliminadas en 20260604120000_remove_siteping_project_admin_management, de modo que un usuario autorizado nunca puede gestionar feedback ajeno.

Las mutaciones individuales del panel siempre combinan feedbackId con el projectName autorizado por /api/siteping/identity; no aceptan el proyecto enviado por el cliente ni dependen de que el identificador sea globalmente unico entre proyectos. Si el feedbackId no pertenece al usuario, la RLS no expone ninguna fila: el borrado individual es un no-op y el cambio de estado responde 404, sin filtrar la existencia del registro.

03
Datos capturados

La captura de v1 combina feedback base con diagnosticos tecnicos y mantiene screenshots desactivados.

  • Se guarda texto, tipo, URL, viewport, user agent, autor, clientId y anclas DOM.
  • Se guarda diagnostics como jsonb con consola reciente y requests fallidos.
  • En los diagnosticos de red, method se limita a verbos HTTP conocidos y cualquier valor desconocido se reemplaza por [redacted] antes de persistirse.
  • enableScreenshot queda en false. Si llega screenshotDataUrl, se ignora y no se persiste.
Privacidad: los diagnosticos y las anclas DOM pueden contener datos sensibles si el frontend captura texto cercano a tokens, cookies o secretos. Por eso se redactan cookies, tokens, secretos y parametros sensibles en mensajes, diagnosticos, URL, user agent y texto de anotaciones antes de persistirlos o publicarlos en GitHub.
04
GitHub issues

Cada feedback nuevo publica una issue en SITEPING_GITHUB_REPOSITORY, por defecto guidomodarelli/LaTribu. La idempotencia vive en la combinacion project_name, created_by y client_id, asi que una repeticion del mismo envio del mismo usuario no crea otra issue sin bloquear envios de otros usuarios o proyectos.

La creacion usa ON CONFLICT DO NOTHING sobre esa clave para que dos envios concurrentes con el mismo clientId no aborten la transaccion perdedora. Si el insert no devuelve fila, el adapter vuelve a leer el feedback existente y conserva el camino idempotente.

La issue incluye mensaje, tipo, URL redactada, deep link ?siteping=<feedbackId>, viewport, user agent, autor y resumen redactado de diagnosticos. El titulo se resume para respetar el limite de GitHub, pero el mensaje completo queda en el body. No incluye screenshots, cookies, tokens, query params sensibles, stack traces completos ni payloads raw de proveedores.

Las llamadas a GitHub usan fetchWithResilience para aplicar timeout bounded. La creacion de issues no reintenta respuestas retryable porque POST /issues no es idempotente: si GitHub crea la issue pero la respuesta se pierde o vuelve como 5xx, un retry podria duplicar la publicacion antes de que LaTribu marque el feedback como publicado. Las operaciones posteriores mantienen el retry corto compartido cuando el riesgo de duplicacion no afecta la creacion principal.

Si la creacion de la issue en GitHub falla, el feedback queda guardado y se marca github_issue_status = failed para permitir reintentos operativos posteriores. Si GitHub ya creo la issue pero falla la persistencia local de issueUrl o issueNumber, LaTribu no sobrescribe el estado como failed; el feedback queda pendiente para evitar que un reintento operativo cree una issue duplicada.

Cuando el dueño elimina uno de sus feedback desde el panel, LaTribu marca primero el registro local con github_issue_status = deletion_pending, lo oculta de los listados del panel y despues comenta/cierra la issue vinculada. Si el cierre de GitHub falla, intenta restaurar published para que el feedback vuelva a quedar disponible. Cuando GitHub confirma el cierre, marca deletion_completed antes del DELETE final; si ese borrado local falla por una caida transitoria de base de datos, el siguiente retry solo reintenta el borrado local y no vuelve a comentar/cerrar la issue. El publisher tambien evita duplicar el comentario de eliminacion si GitHub ya lo tiene. No existe una accion de borrado masivo: el borrado es siempre individual y acotado al feedback propio por RLS.

Si el dueño intenta resolver o reabrir un feedback que ya fue eliminado o que no pertenece al projectName autorizado, el endpoint responde 404 con un mensaje estable en lugar de registrar un error inesperado. Esto mantiene los casos de UI stale y concurrencia fuera del camino de server-error.
