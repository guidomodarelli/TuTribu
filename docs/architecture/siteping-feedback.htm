01
Decision vigente

TuTribu consume @beezping/widget@0.12.0 publicado en npm. La configuración se obtiene de /api/siteping/identity, se valida como DTO público propio y el widget se inicializa con initBeezping después de la hidratación. Solo se monta si el servidor habilita el acceso y entrega una identidad. El request se cancela al desmontar; los errores muestran feedback seguro en español con reintento para la lectura de identidad.

El backend sigue perteneciendo a src/modules/siteping, con los mismos puertos, tablas, rutas /api/siteping, configuración SITEPING_* y políticas de ownership. No se usa el backend de la librería ni se ejecutan migraciones de base de datos. El listado declara capabilities.comments: false y permissions.canDeleteAll: false: TuTribu no ofrece conversaciones por hilo ni borrado masivo.

Beezping administra su host <beezping-widget>, las superficies data-beezping-ignore, el aislamiento de foco y eventos frente a modales, el cierre de formularios al cancelar y la posición dentro del viewport. TuTribu no instala guards que dupliquen esas funciones ni intercepta Storage.prototype.setItem. La cola beezping_retry_queue queda bajo la política nativa de reintentos y cuota de la librería.

La única personalización visual del host coloca las instrucciones de anotación debajo de un diálogo de TuTribu abierto, para dejar libre su encabezado. Beezping calcula el área disponible a partir de la posición real de esa toolbar. La hoja siteping-overlay.scss usa el marcador nuevo, el z-index y el anclaje de la toolbar; excluye los formularios con role="dialog" y no modifica las superficies de dibujo.

La dependencia está fijada a 0.12.0; el lockfile consume npm, sin paquetes locales. La excepción de edad mínima de publicación se limita a @beezping/widget@0.12.0. La captura usa directamente la dependencia html2canvas-pro del widget, sin el alias y override anterior de TuTribu.

La prueba E2E del widget (tests/e2e/beezping-provider.spec.ts) no forma parte de pnpm test:e2e: el servidor web de esa suite (dev:next) no activa SITEPING_ENABLED, asi que el layout no monta el provider. Se ejecuta aparte con pnpm test:e2e:beezping (playwright.beezping.config.ts), que recorre Chromium y WebKit en escritorio y mobile contra https://dev-tutribu.app; requiere el servidor levantado con pnpm run dev y SITEPING_ENABLED activo.

02
Acceso

El widget no es publico. Se habilita solo cuando:

  • SITEPING_ENABLED esta activo.
  • Better Auth resuelve una sesion valida.
  • El usuario tiene al menos una membresia activa como leader o guardian, o su email esta incluido en SITEPING_ALLOWED_EMAILS.

Cuando SITEPING_ENABLED esta apagado, el layout no monta el provider del widget y /api/siteping/identity devuelve enabled: false antes de resolver modulos, sesion o membresias.

La base tambien aplica RLS con un modelo de ownership estricto: cada usuario solo puede ver, actualizar y borrar el feedback que creo. Todas las operaciones del panel (listado, cambio de estado y borrado) corren bajo el contexto del usuario autenticado y quedan atadas a la policy base created_by = current_app_user_id(). No existe un contexto de administrador de proyecto: la maquinaria app.siteping_project_admin/app.siteping_project_name y las funciones is_siteping_project_admin/current_siteping_project_name fueron eliminadas en 20260604120000_remove_siteping_project_admin_management, de modo que un usuario autorizado nunca puede gestionar feedback ajeno.

Las mutaciones individuales del panel siempre combinan feedbackId con el projectName autorizado por /api/siteping/identity; no aceptan el proyecto enviado por el cliente ni dependen de que el identificador sea globalmente unico entre proyectos. Si el feedbackId no pertenece al usuario, la RLS no expone ninguna fila: el borrado individual es un no-op y el cambio de estado responde 404, sin filtrar la existencia del registro.

03
Datos capturados

La captura combina feedback base, diagnosticos tecnicos y un screenshot del area anotada.

  • Se guarda texto, tipo, URL, viewport, user agent, autor, clientId y anclas DOM.
  • Se guarda diagnostics como jsonb con consola reciente y requests fallidos.
  • En los diagnosticos de red, method se limita a verbos HTTP conocidos y cualquier valor desconocido se reemplaza por [redacted] antes de persistirse.
  • enableScreenshot esta en true: Beezping captura el area anotada como JPEG (via html2canvas, import dinamico) y la envia como screenshotDataUrl (data URL base64).
  • El endpoint POST /api/siteping valida el screenshot antes de procesarlo: solo acepta un data URL data:image/...;base64, dentro de un tope de tamaño (2_000_000 chars); si no cumple, lo descarta y el feedback igual se guarda sin imagen.
  • El screenshot se sube server-side a Cloudflare Images (mismo proyecto/credenciales que las imagenes del feed) via el port SitepingScreenshotStorage y su adaptador CloudflareImagesSitepingScreenshotStorage: el use case decodifica el base64, hace POST images/v1 y persiste en screenshot_url la URL publica imagedelivery.net. El panel y el issue de GitHub la renderizan como imagen.
  • El use case crea primero la fila durable sin screenshot (screenshot_url en null) y recien despues sube la imagen y la vincula con attachScreenshotUrl. El orden importa: subir antes de que exista la fila dejaria una imagen publica sin ninguna fila que dispare su cleanup ante una falla de insert, y un delete best-effort que vuelve con screenshotCleared: false (timeout, auth 4xx/5xx) nunca podria reclamarla. Antes de todo, consulta la idempotencia (findByIdempotencyKey sobre project_name, created_by y client_id) y corta sin crear fila ni subir cuando el envio ya existe: una repeticion del mismo clientId (por ejemplo tras un timeout del cliente) reutiliza el feedback existente sin volver a subir ni pagar la latencia. El ON CONFLICT DO NOTHING sigue cubriendo la carrera concurrente residual entre el pre-check y el insert: si dos envios con el mismo clientId pasan el pre-check a la vez, ambos crean su fila pero solo uno gana el insert; el perdedor recibe wasCreated: false y, como todavia no subio nada, no hay imagen que reclamar y el ganador conserva su propio screenshot. Lo mismo aplica cuando create lanza (error transitorio de base de datos, falla de RLS o falla al insertar las anotaciones): no se subio ningun screenshot, asi que no hay huerfano y el error se propaga directo. La ventana residual es un upload que sale ok pero cuyo attachScreenshotUrl no persiste el link: ahi la fila ya es durable pero quedo con screenshot_url en null, asi que el screenshot se reclama best-effort con delete, quedando el feedback sin imagen. Ese link no persiste en dos casos: que el attachScreenshotUrl lance, o que no matchee ninguna fila porque el feedback fue borrado entre el create y el link (o dejo de ser visible para el owner bajo RLS). El segundo caso es sutil: el UPDATE resuelve sin error aunque afecte cero filas, asi que attachScreenshotUrl usa returning para informar si toco una fila (screenshotAttached); sin ese chequeo el use case trataria el screenshot como adjunto y publicaria una issue de GitHub con una delivery URL que ninguna fila referencia, dejando una imagen publica sin nada que dispare su cleanup. Por eso, ante screenshotAttached: false tambien se reclama la imagen y se descarta el screenshot. En ambos casos ese reclaim no se descarta: si delete vuelve con screenshotCleared: false (auth, 4xx/5xx, timeout o error de red) el huerfano puede seguir vivo y, como el link nunca persistio la delivery URL en la fila, no hay registro que dispare un retry; por eso el use case emite un log estructurado de nivel warn (via el logger inyectado, con feedbackId y la delivery URL publica) para que el huerfano se pueda reclamar manualmente en vez de tirarlo en silencio. Esa ventana es muchisimo mas angosta que subir antes de que exista cualquier fila.
  • El upload reutiliza el config compartido shared/infrastructure/cloudflare/cloudflare-images-config.ts (CLOUDFLARE_ACCOUNT_ID, CLOUDFLARE_IMAGES_API_TOKEN, CLOUDFLARE_IMAGES_ACCOUNT_HASH, CLOUDFLARE_IMAGES_DELIVERY_VARIANT), con timeout acotado y sin retry (un POST crea imagen y un retry duplicaria). Si Cloudflare no esta configurado o el upload falla, no se persiste screenshot (screenshot_url queda en null): se descarta la captura en vez de inlinear el data URL de varios MB en la columna, porque GET /api/siteping serializa screenshotUrl para cada feedback de la pagina (hasta 100) y un payload inline inflaria la respuesta del panel a cientos de MB.
  • Como el POST images/v1 no es idempotente, el adaptador reserva el id de la imagen antes de subir: genera un identificador propio (un UUID aleatorio con los guiones removidos: 32 caracteres hex, inyectable para tests) y lo manda en el campo multipart id, de modo que la delivery URL queda determinada de antemano. El identificador no debe estar en formato UUID: Cloudflare reserva ese formato para los id que el mismo autogenera y rechaza un custom id con esa forma (Custom ID is not valid: Must not be UUID), por eso se le quitan los guiones a un crypto.randomUUID() en vez de mandarlo crudo —un UUID crudo seria rechazado y descartaria todos los screenshots silenciosamente. Esto es clave porque Cloudflare puede recibir el multipart completo y tardar mas que el timeout en responder: cuando eso pasa, abortar el fetch y tratar la respuesta perdida como un no-op seguro dejaria una imagen publica creada server-side sin ninguna fila en base que dispare su cleanup. Con el id reservado, todo desenlace genuinamente no confirmado del upload —timeout, abort o error de red; un status 5xx de servidor; o una respuesta ok cuyo body no se puede leer, sea porque es no-JSON malformado o porque el stream del body se estanca— dispara un DELETE best-effort de ese id para reclamar el posible huerfano. En cambio, un rechazo confirmado del upload con status 4xx (credenciales invalidas 401/403 o un error de validacion) significa que Cloudflare rechazo el request y nunca creo la imagen: no hay huerfano que reclamar, asi que el adaptador descarta el screenshot devolviendo null sin emitir el DELETE de reclaim. Reclamar en ese caso reusaria las mismas credenciales que ya fallan y podria persistir una delivery URL reservada para una imagen inexistente, que luego bloquearia el borrado del feedback hasta arreglar las credenciales. El timeout del fetch solo cubre la recepcion de los headers y se libera apenas la respuesta llega, asi que la lectura del body se acota con su propio timeout (el mismo presupuesto del upload via readJsonWithTimeout): Cloudflare puede mandar los headers y despues colgar el stream del body, y sin ese limite un response.json() crudo colgaria indefinidamente la creacion del feedback en vez de caer al fallback sin screenshot. Como el id es aleatorio nunca colisiona con una imagen valida preexistente, asi que ese reclaim solo puede borrar la imagen que este mismo request creo. El resultado de ese reclaim no se descarta: si el DELETE confirma que el huerfano esta limpio el adaptador devuelve null y no se persiste screenshot; pero si el reclaim no puede confirmar la limpieza (auth, 4xx/5xx, timeout o error de red) el upload pudo haberse completado en Cloudflare y dejado una imagen publica viva, asi que devuelve la delivery URL reservada para persistirla en screenshot_url. Que cuenta como confirmacion depende del origen del reclaim: un DELETE con respuesta ok siempre confirma, pero un 404 solo confirma cuando la imagen ya pudo haberse creado antes del delete (un reclaim tras un upload con respuesta —un 5xx—). Para un reclaim tras un upload abortado (timeout/abort, sin respuesta) la creacion no idempotente puede seguir corriendo en Cloudflare y un DELETE rapido puede adelantarse a esa creacion y dar 404 antes de que la imagen aparezca; ese 404 entonces no se trata como confirmacion (el adaptador pasa treatNotFoundAsCleared: false) y se conserva la delivery URL reservada para reclamarla mas tarde. Asi la fila de feedback queda como unico registro de esa URL y un retry de borrado posterior puede reclamar el huerfano, en vez de tirar la referencia y dejar una imagen publica irrecuperable sin fila que dispare su cleanup. Solo una respuesta ok con success: true persiste screenshot_url como upload confirmado, construida a partir del id reservado (no del eco del body).
  • El publisher de GitHub embebe la imagen con ![Screenshot](url) solo cuando la URL es publica (https); como ya no se persisten data URLs inline, un screenshot sin URL durable simplemente no se embebe.
  • El port SitepingScreenshotStorage tambien expone delete, y su adaptador clasifica la URL guardada con classifyCloudflareImagesDeliveryUrl (inverso de buildCloudflareImagesDeliveryUrl) en tres casos antes de hacer DELETE images/v1/{id}. Nunca lanza: en vez de eso devuelve { screenshotCleared } para que el caller decida si puede borrar la fila. Reporta screenshotCleared: true (la imagen esta confirmadamente borrada) cuando la respuesta del DELETE es ok, cuando es 404 (ya no existe), o cuando el valor no es una delivery URL de Cloudflare Images (clasificacion not-delivery: un data URL inline heredado de filas viejas, o una URL en un host que la app nunca escribe) y por ende no hay imagen remota propia que borrar. Esta clasificacion not-delivery se evalua con isCloudflareImagesDeliveryUrl (chequeo de host, independiente del account hash) antes de requerir el entorno de Cloudflare, asi que un valor no-delivery reporta true incluso cuando faltan credenciales: una fila vieja con screenshot inline (o cualquier URL no-delivery) no debe quedar atrapada para siempre solo porque el storage esta sin configurar. Reporta screenshotCleared: false (la imagen podria seguir existiendo) cuando faltan credenciales pero la URL si esta en el host imagedelivery.net, cuando hay timeout o error de red, cuando el status no es ok ni 404 (por ejemplo un error de auth 4xx o un 5xx), o cuando la URL esta en el host imagedelivery.net pero con un account hash distinto al configurado (clasificacion foreign-account). Como esta app es la unica fuente de las screenshot URLs persistidas, un host de Cloudflare con hash distinto no es una URL ajena sino una rotacion del account hash o un typo de env: la imagen publica es probablemente un huerfano real que las credenciales actuales no pueden confirmar borrado, asi que el adaptador no llama a Cloudflare y conserva la fila —el unico registro de la delivery URL— para reintentar cuando el account hash se realinee, en vez de borrar la fila y orfanar el screenshot en silencio. En todos los casos false el caller debe conservar la fila para reintentar el borrado mas tarde en vez de dejar un huerfano sin disparador para reclamarlo. El 404 se trata como confirmacion salvo que el caller pase treatNotFoundAsCleared: false: ese opt-out lo usa el use case de borrado para una delivery URL reservada cuyo upload nunca se confirmo y cuyo feedback se elimina dentro de la ventana de carrera del upload (ver seccion GitHub issues), porque ahi un 404 puede ser el DELETE adelantandose a una creacion que todavia no aterrizo. Un DELETE con respuesta ok confirma el borrado sin importar ese flag.
Privacidad: el screenshot embebe el contenido visible del area anotada y se persiste tal cual, sin enmascarar. Es una decision explicita de producto para esta tribu. Si en el futuro se anotan zonas con datos sensibles (tokens, formularios de pago), marcar esos elementos con data-beezping-ignore="true" para que la captura de @beezping/widget los enmascare; el marcador anterior data-siteping-ignore ya no tiene efecto y debe migrarse. El texto (mensajes, diagnosticos, URL, user agent, anclas) sigue redactando cookies, tokens, secretos y parametros sensibles antes de persistirse o publicarse en GitHub.
04
GitHub issues

Cada feedback nuevo publica una issue en SITEPING_GITHUB_REPOSITORY, por defecto guidomodarelli/LaTribu. La idempotencia vive en la combinacion project_name, created_by y client_id, asi que una repeticion del mismo envio del mismo usuario no crea otra issue sin bloquear envios de otros usuarios o proyectos.

La creacion usa ON CONFLICT DO NOTHING sobre esa clave para que dos envios concurrentes con el mismo clientId no aborten la transaccion perdedora. Si el insert no devuelve fila, el adapter vuelve a leer el feedback existente y conserva el camino idempotente.

La issue incluye mensaje, tipo, URL redactada, deep link ?siteping=<feedbackId>, viewport, user agent, autor y resumen redactado de diagnosticos. El titulo se resume para respetar el limite de GitHub, pero el mensaje completo queda en el body. No incluye screenshots, cookies, tokens, query params sensibles, stack traces completos ni payloads raw de proveedores.

Las llamadas a GitHub usan fetchWithResilience para aplicar timeout bounded. La creacion de issues no reintenta respuestas retryable porque POST /issues no es idempotente: si GitHub crea la issue pero la respuesta se pierde o vuelve como 5xx, un retry podria duplicar la publicacion antes de que LaTribu marque el feedback como publicado. Las operaciones posteriores mantienen el retry corto compartido cuando el riesgo de duplicacion no afecta la creacion principal.

Si la creacion de la issue en GitHub falla, el feedback queda guardado y se marca github_issue_status = failed para permitir reintentos operativos posteriores. Si GitHub ya creo la issue pero falla la persistencia local de issueUrl o issueNumber, LaTribu no sobrescribe el estado como failed; el feedback queda pendiente para evitar que un reintento operativo cree una issue duplicada.

Cuando el dueño elimina uno de sus feedback desde el panel, el flujo depende de si el feedback tiene una issue de GitHub vinculada. Tanto deletion_pending como deletion_completed ocultan la fila de los listados del panel (findPage los excluye). El borrado coordina dos acciones irreversibles —cerrar la issue de GitHub (el publisher no expone reopen) y borrar el screenshot durable de Cloudflare Images— y el invariante rector es que ninguna accion irreversible debe correr antes de confirmar la otra de forma que destruya parte de un feedback que sigue vivo. En particular, el borrado del screenshot nunca debe correr antes de confirmar el cierre de la issue: una falla de cierre es comun y transitoria (timeout o 5xx de GitHub), y si el screenshot ya se borro, el feedback no eliminado quedaria visible apuntando a un screenshot_url muerto mientras su issue, todavia abierta, embebe una imagen rota.

Feedback con issue vinculada: el use case primero oculta la fila marcando github_issue_status = deletion_pending, despues comenta/cierra la issue, y recien con el cierre confirmado (deletion_completed) borra el screenshot durable via SitepingScreenshotStorage.delete (cuando hay screenshot_url) antes de correr el DELETE local. Diferir el borrado irreversible del screenshot hasta despues del cierre confirmado evita el modo de falla principal: si el cierre de GitHub falla, el use case restaura published y re-lanza con el screenshot intacto, asi que el feedback vuelve a quedar visible y reintetable sin ninguna imagen rota ni en el panel ni en la issue abierta. Como un cierre confirmado deja la fila en deletion_completed (oculta de los listados), diferir el clear hasta ese punto tampoco reintroduce el desync inverso: un clear no confirmado despues del cierre confirmado lanza con la fila oculta en deletion_completed —nunca restaurada a un estado visible—, de modo que una issue cerrada jamas queda emparejada con una fila visible. La rama de deletion_completed reintenta el clear idempotente + el DELETE local en un intento posterior. El retry es seguro: el PATCH state=closed es idempotente, el comentario de eliminacion solo se publica si todavia no existe, y el borrado del screenshot es idempotente (un 404 cuenta como ya borrado), asi que reintentar el clear de una imagen ya borrada tambien es seguro.

El costo de diferir es acotado: si el cierre confirma pero el clear queda permanentemente no confirmado (por ejemplo storage sin credenciales), la fila queda en deletion_completed (oculta) conservando un screenshot_url vivo. Eso no es un huerfano irrecuperable —la fila sigue referenciando la delivery URL, asi que el clear idempotente puede reclamarla en un retry— y es estrictamente menos dañino que la perdida irreversible del screenshot de un feedback vivo que provocaba el orden anterior (clear-first) ante una falla de cierre comun.

Feedback sin issue vinculada: no hay cierre de GitHub en dos fases que checkpointear, asi que la fila nunca se marca deletion_pending. El use case borra el screenshot mientras la fila sigue en su estado original listable y recien despues corre el DELETE local. Un clear no confirmado lanza con la fila intacta y visible, de modo que el flujo normal de panel/widget la sigue alcanzando para reintentar.

En ambos casos el DELETE local solo corre cuando delete confirma screenshotCleared: true; si la imagen no pudo borrarse de forma confirmada (faltan credenciales, respuesta de auth/4xx/5xx, o timeout), el use case lanza y conserva la fila —el unico registro de la delivery URL— para que un retry posterior reintente el borrado idempotente en vez de dejar un huerfano publico irrecuperable. Un borrado interrumpido es reintentable porque el siguiente intento recarga la fila por findById (que no filtra por estado) y vuelve a correr el borrado idempotente del screenshot; el orden inverso (borrar la fila primero) dejaria un huerfano sin disparador para reclamarlo. Para el feedback sin issue vinculada la fila permanece visible hasta el clear confirmado; para el feedback con issue vinculada, tras un cierre confirmado la fila queda en deletion_completed (oculta) y puede conservar transitoriamente un screenshot_url vivo hasta que la rama de deletion_completed reintente el clear idempotente y el borrado local —ese reintento no vuelve a comentar/cerrar la issue—. El publisher tambien evita duplicar el comentario de eliminacion si GitHub ya lo tiene. No existe una accion de borrado masivo: el borrado es siempre individual y acotado al feedback propio por RLS.

Ventana de carrera del upload (borrado vs. creacion todavia en vuelo): una delivery URL reservada que persistio un reclaim no confirmado puede apuntar a una imagen cuya creacion no idempotente seguia corriendo en Cloudflare cuando se abortó el upload. Si el feedback se elimina poco despues, el DELETE del screenshot puede adelantarse a esa creacion y dar 404 antes de que la imagen aparezca; tratar ese 404 como "ya borrado" eliminaria la unica fila que referencia una imagen publica a punto de existir y dejaria un huerfano sin disparador. Por eso el use case de borrado calcula treatNotFoundAsCleared a partir de la antiguedad de la fila: solo confia en un 404 como borrado confirmado cuando ya transcurrio SITEPING_SCREENSHOT_UPLOAD_RACE_WINDOW_MS (5 min, holgado sobre el timeout de upload de 5s mas la finalizacion de Cloudflare y el skew de reloj) desde created_at; dentro de esa ventana pasa treatNotFoundAsCleared: false, asi que un 404 reporta screenshotCleared: false, el clear lanza y la fila se conserva para reintentar una vez que la creacion seguro ya resolvio. La ventana se aplica a cualquier URL porque una imagen subida normalmente responde ok al DELETE (nunca 404) y se borra de inmediato: lo unico que la ventana difiere son los borrados de filas cuyo screenshot realmente da 404 a los pocos minutos de creado —el caso raro del reclaim no confirmado—, y nunca deja una fila permanentemente imborrable porque al vencer la ventana el 404 vuelve a contar como borrado.

Si el dueño intenta resolver o reabrir un feedback que ya fue eliminado o que no pertenece al projectName autorizado, el endpoint responde 404 con un mensaje estable en lugar de registrar un error inesperado. Esto mantiene los casos de UI stale y concurrencia fuera del camino de server-error.
