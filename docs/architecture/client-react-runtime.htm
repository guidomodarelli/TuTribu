ARCHITECTURE
Runtime de React en el navegador
Los componentes cliente corren sobre React; TanStack Redact se probo y se revirtio.
Scope: Frontend runtimeStatus: Reverted
01
Decision

TuTribu ejecuta los componentes cliente con React (react-dom), igual que el servidor. next.config.ts exporta nextConfig sin ningun wrapper que reemplace el runtime del navegador.

Hubo un intento de usar TanStack Redact (@tanstack/redact 0.2.0, con withRedact) como runtime de React solo en el navegador, para bajar el JavaScript de cada pagina. Se revirtio.

02
Por que se revirtio
  • Ahorro chico: medido en build de produccion, cada pagina bajaba unos 31 KB gzip (3,7 % a 4,9 % de unos 750 KB). Es el peso fijo del runtime; el resto del bundle es codigo propio y dependencias.
  • Roturas que los tests no ven: Redact pasa a los handlers el Event nativo, sin isPropagationStopped(), isDefaultPrevented() ni persist(). Radix RadioGroup, Checkbox, Switch y Select llaman a isPropagationStopped(), asi que el clic lanzaba un error y el control no cambiaba (por ejemplo, elegir «Lista de habilitados» en Reglas). Vitest corre con React, por lo que solo aparecia en el build de produccion.
  • Next.js atado a Redact: withRedact solo acepta las versiones de Next.js que soporta (en 0.2.0: 15.5 y 16.0 a 16.4); subir Next.js exigia esperar a Redact.
  • Render sincronico: sin time slicing, useTransition y useDeferredValue no bajan la prioridad del trabajo, y <Profiler> no ejecuta su callback.
Antes de volver a probar otro runtime de React en el navegador: verificar con pnpm run build y la app real los controles de Radix (radio, casilla, interruptor y lista desplegable), porque los tests de Vitest no cubren el runtime del bundle.
