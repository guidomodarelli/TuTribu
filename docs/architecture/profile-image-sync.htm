ARCHITECTURE
Sincronizacion de la imagen de perfil
Como se obtiene, persiste y refresca user.image desde Google.
Scope: AuthenticationStatus: Active
01
Origen y persistencia

La imagen de perfil proviene del claim picture del ID token de Google. Better Auth lo mapea al campo user.image en la tabla de autenticacion (src/modules/shared/infrastructure/database/schema.ts).

La escritura ocurre dentro del callback OAuth gracias a overrideUserInfoOnSignIn: true en el provider Google (src/modules/auth/infrastructure/better-auth/auth.ts). Es decir, solo se reescribe cuando el usuario atraviesa el flujo de inicio de sesion de Google.

La UI lee user.image sin caches intermedias. Por ejemplo, los miembros de la tribu salen de la funcion SQL public.list_visible_tribe_members_by_slug, que devuelve "user".image tal cual.

02
El problema: imagen congelada

La sesion de Better Auth usa los valores por defecto (expiracion 7 dias, refresco rotativo cada 1 dia). El refresco de sesion no vuelve a pedir el perfil a Google, por lo que la URL de picture queda congelada mientras la sesion siga viva.

Consecuencia: si un usuario cambia su foto en Google despues de iniciar sesion (caso tipico de una cuenta nueva que arranca con avatar por defecto), la URL nueva nunca llega a la base de datos hasta que el usuario rehace el login. La imagen mostrada queda desactualizada por dias.

03
Decision: refrescar al renovar sesion

Cuando Better Auth renueva la sesion se dispara el hook databaseHooks.session.update.after. Ese hook agenda, con after() de next/server (post-respuesta, sin bloquear), un refresco en background de la imagen del miembro.

El flujo respeta los limites hexagonales del modulo auth:

  • Dominio: puertos MemberProfileRepository y ExternalProfilePictureProvider.
  • Aplicacion: caso de uso refreshMemberProfileImage, que lee la imagen actual, pide la vigente y persiste solo si cambio.
  • Infraestructura: GoogleProfilePictureProvider (consulta el endpoint userinfo de Google), PostgresMemberProfileRepository (lee/actualiza user.image) y la composicion en infrastructure/composition/member-profile-image-refresh.ts.

Para obtener la picture vigente sin el usuario presente se usa auth.api.getAccessToken, que desencripta y refresca el access token con el refresh token guardado, y luego se llama al endpoint OpenID https://openidconnect.googleapis.com/v1/userinfo. Se prefiere userinfo sobre decodificar el id token de un refresh porque ese id token puede ser un valor viejo.

El UPDATE sobre user.image corre sin contexto RLS de request, igual que Better Auth al escribir la imagen en el sign-in. No requiere migracion SQL ni cambios de politicas.
04
Offline access y trade-offs

El refresco requiere un refresh token de Google. El provider esta configurado con accessType: "offline" y prompt: "consent" para garantizar que Google emita un refresh token tanto a usuarios nuevos como existentes.

prompt: "consent" muestra la pantalla de consentimiento de Google en cada inicio de sesion. Es el costo aceptado a cambio de cobertura completa del refresh token.
  • El refresco corre aproximadamente una vez por dia por usuario activo (cadencia de renovacion con updateAge por defecto).
  • Si getAccessToken responde sin accessToken, el refresco se omite sin actualizar la imagen. Si Better Auth falla al resolverlo, el caso de uso registra el fallo como failed para mantener observabilidad.
  • Los logs son estructurados y seguros: nunca se registran tokens ni la URL completa de la imagen, solo el host.
