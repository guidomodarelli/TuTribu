Se verifica el SDK instalado `@zavudev/sdk@0.57.0`: `messages.retrieve` ejecuta GET del ID puntual. La [documentación oficial de Zavu](https://www.zavu.dev/en/messaging-api) confirma esa superficie de consulta; no se requieren webhook, lista de historial o conversaciones para esta primera implementación.

El port privado `MessageStatusLookup` recibe referencias propias de intento/entrega/conexión, nunca datos elegidos por un browser. El adapter copia y congela esas referencias antes del await, exige coincidencia de preparación y sólo permite el GET al ID original. La credencial queda transitoria dentro de infraestructura y el transporte fija origen, sender, correlation, ausencia de body, redirects cerrados y maxRetries cero. La preparación real que autoriza storage/líder/versión/retirement sigue pendiente; la interfaz no acredita esa autoridad por sí misma.

La respuesta upstream sólo se estrecha por ID/direction/channel consumidos y discrimina status; no se valida un schema completo del proveedor. El resultado propio conserva outcome e ID original, sin destinatario, texto, sender o payload raw. Estados futuros conservan unknown. Una consulta no implica un nuevo POST, prueba de contacto, membresía ni liberación de consumo. Los errores usan el clasificador de lectura y una causa privada; cancelación conserva su semántica antes de preparación, después de ella y durante GET.
