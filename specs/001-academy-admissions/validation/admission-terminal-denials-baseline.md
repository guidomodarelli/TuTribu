# Rechazos terminales y recuperación de admisión

Incremento sobre `8c4a6f21`: completa la conservación de rechazos conocidos de los comandos comunes. El objetivo mantiene todo el scope de 212 tareas; las tareas de matching completo, fuentes personales/históricas y gates operativos no se cierran por este fix.

## Problema reproducido y solución

Dos casos PostgreSQL nuevos rechazaban correctamente falta de habilitación y conflicto de owner, pero no guardaban un resultado terminal: el claim quedaba `started` y no había referencia pública de conclusión. El rojo nativo terminó en 226,06 s. Cuatro recuperaciones locales rechazaban un DTO de negocio terminado como contrato no utilizable.

El writer conserva un snapshot mínimo `denied` con código cerrado y referencia propia de solicitud cuando corresponde. Un savepoint revierte todo staging del comando antes de completar sólo su ledger original. Auth, permisos, transporte y contratos inutilizables quedan fuera de esa clasificación; conservan el rollback exterior y no se convierten en rechazo confirmado. La lectura usa autorización actual y no reclama leases. Replay precede al CAS; un cambio de lista posterior no transforma la operación anterior en ingreso.

El browser verifica la identidad de la operación original. Una respuesta de negocio `completed` es definitiva; `started`, respuesta perdida o id ajeno conservan incertidumbre. La UI recupera el motivo seguro, preserva explicación/motivo, retira el intent terminado y no anuncia ingreso ni aprobación. La cancelación/decisión recuperadas siguen ligadas a la solicitud exacta.

No cambia esquema productivo ni requiere una nueva migración: se usa el ledger y los readers versionados existentes. El DTO propio se valida con el guard real; no se schema-validan filas PostgreSQL o payloads de proveedores. Los nuevos códigos/SQL/schemas estáticos pertenecen a `constants/`, con unions explícitas y `satisfies`.
