# Preparación local y plazo del RPC

El objetivo general sigue activo: 78/212 tareas completas y 134 pendientes. No se acredita una matriz Native nueva ni un gate de producción mediante este incremento.

Native telefónico `50187` sobre el build anterior observó en Chromium390 un intento y entrega `unknown`, SDK2, una reserva consumida, duración HTTP 78771 ms y diagnóstico late/unexpected_failure. El contador de transporte acredita que ese intento no alcanzó el SDK, pero esa observación no identifica por sí sola cuál lectura SQL tardó. No se reenvió el original ni se liberó su consumo.

El dispatcher anterior aplicaba `requestTimeoutMs` a `sender.send`, que incluía preparación local, SecretStore y resolución de proveedor antes del SDK. TDD `c4fd74` reproduce el defecto con SDK real y transporte propio: preparación local de 60 ms, RPC previsto de 30 ms y run de 300 ms produce unknown/accepted0 sin entrada de SDK aunque queda tiempo de ejecución. Las cifras reducidas pertenecen al test; los defaults de producto no se modifican.

El puerto ahora devuelve una operación preparada opaca. Preparación y resolución de proveedor usan el tiempo restante del run; el RPC posterior usa el menor entre `requestTimeoutMs` y el tiempo restante. Se conservan defaults 15 s/45 s, lease90 y concurrencia2. Se revalida abort después de preparar y antes de enviar. Una preparación que termina tarde no ejecuta send ni inicia SDK; el marker y el consumo permanecen inciertos, con finalización retenida del trabajo original. El timeout del RPC conserva la reconciliación de su respuesta original tardía, sin POST adicional ni cambios en contadores ya publicados.

`MessagingDispatchDeadlineError` identifica un deadline local real con etapa/duración, sin atribuir resultado al proveedor. El boundary registra sólo etapa, código propio e IDs de entrega/intento. El IPC de tests admite prepare y conserva la allowlist de códigos, sin raw payload/cause/contacto/código/credencial. Las clases concretas conservan send como conveniencia de compatibilidad; el scheduler y los ports usan la operación preparada, sin singleton ni fallback.
